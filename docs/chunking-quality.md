# 切分质量的人工判据

> 这份文档定的是**人怎么读样本、怎么打勾**。
> 样本产物在 `data/samples/chunking/`（脚本 `scripts/chunking_samples.py` 导出，**不入库**）。
>
> **为什么需要人工判据**：块数、块长分布、冗余率都能量化，但它们**不反映质量** ——
> 100 个 50 字的块和 20 个 250 字的块可以有一模一样的"平均块长"，质量却天差地别。
> 所以必须有人真的读一遍。本文档把"读什么"固定下来，否则每次读的人的关注点会漂移，
> 不同周的数据就没法比。

---

## 判据一：句子是否完整

**看什么**：块的**首字符**与**末字符**。

| 现象 | 判定 |
| --- | --- |
| 块首是一个完整的句子开头（或标题、或续接标记） | ✅ |
| 块首是半句（开头就是从主语中间断出来的，如 `"成付款，逾期按日…"`） | ❌ 断裂 |
| 块尾落在句末标点（`。！？；`）或段落自然结束 | ✅ |
| 块尾停在一个词中间（如 `"…验收标"` / `"支付合同价"`） | ❌ 断裂 |

**为什么这条最硬**：它是唯一一条**能自动判定 90%** 的判据。
"块尾是否以句末标点结束"用正则可以查；"块首是否半句"需要结合上一块尾看。

**自动检测的边界（必须写清楚）**：
- 表格块、代码块、标题块**不以句末标点结尾是正常的** —— 它们不是句子
- 列表项（`- xxx` / `1. xxx`）本身可能不带标点
- 所以自动判定的结果要人工复核**可疑项**，不能直接当结论

**实测参照**：W4 的 `DelimiterSplitter` 在这条上全绿（5/5 块尾落在 `。`），
而 LangChain 是 1/5（4 块停在半个词上）。见 `delimiter.py` 的实测表。

## 判据二：段落是否被拦腰切

**看什么**：**一个完整的论述单元**是否落在同一个块里。

"论述单元"的判定标准（按优先级）：

1. 一个条款 / 一个条目（"第六条 违约责任"那一段）
2. 一个带条件的因果句群（"若 A，则 B。C 由此产生。"）
3. 一个带数据说明的段落（"下表列出…" + 表格 + "其中第二期…"）

| 现象 | 判定 |
| --- | --- |
| 整个条款在一块的**字数占比 ≥ 90%** | ✅ |
| 条件与后果被分到两块（前半块只有"若甲方未按期付款"，后半块只有"则乙方有权…"） | ❌ 拦腰切 |
| 表格与它的引导句被分到两块（"下表列出各期金额" + 表格） | ⚠️ 可接受但要看检索后果 |
| 一个条款被切成 3 块以上 | ❌ 严重切碎 |

**这条最需要人工**：机器只能近似（"块首是否以半个句子开头"），
而"这两块是不是一个论述单元"是语义判断。**这就是为什么必须有人读样本。**

**为什么它的后果比判据一严重**：判据一断的是句子（模型能看到残缺，仍能判断"材料不完整"），
判据二断的是**论述结构** —— 模型看到"若 A"却看不到"则 B"，
会**自信地给出一个错答案**（"合同没规定后果"），而这是最危险的一类错误。

## 判据三：标题与内容是否分离

**看什么**：块首的标题**有没有带着它的正文**。

| 现象 | 判定 |
| --- | --- |
| 块首是标题，紧跟它的正文 | ✅ |
| 块首是标题，**块里只有标题**（正文在别的块） | ❌ 标题孤儿 |
| 块里没有标题，且**看得出是半路截出来的**（"这一节"、"如下所示"指代不明） | ❌ 上下文缺失 |
| 二次切的后续片带了路径标记（`【L2 > 标题】`） | ✅（这是 `heading_keep_path` 的目的） |

**这条最容易自动判定**：见 `heading.py::_is_heading_only` ——
"去掉标题行后正文为空"就是标题孤儿。实测 `docs/w4-checklist.md` 上，
第一版 heading 策略产出了 `## P0-2` 的 27 字纯标题块（正文 518 字在下一块），
判据三当场就抓到了它。

> 这条也验证了 `chunking-predictions.md` 末尾那个附带预判：
> **"标题与内容是否分离"能自动判定**，确实如此。

## 怎么用这三条

### 读样本的顺序

1. 先看**判据三**（最快，几乎不用读内容，扫块首块尾就行）
2. 再看**判据一**（看每块首尾，标记可疑项）
3. 最后看**判据二**（要读，最慢，但最重要）

顺序是从"最便宜"到"最贵"：判据三能把"标题孤儿"那批块直接圈出来，
后面两条就不用在那批块上花时间。

### 打分表怎么填

每个样本一行，三条判据各给一个 0~1 的分数：

```
样本                     策略        判据一  判据二  判据三   备注
sample20.pdf             recursive   0.90   0.85   1.00    块尾全在句末；跨页句被重叠救回
sample20.pdf             heading     0.90   0.70   0.60    降级为按页切，每页一块，页内跨主题
w4-checklist.md          heading     0.95   0.90   0.95    孤儿标题已合并；小节粒度不均匀
```

**分数的含义要说清**（否则 0.85 与 0.90 的差别没人知道代表什么）：

| 分数 | 含义 |
| --- | --- |
| 1.00 | 全部符合，没有一处例外 |
| 0.85~0.99 | 有个别例外，但都是边缘情况（表格、列表项） |
| 0.60~0.84 | 有一批块不符合，但主体结构还行 |
| < 0.60 | 系统性失效 —— 这条判据在这个策略/文档组合上不成立 |

### 一个必须承认的边界

**分数不是跨文档可比的。** 一份"每页 108 字的合成 PDF"与"44 段的多级标题 md"
本身难度不同：后者的判据二天然容易拿高分（每节内容自足），
前者的判据二天然难（PDF 页内可能跨三个主题）。

所以结论要写成 **"在这个文档上，A 策略比 B 策略好 X 分"**，
而不是 **"A 策略全局比 B 好 X 分"** —— 后者需要一份文档类型分布，
而我们现在**没有**。

## 与自动指标的关系（避免自欺）

`scripts/chunking_samples.py` 会输出 `summary.json`，里面是块数、块长、冗余率。
这些数字**能回答"有没有明显异常"，不能回答"切得好不好"**：

| 数字 | 它能说明什么 | 它不能说明什么 |
| --- | --- | --- |
| 块数 | 是否切碎（块数接近段数 = 没合并） | 块内容是否完整 |
| 平均块长 | 是否远离预算（说明有大量短块/超长块） | 短块是"该短"还是"被切碎" |
| **冗余率** | 重叠的真实成本（递归字符约 9.4%，语义策略为负 = 句子被丢） | 冗余是否换来了更好的边界 |
| **半句率** | 切点是否落在句子边界上（7% vs 34% 差一个量级） | 论述是否被拦腰切（判据二仍需人读） |

> **半句率**（W5 周二新增，`app/rag/chunking/quality.py`）是这三条判据里
> **唯一已经自动化**的那条 —— 它大致对应判据一。定义与判据细节见
> [chunking-boundaries.md](chunking-boundaries.md)。
>
> 它测不出判据二，这是它的边界而不是缺陷：`若甲方未按期付款。` 有句号，
> 但它是一个只有条件、没有后果的残句 —— 机器看不出来，人一眼就能。
>
> **冗余率为负是有意义的信号**：周一那版语义策略实测 -27.8%，那不是"省了字数"，
> 是**句子被丢了**（覆盖率只剩 72%）。修好之后是 -0.1%（四舍五入的正常误差）。
> 所以"字数总和"不能当作"覆盖了原文"的证据 —— 要查覆盖，必须回原文比对。
