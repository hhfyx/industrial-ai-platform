# 上下文压缩：效果、代价与决策（W6 周五）

> 目标：在保住答案句的前提下砍 token，省成本 + 抗 lost in the middle。
> 代码：`app/rag/generation/compress.py`｜命令：`make compress-eval`

## 〇、决策：**不接入最终链路**（本轮）

| 项 | 结论 |
| --- | --- |
| 压缩能力 | ✅ 已实现并可注入（`build_context(texts=...)`） |
| 默认是否启用 | ❌ **不启用** |
| 理由 | **上下文预算根本没用满** —— 平均只用掉 **17.7%**，0/40 题超预算 |

这是任务书预判过的一种结果（"可能结论是'不进'"）。但**理由不是"压缩不好"，
而是"现在没有需要压缩的问题"** —— 这两者完全不同，后者可以随时推翻。

### 触发条件（什么时候该重新考虑）

**当前 top5 上下文长度分布（全 40 条）**：

| 指标 | 值 |
| --- | ---: |
| 最短 | 588 字符 |
| p50 | **1060 字符** |
| 最长 | 1600 字符 |
| 预算（`max_context_chars`） | 6000 字符 |
| 超预算题数 | **0/40** |
| **平均预算使用率** | **17.7%** |

**当出现下面任一条件时，压缩就该重新评估：**

1. `top_k` 提到 10~20（上下文翻倍，p50 会到 2100~4200）
2. 块长从 500 调到 800+（W5 已测过 800 会撞 bge 截断墙，但没人说不能调）
3. 语料换成 PDF 长页 / 工业长文档 —— **这是最可能的触发场景**
4. 出现 `lost in the middle` 的实测症状（答案在中段被忽略）
5. 单次请求上下文成本成为账单可见项

**这五条写在这里，是为了让"下次要不要用"有判据** ——
否则半年后会变成"当时为什么没用？没人记得"。

## 一、为什么要压（目标写清）

**目标**：在保住答案句的前提下砍 token。

**当前的实际数字**：精排后 Top5 每块平均约 200 字符（不是任务书预估的 500 token），
5 块合计 **1060 字符（p50）**。而预算是 6000 字符。

    任务书预估：5 块 × 500 token ≈ 2500 token 上下文
    本项目实测：5 块合计 1060 字符 ≈ 700 token

**差 3.5 倍。** 原因：本项目块长 `chunk_chars=500` 是**字符**上限，
而实际块的中位数只有 **131 字符**（W6 周三实测）。500 是天花板不是均值。

所以"为什么压"这个问题在本项目上的答案是：**暂时不需要压**。

## 二、句子级压缩：实现

### 2.1 算法

1. **拆句**：按 `SENTENCE_END`（`。！？；.!?;`）切，**保留标点**
2. **打分**：每句与 query 的相关性 = `共同实词 IDF 之和 / sqrt(句子长度)`
3. **选句**：按分数取前 N，**再按原顺序重组**（保序）
4. **兜底**：至少保留 `min_ratio`（30%）或 `min_sentences`（2 句）

### 2.2 为什么打分不用 LLM

压缩是**每次请求**都要做的。用 LLM 打分会让延迟翻倍，而"这句和问题有没有共同实词"
字面就够判了 —— 这正是 W6 周一 BM25 证明过的强项。

### 2.3 为什么用"组内 IDF"而不是全库 IDF

两个理由：

1. **目的不同**：压缩要回答"**在这几个候选块里**，哪句最能区分"。
   全库 IDF 会让"错误码"这类词被压得很低（全库常见），但在这 5 块里它可能正是关键。
2. **依赖方向**：全库 IDF 需要持有 BM25 索引，而压缩不该依赖它 ——
   部署精简版（无 jieba）也该能压缩。

### 2.4 位置加成刻意做得很小

`POSITION_BONUS = (1.15, 1.08)` —— 只有前两句有微弱加成。

**为什么不加大**：W6 周三的截断实验证明过，答案可能在块尾
（`head` 策略在答案居末尾时得分 0.65）。所以不能真的偏好块首，
这个加成只够在"两句分数接近"时起决胜作用。

## 三、效果与代价：三个数字

### 3.1 成本

| keep_ratio | 原文 | 压缩后 | **节省** | 兜底块 | 空块 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0.3 | 37230 | 20268 | **45.6%** | 126 | 0 |
| 0.5 | 37230 | 23252 | **37.5%** | 36 | 0 |
| 0.7 | 37230 | 30081 | 19.2% | 36 | 0 |
| 1.0 | 37230 | 37597 | −1.0% | 0 | 0 |

`keep=1.0` 时是 **−1.0%**（不是 0%）—— 因为保序重组用空格拼句子，
比原文多了空格。**这个负值是诚实的**：不压缩就不该省。

### 3.2 检索：**必然是一条水平线**

| keep_ratio | Recall@5 | MRR |
| ---: | ---: | ---: |
| 0.3 | 40.0% | 0.2367 |
| 0.5 | 40.0% | 0.2367 |
| 0.7 | 40.0% | 0.2367 |
| 1.0 | 40.0% | 0.2367 |

**这不是"脚本没测"，是设计如此。** 压缩不改变块的可检索身份，
所以 Recall@5 与压缩参数无关。

> 如果哪天它随压缩参数变化了，说明实现把压缩写进了索引 —— **那是 bug**。

### 3.3 答案质量代理指标（抽检 20 条）

| keep_ratio | 答案句存活 | 锚点存活 | 判定 |
| ---: | ---: | ---: | :---: |
| 0.3 | **25.0%** | 50.0% | ⚠ 风险 |
| 0.5 | **37.5%** | 62.5% | ⚠ 风险 |
| 0.7 | 62.5% | 87.5% | OK |
| **1.0** | **100.0%** | **100.0%** | OK |

这是一条清晰的**成本-质量权衡曲线**：

- `keep=0.3`：省 45.6% token，但**只有 1/4 的答案句还在** —— 高风险
- `keep=0.5`：省 37.5%，答案句近 4 成还在 —— 仍然危险
- `keep=0.7`：省 19.2%，62.5% 答案句存活 —— 勉强可用
- `keep=1.0`：不省，100% 存活 —— 基线

**`keep=1.0` 必须是 100%**：如果它不足 100%，说明统计或实现有问题。
这一条是自检 —— 我第一版就是 44.4%，查出是两个 bug（见 §四）。

## 四、修了两个统计 bug（都在"存活率"判定上）

### 4.1 把"召回未命中"算成了"答案句被删"

第一版对所有题统计答案句存活，于是 `keep=1.0`（完全不压缩）只有 44.4%。

原因：那些题的 **gold 块根本没进 top5**（召回未命中），压缩输出里当然没有它。

**这和 W6 周四"天花板"那条是同一个教训**：

> 统计压缩风险之前，先确认候选里有 gold。

修法：`gid not in texts` 就跳过，不计入分母。

### 4.2 锚点跨句子边界导致假失败

第一版直接判 `anchor_quote in compressed`，于是 `keep=1.0` 时锚点存活率只有 50%。

原因：**`quote` 可能跨句子边界**。压缩的保序重组用空格把句子拼起来，
如果 quote 跨越了句号，那么"按句切分再拼回"的文本里多了一个空格，
子串匹配就失败 —— **而内容一个字都没少**。

这正是任务书警告的那件事：

> 压缩后 gold 锚点在压缩文本里可能找不到 → 判定要能处理这种情况。

修法：判"**quote 的各个片段是否都还在**" —— 按标点/空白切片，
每片（≥4 字）都能找到就算存活。这容忍了重组引入的空格差异，
但不容忍"删掉了含 quote 的那句"。

修完后 `keep=1.0` 的锚点存活率是 **100%**，曲线才可信。

> **教训**：一个"看起来很合理"的指标，如果基线（不压缩）不等于满分，
> 那它测的就不是我以为的东西。**先验证基线再相信曲线。**

## 五、风险对照：压缩过头的症状

| 症状 | 判据 | 本轮实测 |
| --- | --- | --- |
| 答案句被删 | 答案句存活 < 60% | `keep=0.3` 是 25%、`keep=0.5` 是 37.5% ✗ |
| 锚点对不上 | 锚点存活 < 70% | `keep=0.3` 是 50%、`keep=0.5` 是 62.5% ✗ |
| 压缩比例失真 | `floor_count` 占比 > 50% | `keep=0.3` 时 126/200 块触发兜底 |
| 压成空块 | 任一块 `text == ""` | **0 个** ✓ |

### 5.1 兜底规则的实测作用

`keep=0.3` 时 **126 块触发兜底**（占 63%）—— 说明"按分数选 30%" 本来会删得更多，
是兜底把它们救了回来。**这正是兜底存在的理由。**

但反过来说：**63% 的块都在靠兜底救场，说明 0.3 这个比例对当前语料已经过头了。**

### 5.2 兜底参数

```python
DEFAULT_MIN_RATIO = 0.30  # 至少留 30% 的句数
DEFAULT_MIN_SENTENCES = 2  # 至少留 2 句
# 两者取更宽松的那个
```

**为什么两个都要**：一块只有 3 句时，30% = 0.9 句 → 向上取整 1 句，可能删掉答案；
而有 2 句下限，至少保住"上下文 + 答案"的搭配。

## 六、必答问题：压缩提高的是检索指标还是生成质量？

**都不是。** 它主要降 token 成本，**同时有以下风险**：

| 轨道 | 压缩的影响 | 本轮实测 |
| --- | --- | --- |
| **成本** | ✅ 降低（可量化） | 省 19.2% ~ 45.6% |
| **检索指标** | **不该有影响**（设计上解耦） | Recall@5 恒为 40.0% |
| **生成质量** | ⚠ **可能下降**（答案句被删） | 答案句存活 25% ~ 62.5% |

### 6.1 为什么这个区分是"本周最容易被自己糊弄过去的一层"

因为**成本数字最显眼、最容易报**。而"省了 40% token"这句话读起来像成果，
但配上"答案句存活 25%"就是灾难 —— 两者**必须同时出现**。

如果只报前者，会得出"压缩很成功"的结论，然后在真机测试时发现模型开始编，
而那时人会怀疑模型、怀疑 prompt —— **查不到压缩头上**。

### 6.2 所以口径必须分开

本脚本产出三张**独立**的表（成本 / 检索 / 答案质量），
且文档里三者并列。**不允许合成一个"综合得分"** ——
那会把权衡藏起来（W5 的 `overall_accuracy` 就踩过这个坑）。

## 七、设计决定：压缩不改可检索身份

这是任务书点名"要在今天就定"的那条。**代码层面的落实**：

| 层 | 用什么 | 压缩影响 |
| --- | --- | --- |
| 切分 / 索引 | `Chunk.text` | ❌ |
| 检索 / 精排 / Recall / MRR | `Chunk.text` | ❌ |
| **只在这里**：拼 prompt | `build_context(texts=...)` | ✅ 唯一入口 |

### 7.1 用"id → 文本"映射，而不是传压缩后的 `Chunk`

如果 `compress_for_prompt()` 返回新的 `Chunk`（换了 text），
那么 `Chunk.id` 会跟着变（它是 `sha256(source+page+正文)` 派生的）——
**引用就指向不了原文了**，UI 点 `[n]` 回查会落空。

用映射的话：`chunks` 仍是检索层给的那批原块，`id` / `pages` / `location` 全不变，
只有"贴进 prompt 的那段字"被替换。

**集成校验**：`build_context` 注入压缩文本后，引用 `chunk_id` 完全一致 ✓
（脚本每次跑都会验证这条）。

### 7.2 双重防护

1. `Chunk` 是 **frozen dataclass** —— 写 `chunk.text = ...` 直接 `FrozenInstanceError`
2. `test_compress_does_not_mutate_chunk` 断言 `chunk.text` / `chunk.id` 不变

我用"故意注入 `chunk.text = text`"验证过：两层都会拦住。
