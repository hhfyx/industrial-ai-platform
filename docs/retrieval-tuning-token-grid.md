## 〇、一句话结论（以及一条不能省的限定）

在 13 份文档（12.1 万字）+ 20 条检索金标上：

1. **`chunk_chars=500 / overlap=50` 在 token 上是安全的**：527 块里只有 1 块超过
   512 token（0.19%）。这条任务要求验证的 C3 风险（超长块被 bge 静默截断）**不成立**。
2. **但 `chunk_chars=800 / 1000` 不安全**：越界率跳到 **12.2% / 14.3%**。
   这是本次最有操作价值的一条：**调大块长会撞上截断墙，而撞上时没有任何报错**。
3. **`chunk_chars` 与 `overlap` 的所有命中率差异，在 20 条样本上都不显著**
   （McNemar 精确检验 p 全部 = 1.0）。**今晚没有证明哪组参数更好**。

限定：**20 条 gold 意味着 1 条翻转 = 5pp**，而置信区间宽达 ±18pp
（65% 的 95% CI 是 [43.3%, 81.9%]）。所以第 3 条不是"参数无所谓"，
是"**这些数据还不足以区分它们**"。要区分，需要先把样本量做上去
（见 §6）。

## 一、Token 审计：用 bge 自己的 tokenizer，不用系数折算

### 为什么不能用 `字数 × 0.676`

`docs/embedding.md` 第 105 行写着"按中文 0.676 tok/字算，500 字 ≈ 350 token"。
那个系数**不是 bge 的**，是从另一个模型网关的 `usage` 反推的
（`scripts/token_result.json`）。

bge 的 vocab 是**字级**的：实测 `付款计划` → `['付','款','计','划']`，4 个汉字 4 个 token。
而本次全语料实测的真实密度是 **0.6667 tok/字** —— 两者在**总量**上接近，
但这不是巧合也不是可以互相替代：

| 口径 | 值 | 用在 500 字上 |
| --- | --- | --- |
| 文档里原来的系数（别家网关） | 0.676 tok/字 | 338 token |
| 本次 bge 实测 | 0.6667 tok/字 | 333 token |

差别很小（1.4%），**所以这次没有翻车**。但成本几乎为零的校验还是要做：
换一个 vocab 更大的模型（比如 bge-m3），或换成英文/代码为主的语料，
系数就会明显偏离。**用系数做安全判断，只有在数过一次之后才知道能不能信。**

> 注意：`0.6667` 是**全语料平均**（含表格、代码、标题）。**单块之间的方差极大**：
> 平均 163 token，但最大 606 token、最小 6 token。平均值对"会不会越界"这个问题
> 没有信息量 —— 那是 §1.2 的直方图要回答的。

### 1.1 结果（`chunk_chars=500 / overlap=50`）

| 指标 | 值 |
| --- | --- |
| 块数 | 527 |
| 平均 token | 163.4 |
| P50 / P95 | 90 / 380 |
| **最大 token** | **606** |
| **超过 512 的块** | **1** |
| **越界占比** | **0.19%** |

**判定：安全。** 任务的阈值是 5%，实测 0.19%，差一个量级。

### 1.2 分布直方图

```
 token 区间      块数    占比  分布
       0-32    122  23.15%  ██████████████
      32-64     42   7.97%  █████
     64-128     98  18.60%  ███████████
    128-256    110  20.87%  █████████████
    256-384    131  24.86%  ███████████████
    384-448     19   3.61%  ██
    448-480      1   0.19%  █
    480-512      3   0.57%  █
    512-640      1   0.19%  █ ← 越界
    640-1024     0   0.00%  ← 越界
       1024+     0   0.00%  ← 越界
```

两个形状值得记：

**① 双峰**。0-32 那一峰（23%）是标题块，128-384 那一峰是正文块。
这个双峰是**结构造成的，不是缺陷** —— `markdown` loader 会把"整块就是一行标题"
单独产出一个 `Document`（`metadata.block="heading"`）。它们平均 16.8 token，
是"最浓缩的信息"（`docs/chunking-quality.md` 判据三），不该为了均一性合并。

**② 512 附近几乎没有块**。448-512 只有 4 块，说明 `chunk_chars=500` 的切分
**没有在边界上堆积** —— 如果有一批块紧贴 512，那说明再改任何参数都会立刻越界。
现在这个形状是"离墙还有余量"。

### 1.3 按 block 类型拆开（这一格才是真相）

| kind | 块数 | 平均 token | 最大 token | 最大字数 | 越界 | 越界率 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| text | 162 | 312.4 | 408 | 500 | 0 | 0.00% |
| code | 135 | 91.3 | 385 | 703 | 0 | 0.00% |
| table | 117 | 181.9 | **606** | **1307** | **1** | 0.85% |
| heading | 113 | 16.8 | 35 | 43 | 0 | 0.00% |

**混在一起看会得到一个漂亮但无用的数字。** 全局"平均 163 token、越界 0.19%"
掩盖了两件事：

- **正文块（text）的最大 token 是 408**，离 512 还有 100 token 的余量。
  这说明 `chunk_chars=500` 对中文正文是**有余量**的，不是"刚好卡住"。
- **唯一的越界块是表格**：`docs/SETUP.md` 第 353 块，1307 字 / 606 token。
  而表格**整块不切**是契约（`app/rag/chunking/base.py` 第 ② 条）——
  为了让行列关系不丢，代价就是超长表格会被截断。
  这正是 `docs/embedding.md` 第 108 行那条"已知损失"，**今天有了具体数字**。

> 所以"超 512 的占比"这个指标，正确的读法是：
> **正文侧 0/162，表格侧 1/117。** 前者要归零，后者是设计取舍。

### 1.4 顺手扫了 800 / 1000（这是最有价值的一条副产品）

| chunk_chars | 块数 | 平均 token | 最大 token | 越界块 | **越界占比** |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 300 | 667 | 136.9 | 606 | 1 | 0.15% |
| **500** | 527 | 163.4 | 606 | 1 | **0.19%** |
| **800** | 461 | 181.2 | 646 | 56 | **12.15%** |
| **1000** | 441 | 187.6 | 791 | 63 | **14.29%** |

**500 → 800 是一个断崖**：越界率从 0.19% 跳到 12.15%（61 倍），
而平均 token 只从 163 涨到 181（+11%）。

这个不对称正是"墙"的特征：块长逼近 512 之后，**分布的尾巴开始被截断墙切掉**。
也解释了一个现象 —— 平均块长由 `chunk_chars` 的**上限**决定，
而实际块长由**分隔符分布**决定（正文块最多 408 token，远没到 500 字 × 0.67 = 335 的上限，
因为 `_merge` 只合并完整原子片，装不下就开新块）。

> ⚠️ **这条是今晚唯一可以直接拿去做决定的数据**：
> 如果 W6 有人想把 `chunk_chars` 调到 800 以上（"块大一点上下文更完整"），
> 他会把 12% 的块推进 bge 的截断区，**而那不会报错**。

**复现**：

```powershell
uv run python -X utf8 scripts/token_audit.py
# 产出 scripts/token_audit.json
```

## 二、口径：为什么 7 次重建而不是 12 次

任务定的纪律：

```
粗筛：overlap 固定 50，只动 chunk ∈ {300, 500, 800, 1000}    → 4 次
细调：在粗筛最优的 chunk 上，overlap ∈ {0, 50, 100}          → 3 次
```

**不是 4×3=12**，因为两轮的信息价值不对等：

- `chunk_chars` 改的是**块的粒度**（一句话在一块的哪个位置、一个论述单元能不能装下），
  对命中率的影响是结构性的。
- `overlap` 改的是**相邻块共享 50 字**，只影响边界附近的内容重复。
  它和 `chunk_chars` 之间**几乎没有交互** —— 不存在"chunk=800 时 overlap 要取 100"这种规律。

所以先在 overlap=50 上把 chunk 的量级定下来，再在那一档上细调。
全网格 12 次会把 9 次花在"重叠信息的重复测量"上。

> 这个纪律 W6 调检索权重、W7 调 judge 参数时会反复用到：
> **先找主效应，再在主效应的最优值附近做局部微调。**

### 语料怎么造的（这一条决定了数字能不能信）

`scripts/chunking_samples.py` 用的是 loader 原样输出（1530 个 `Document`，
平均 172 字）。**那种粒度上网格搜索无效** —— 实测 chunk 从 500 改到 1000，
块数只从 1606 变成 1563（差 2.7%），因为每段本来就短于预算，切分器没机会合并。

所以 `scripts/retrieval_harness.py` 先把每份文档的**正文段按原顺序合并**成一个
`Document`（模拟"用户上传了一整份文档"），再切。实测 chunk 从 300 到 1000，
块数 667 → 441（差 34%），**参数真的起作用了**。

表格块与代码块**不参与合并**（它们在 `recursive` 策略下整块不切，契约要求），
原地成块传入。

代价写清：合并丢掉了 `heading_level` 元数据，所以 **`heading` 策略不能在合并语料上跑**
（它靠元数据找节边界，合并后只能退化成按字数切）。网格搜索因此只用 `recursive`。
跨策略比较是 `chunking_samples.py` 的活，不是这个网格的活。

### 命中怎么判

`eval/retrieval-gold.jsonl` 20 条，每条的 `anchor` 是**逐字原文片段**
（15–60 字，在源文件里唯一）。判"命中"= 返回的 top_k 块里有没有哪一块**包含该 anchor**。

三条口径一起记，否则数字不可比：

| 项 | 取值 | 理由 |
| --- | --- | --- |
| `top_k` | **5** | 全项目唯一默认值（`retrieval.DEFAULT_TOP_K`），不另定 |
| 主指标 | `hit@5` | 有没有命中 |
| 副指标 | `MRR` | 命中排第几的倒数（区分"排第一"和"勉强第五"） |

**这套金标由独立 subagent 生成并逐条校验**（anchor 在源文件内出现次数 == 1，
超出 1 次说明该片段可被多处匹配，命中判定就失去区分度）。
校验代码在 `scripts/retrieval_harness.py::validate_gold`，**跑之前必过**——
金标写错时"未命中"看起来和"检索失败"一模一样（`chroma_acceptance.py`
在 W4 踩过这个坑，那次 gold 里写了一条语料里根本不存在的句子）。

## 三、粗筛：chunk_chars 扫描（overlap=50）

| chunk | 块数 | 平均 token | 越界 | 命中 hit@5 | MRR | 重复率 | 索引 ms |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| **300** | 667 | 136.9 | 1 | **65.0%** (13/20) | 0.424 | 8.0% | 65.6 |
| **500** | 527 | 163.4 | 1 | 60.0% (12/20) | 0.429 | 7.0% | 40.6 |
| **800** | 461 | 181.2 | **56** | 55.0% (11/20) | 0.417 | 4.0% | 47.9 |
| **1000** | 441 | 187.6 | **63** | 55.0% (11/20) | 0.463 | 2.5% | 42.3 |

> `索引 ms` 是**热缓存**下的数字（切分 + 编码 + 入库），冷缓存那一次的对照见 §5。
> `重复率` = top_k 里来自相邻 chunk 的无序对占比（见 §4.2 定义）。

### 看起来 300 最好，但这条不能直接采信

命中率随 chunk 增大而单调下降（65% → 60% → 55% → 55%），**方向上很干净**。
但逐条看翻转就知道为什么不显著：

| id | 300 | 500 | 800 | 1000 |
| --- | --- | --- | --- | --- |
| rg-03 | 未命中 | top1 | 未命中 | top2 |
| rg-06 | top5 | 未命中 | top3 | 未命中 |
| rg-08 | top5 | 未命中 | 未命中 | 未命中 |
| rg-09 | 未命中 | top1 | top1 | top1 |
| rg-13 | top1 | 未命中 | 未命中 | 未命中 |
| rg-14 | top1 | 未命中 | 未命中 | 未命中 |
| rg-15 | 未命中 | 未命中 | 未命中 | top1 |
| rg-17 | top1 | top1 | top1 | 未命中 |
| rg-18 | 未命中 | top3 | 未命中 | top4 |

`300 vs 500`：仅 300 命中 4 条、仅 500 命中 3 条 → **McNemar 精确 p = 1.0000**。
`500 vs 800`、`500 vs 1000` 同样 p = 1.0000。

**读法**：净差 1 条（5pp），而双向翻转各有 3-4 条。这不是"300 更好"，
是"**这两个档位在 20 条样本上分不开**"。

### 那该选哪个？按代价选，不按噪声选

既然命中率分不开，就按**确定性代价**选：

| chunk | 块数 | 越界 | 索引耗时（热） | 判断 |
| ---: | ---: | ---: | ---: | --- |
| 300 | 667 | 1 | 65.6 ms | 块数最多（+26.6% vs 500），检索时 top_k 里更容易挤进同主题碎片 |
| **500** | 527 | **1** | **40.6 ms** | **维持现状** |
| 800 | 461 | **56** | 47.9 ms | ❌ 12% 块被截断 |
| 1000 | 441 | **63** | 42.3 ms | ❌ 14% 块被截断 |

**保留 500**，理由三条（都独立于那个不显著的 +5pp）：

1. **越界安全**：500 是"越界 1 块"的最大档位。800 起就是 12%。
2. **块数适中**：300 要多付 26.6% 的块（667 vs 527），多出来的都是同主题碎片，
   top_k=5 的窗口里挤进重复内容的概率更高（§4 的重复率 8.0% vs 7.0% 也指向这点）。
3. **不因噪声改默认值**：把 500 改成 300，收益是 1 条翻转（p=1.0），
   代价是块数 +26.6%，且**已有的索引全部失效**（`store_id` 位置派生，参数一变就重建）。

> 这就是"粗筛最优"的定义：`hit@5` → 越界数 → 块数 → MRR 的字典序比较。
> 这条链必须写出来（`grid_search.pick_best`），否则两个人跑同样的数据会选出不同的组，
> 然后各自写的文档互相矛盾。

**复现**：

```powershell
uv run python -X utf8 scripts/grid_search.py --stage coarse
```

## 四、细调：overlap 扫描（chunk_chars=300）

> 按 `pick_best` 的字典序，粗筛选出 **chunk_chars=300**（hit@5 最高）。
> 但见 §3 的分析：**这个"最优"是噪声选出来的**。下面两组数据要放在这个前提下读。

| overlap | 块数 | 平均 token | 命中 hit@5 | MRR | 重复率 | 索引 ms |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| **0** | 614 | 131.5 | 60.0% (12/20) | 0.422 | 5.5% | 61.3 |
| **50** | 667 | 136.9 | 65.0% (13/20) | 0.424 | 8.0% | 66.1 |
| **100** | 741 | 143.9 | 65.0% (13/20) | **0.468** | 11.0% | 76.1 |

### 4.1 必答题：overlap 从 0 加到 50，命中率涨了多少，chunk 数涨了多少？

| 项 | overlap=0 | overlap=50 | 变化 |
| --- | ---: | ---: | --- |
| **命中率 hit@5** | 60.0% (12/20) | 65.0% (13/20) | **+5.0pp** |
| **chunk 数** | 614 | 667 | **+8.6%** |
| 重复内容率 | 5.5% | 8.0% | +2.5pp |
| 索引耗时 | 61.3 ms | 66.1 ms | +7.8% |

**按任务给的性价比算法**（"chunk 数涨 30% 而命中率只涨 2%，那 50 就不划算"）：

```
块数 +8.6%   vs   命中率 +5.0pp
```

**块增幅 > 命中率相对增幅**（8.6% vs 相对 8.3%），按这个尺子算是**约等于打平**。

但真正该看的是**翻转结构**：

| | 条数 |
| --- | ---: |
| 仅 overlap=0 命中 | **2** |
| 仅 overlap=50 命中 | **3** |
| 两者都命中 | 10 |
| 两者都不命中 | 5 |

**McNemar 精确检验 p = 1.0000。** 两边各有翻转，净差 1 条 ——
**这不是"overlap 50 更好"，是"20 条样本分不出 overlap 0 和 50"**。

> 任务里那个"不划算"的判据（块数涨 30%、命中率涨 2%）在这里**没有触发**，
> 但触发了更需要警惕的情况：**净收益落在噪声里**。
> 这种情况比"不划算"更难处理，因为它长得像"有效"，容易让人写进文档当结论。

### 4.2 重复内容率：overlap 唯一直接产生的坏处

定义（`retrieval_harness.py` 模块 docstring 第三节）：

> 对每条查询的 top_k 命中列表，统计有多少**无序对** (i, j) 满足
> `同一份文档 && abs(chunk_index 之差) == 1`。分母是总对数。

`chunk_index` 用 `Chunk.index`（同一 `Document` 内部序号），所以"相邻"是
**切分意义上的相邻**。未命中的查询贡献 0/0，**不进分母** ——
否则"没检出东西"会被算成"没有重复内容"，把一个坏结果美化成好结果。

| overlap | 重复内容率 |
| ---: | ---: |
| 0 | 5.5% |
| 50 | 8.0% |
| 100 | 11.0% |

**这条是单调的、可解释的、且与噪声无关的**：overlap 越大，相邻块共享的字越多，
两块向量越像，一起挤进 top_k 的概率越高。5.5 → 8.0 → 11.0，每档 +2.5~3pp。

**关键对照**：overlap 从 50 加到 100，命中率**完全没变**（13/20 → 13/20），
但重复率 +3pp、块数 +11%。也就是说 **overlap=100 付了全部代价、一分收益没有**。

> 这是今晚最硬的一条结论，因为它是**零收益**，不是"收益小到看不出来"。

### 4.3 细调的判断

| overlap | 命中 | MRR | 重复率 | 块数 | 判断 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 0 | 60.0% | 0.422 | 5.5% | 614 | 最省，但失去"跨边界条件句"的保护 |
| **50** | 65.0% | 0.424 | 8.0% | 667 | **维持现状** |
| 100 | 65.0% | **0.468** | 11.0% | 741 | ❌ 零命中收益，代价最全 |

**保留 50。** 但要把话说完整：

- **保留 50 不是因为数据证明了它好**（p=1.0），而是因为
  ①overlap=0 有 2 条查询只在有重叠时命中（`rg-06`/`rg-09` 的反面案例）；
  ②overlap=100 已证明零收益；
  ③50 是当前线上默认值，改它要重建索引。
- **`overlap=100` 的 MRR 0.468 是三个里最高的**，但命中条数一样（13 条），
  只是排得更靠前。在 p=1.0 的前提下，这个差是排位抖动 ——
  **不足以支撑"改成 100"**，因为要多付 11% 的块和 3pp 的重复内容。

**复现**：

```powershell
uv run python -X utf8 scripts/grid_search.py --stage fine --best-chunk 300
```

## 五、缓存验证：第二次重建快了多少

### 5.1 前提：这个缓存是今天新写的

**开始之前，代码库里没有任何 embedding 缓存。** `app/rag/indexing.py` 第 213 行
直接调 `self.embedder.embed(...)`，每次重建都重新编码全部块。

所以"确认缓存命中"这一步**不是验证一个已有机制，而是先把它实现出来**。
实现在 `app/rag/embedding/cache.py`（`CachedEmbedder` + sqlite 后端）。

### 5.2 缓存键设计（"没命中就查 key 设计"的答案）

```python
sha256(f"{model_name}\x1f{dimension}\x1f{text}")  # 取前 32 位
```

三个字段少一个都会**静默串味**：

| 字段 | 不写进去会怎样 |
| --- | --- |
| `model_name` | 换模型后仍命中旧向量 —— 而**维度可能恰好相同**（512 维的模型不止 bge 一个），于是"换了模型效果变差"永远查不出来 |
| `dimension` | 同上，且报错点会跑到 `ChromaStore` 的"维度不匹配"，离真正的原因很远 |
| `text` | —— |

三个设计决定值得单独记：

**① 不对 `text` 做 strip / 归一化。** `" 付款 "` 与 `"付款"` 是两个不同输入，
模型给出的向量本来就不同。为了多几个命中而把它们并成一个键，等于拿
"省几毫秒"换"向量与文本不再一一对应"——**这种不一致没有任何报错**。

**② 键里不放时间戳 / 随机数 / 进程 id。** 那些会让同一次输入每次都算出新键，
命中率恒为 0 —— 而那看起来和"缓存没生效"一模一样，最难查。

**③ 只缓存 passage 侧（`embed`），不缓存 `embed_query`。** 后者要加检索指令前缀，
想在缓存层命中就得把前缀逻辑再实现一遍 —— 那份逻辑一旦与 `bge.py` 漂移，
症状是"前缀有时加有时不加"，**没有报错，只是命中率低一点**。
这正是 `bge.py` 用 `embed_query` 接口而不是靠注释提醒要防的那类故障。

### 5.3 实测：同参数连跑两次

| 步骤 | 耗时 | 缓存命中 |
| --- | ---: | --- |
| ① 删掉 664 条 key 后重建（零命中） | **9498.0 ms** | 0 / 667 |
| ② 立刻重建（同输入） | **40.3 ms** | **667 / 667** |
| **提速** | **-9457.7 ms** | **99.6%** |
| ③ 开新连接复查（模拟换进程） | — | 667 / 667 |

**提速百分比：99.6%。**

两点必须说清，否则这个数字会被误读：

1. **冷/热都排除了模型加载。** 模型（17 s）在第一次 `embed` 时就加载完了，
   不进这个对比。混进去会把提速比夸大到失真。
2. **①→②的对照是干净的**：切分结果逐字节相同，`embed()` 输入逐个相同，
   差异只可能来自缓存。拿"网格里第 2 组比第 1 组快"当证据是不行的 ——
   不同 chunk 切出来的文本没有一句一样，热缓存对它们几乎没帮助。

### 5.4 整张网格的冷热对照

同一天跑了两次完整网格（`scripts/grid_search.json` 冷、`scripts/grid_search.warm.json` 热）：

| chunk | 冷缓存 索引 ms | 热缓存 索引 ms | 提速 |
| ---: | ---: | ---: | ---: |
| 300 | 20559.3 † | 65.6 | — |
| 500 | 4638.2 | 40.6 | **99.1%** |
| 800 | 3897.0 | 47.9 | **98.8%** |
| 1000 | 3224.3 | 42.3 | **98.7%** |

† 第一组含模型加载（约 11 s），不参与提速计算。

**两轮的命中率逐组完全一致**（65/60/55/55）。这不只是"缓存没搞坏结果"，
也是缓存正确性的直接证据：**命中缓存后回读的向量与重新编码的向量，
在 20 条查询上没有产生任何排序变化**。

### 5.5 一个必须承认的精度损失

向量以 **fp32**（`struct` 格式 `f`）存进 sqlite BLOB，回读后与原始 fp64 结果
有约 **1e-8** 的差异（实测最大分量差 8.3e-9）。

不"修"成 fp64 的理由：bge 本身输出就是 fp32
（`model.encode(convert_to_numpy=True)`），用 fp32 存回去是**保持原精度**，
用 fp64 反而是在存储一个不存在的精度，且存储翻倍。

影响面：1e-8 扰动改变余弦值的第 8 位小数，而 bge 的相关/无关分布间隔是
**0.367 → 0.578**（差了近 0.2）。所以 §3/§4 的命中率数字不受缓存影响 ——
§5.4 里"命中率逐组完全一致"是这条的实测确认，不是推断。

**复现**：

```powershell
uv run python -X utf8 scripts/grid_search.py --stage cache
```

## 六、显著性：为什么上面的"改进"一条都不能写成结论

任务没说要做检验，但 20 条样本必须做 —— 否则会写出一份看起来有结论、
实际上都在噪声里的文档。

### 6.1 置信区间（Wilson，n=20）

| 配置 | hit@5 | 95% CI |
| --- | ---: | --- |
| chunk=300 / ov=50 | 65.0% | [43.3%, 81.9%] |
| chunk=500 / ov=50 | 60.0% | [38.7%, 78.1%] |
| chunk=800 / ov=50 | 55.0% | [34.2%, 74.2%] |
| chunk=1000 / ov=50 | 55.0% | [34.2%, 74.2%] |
| chunk=300 / ov=0 | 60.0% | [38.7%, 78.1%] |
| chunk=300 / ov=100 | 65.0% | [43.3%, 81.9%] |

**六组的区间全部互相重叠。** 65% 的区间下界 43.3% 低于 55% 的上界 74.2% ——
即"最好的"和"最差的"在统计上无法区分。

### 6.2 配对检验（McNemar 精确）

同一批 gold、同一批 query，只有"翻转"携带信息。

| 对比 | 仅前者命中 | 仅后者命中 | p 值 | 判定 |
| --- | ---: | ---: | ---: | --- |
| chunk 300 vs 500 | 4 | 3 | 1.0000 | 不显著 |
| chunk 500 vs 800 | 2 | 1 | 1.0000 | 不显著 |
| chunk 500 vs 1000 | 2 | 1 | 1.0000 | 不显著 |
| overlap 0 vs 50 | 2 | 3 | 1.0000 | 不显著 |
| overlap 50 vs 100 | 3 | 3 | 1.0000 | 不显著 |

**全部不显著。** 用精确二项而不是卡方近似，因为 n 小的时候卡方误差很大 ——
而这里恰恰是最需要精确解的场景。

### 6.3 那今晚做的东西有什么用

三条**不依赖显著性**的结论（它们是确定性事实，不是抽样结果）：

1. **`chunk_chars=800/1000` 会让 12%-14% 的块越过 bge 的 512 token 墙。**
   这是全语料逐块数出来的，不是抽样推断。**可以直接拿去阻止一次错误的调参。**
2. **`overlap=100` 零收益。** 命中条数完全不变（13→13），代价是块数 +11%、
   重复率 +3pp。零收益不需要置信区间。
3. **缓存把重建从 9.5 s 压到 40 ms（99.6%），且不改变任何检索结果。**
   这是机制验证，不是效果评估。

以及一条**诚实的负面结论**：

4. **20 条 gold 不足以区分 chunk 300/500/800/1000 与 overlap 0/50/100 的命中率。**
   今晚没有证明哪组参数更好。

## 七、诚实边界

| 边界 | 具体是什么 | 影响 |
| --- | --- | --- |
| **样本量** | 20 条 gold，1 条 = 5pp | 所有命中率差异都不显著；不下"哪组更好"的结论 |
| **单人标注** | gold 由单个 subagent 生成 + 机器校验（anchor 唯一性） | 校验只保证"片段存在且唯一"，不保证"这个问题值得问"。换一个人出题，数字会变 |
| **语料是自造的** | 13 份本项目文档（12.1 万字），都是技术说明文 | 与真实业务语料（合同、工单、FAQ）的难度分布不同。**参数结论不可外推** |
| **只用 recursive 策略** | 合并语料丢掉了 `heading_level`，heading 策略会退化 | 跨策略比较不在本文范围（见 `docs/chunking-quality.md`） |
| **索引耗时不含持久化** | 用 `InMemoryVectorStore`，避开 Chroma 的建库开销 | `index_ms` 只代表"切分 + 编码"，不代表完整重建（Chroma 的耗时见 `docs/chroma-store.md`） |
| **表格越界未解决** | 表格整块不切（契约），1307 字的表必然被截断 | C3 风险在表格上**依然存在**，只是比例低（1/117）。要修得改契约 |
| **缓存无淘汰** | 不做过期 / LRU | 规模上界由"块数 × 换过几套参数"决定（当前 1575 条 / 6.2 MB）。要清就删文件 |

### 下一步该做什么（按性价比排序）

1. **把 gold 扩到 60-100 条**（同一套 anchor 机制，多出题）。
   这是唯一能把"分不出来"变成"分得出来"的动作 —— 当前 CI 宽达 ±18pp，
   要把它压到 ±10pp 需要约 4 倍样本。**这件事的收益高于再跑任何网格。**
2. **给表格单独设一个块长上限**（比如 400 字后按行切，保留表头行）。
   当前"整块不切"的契约在 1307 字的表上直接丢掉 594 字的可检索内容。
   这是一个**已知损失**，不是 bug，但它现在有确切数字了。
3. **`chunk_chars=800+` 加一条断言或告警**：越界率 >5% 时在索引报告里 warning。
   现在这个风险完全静默（bge 截断不报错），是本文发现的最危险的一处。
4. **W6 调检索权重时复用同一套 harness**（`scripts/retrieval_harness.py`）。
   金标、语料、命中判定已经抽好了，换个被测对象即可 ——
   这正是把它抽成模块而不是写在 `grid_search.py` 里的原因。
