# Streamlit UI：流式、引用、以及那 1.5 秒花在哪

> 代码：`app/ui/streamlit_app.py` · `app/rag/query.py`（编排 + 打点）·
> 测试：`tests/test_rag_query_timing.py`（21 条）·
> 数字：`scripts/rag_bench.py` → `scripts/rag_bench.json`

启动：

```powershell
uv run streamlit run app/ui/streamlit_app.py     # http://localhost:8501
```

---

## 0. 必答题：1.5 秒里检索占多少

**检索约 9~11 ms，占首 token 的 0.36%~0.80% —— 不到 1%。**

实测（`scripts/rag_bench.py`，50 页 PDF、bge-small-zh、CPU、top_k=5）：

| 检索段 | 耗时（5 次中位数） |
| --- | ---: |
| query 向量化（bge 单条） | **6 ms** |
| 相似度 + TopK（内存库，50 条） | **3 ms** |
| **合计** | **9 ms** |

分母用**历史实测 TTFT**（不是今天的模拟值）：

| TTFT | 检索占比 |
| ---: | ---: |
| 1128 ms（W2 `latency_result.json` 下沿） | **0.80%** |
| 1460 ms（W3 `docs/sse.md` 流式 TTFT） | **0.62%** |
| 2526 ms（W2 上沿） | **0.36%** |

### 这个数字决定了 W8 该做什么

**优化检索对降低首 token 时间几乎没有帮助。** 9 ms 换到 4.5 ms（提速一倍）
也只是 0.4% → 0.2%，用户完全感知不到。瓶颈在模型侧。

所以：
- ❌ W8 不该做"换更快的向量库"、"加 IVF 索引"、"缓存 query 向量" —— 省不出可感知的时间
- ✅ W8 该做的是**模型侧**：换更快的模型、减少 prompt 长度、预生成首句
- ⚠️ W5 调 TopK 时也**不能用延迟做依据** —— TopK 从 5 到 10 只多约 1 ms，但它对答案质量的影响是实质的

> **不知道就把打点加上。** 这句话的落地就是 `QATiming`：
> `embed_ms` / `search_ms` / `build_context_ms` / `ttft_ms` / `total_ms` 五段分开记。
> 合成一个"耗时 1.2s"，就再也回答不了这个问题。

### 为什么分母不能用模拟值

第一版我拿模拟客户端的 TTFT（29 ms）做分母，算出"检索占 34%"，
还打出了"→ 检索占比显著：值得优化"的结论。

**那是个荒谬的数字**：模型不可能 29 ms 出第一个字。模拟客户端只是"按脚本吐字"，
它的间隔是我设的，和真实模型无关。拿它做分母等于自己编了个结论。

所以脚本现在把模拟值标成 `← **模拟值，非真实 TTFT**`，
并且**用历史实测值算占比**。真实 TTFT 要等有凭据重测 —— 见 §7。

## 1. 五个数字（任务要求）

50 页 PDF 全流程（`scripts/rag_bench.py`）：

| # | 指标 | 数值 |
| --- | --- | ---: |
| ① | 解析 | **714 ms** |
| ② | 索引总计 | **1015 ms**（切分 0 + 编码 300 + 入库 0） |
| ③ | 检索 | **9 ms**（编码 6 + 相似度 3） |
| ④ | 首 token | 1210 ms ⚠️ **模拟值** |
| ⑤ | 总时长 | 1308 ms ⚠️ **模拟值** |

另有冷启动模型加载 **11.0 s**（**不计入请求耗时** —— 它是启动成本）。
索引阶段的大头是**编码 300 ms**（50 块 × bge CPU ≈ 6 ms/块），
解析 714 ms 是 PDF 逐页抽取 + 表格检测（pdfplumber）+ 清洗。

## 2. UI 骨架：上传 → 索引 → 进度

### 三阶段进度条

任务要求进度条显示"解析 N 页 / 切出 M chunk / 编码耗时"。实现方式是
`Indexer` 的**阶段回调**（`OnStage`），而不是 UI 里猜时间：

```python
def on_stage(stage: str, ratio: float, message: str) -> None:
    # stage ∈ {"load", "split", "embed", "store"}
```

| 层 | 职责 |
| --- | --- |
| `Indexer` | 在每个阶段前后打点，调用回调 |
| UI | 把事件翻译成进度条文案 |

**领域层不 import streamlit**。`on_stage=None` 时 CLI 照常工作，
测试传一个假回调 —— 三者都不用改领域代码。

两处刻意的设计：

1. **回调抛异常不能毁掉索引**：进度条是"展示"，索引是"事实"。
   让画进度条 bug 把索引搞挂是最得不偿失的耦合。实测验证（
   `test_index_survives_broken_progress_callback`）。
2. **进度按文件数算，不按阶段算**：阶段只有 4 个，按阶段画会在每个文件里
   从 0 跑到 100 再归零。

### 每个文件的四段耗时都显示

```
✅ sample50.pdf · 50 页 → 50 块 · 解析 714ms / 切分 0ms / 编码 300ms / 入库 1ms
```

只给一个总耗时无法回答"慢在哪一步"。这份展示就是 `IndexReport` 那四个新字段的用途。

## 3. 流式：TTFT 与检索耗时**分开显示**

界面上三个数字并列，**不合并**：

```
🔍 检索 9ms（编码 6 + 相似度 3）　｜　⏱ 首字 1210ms　｜　检索占首字 0.74%　｜　⏳ 总计 1308ms
```

### 关键：检索结果在 TTFT **之前**就上屏

`QAEngine.answer_stream` 的事件顺序是：

```
retrieved  →  delta  →  delta  →  …  →  done
   ↑
   检索完、调用模型之前
```

**这个顺序是必答题的接口落点**：用户在整个 TTFT 期间（1 秒以上）看到的是
"🔍 检索 9ms · 命中 5 块 · 最高分 0.63"，而不是一片空白。

顺序调换**不会报错**，只会让体验退回"空白等待" —— 所以它由测试守着：
`test_stream_emits_retrieved_before_delta`。

## 4. 引用出处：「参考来源」可展开

回答下方列出被真正引用的条目，点开看原文：

```
📖 参考来源（2 条）
[1] 合同.pdf · P7
   违约金按日万分之五支付，累计不超过合同总额的百分之十…
[2] 合同.pdf · P9
   逾期超过三十日，甲方有权解除合同…
```

三个细节：

| 细节 | 理由 |
| --- | --- |
| **只列被引用的块** | 列全部检索结果会让人以为"这些也是依据" |
| 用 `st.text` 而非 `st.markdown` 显示原文 | 原文里的 `#` `\|` `*` 会被 Markdown 渲染吃掉，看起来和 PDF 不一样；用户是拿这段去对照的 |
| 有编号但找不到出处 → **显式警告** | `invalid_refs` 非空说明模型在编，必须可见（`⚠️ 编号 [9] 不在检索结果里，已忽略`） |

最后一条是硬要求：**有编号但找不到出处就是 bug**。静默丢弃会让用户
以为那个 `[9]` 有依据。

## 5. 健壮性：四类都兜住

| # | 场景 | 处理 |
| --- | --- | --- |
| 1 | **空检索** | 拒答话术 + **不调模型**（`_ExplodingClient` 测试证明） |
| 2 | **解析失败** | 指出**哪个文件** + 错误类型与原文；提示持久化到 `session_state.last_error`，重跑后仍可见 |
| 3 | **模型报错** | 显示原因（不抛红色栈）+ 「🔄 重试这一问」按钮 |
| 4 | **长文档** | 三阶段进度条 + 每文件四段耗时 + 扫描件 warning 逐条显示 |

**空知识库时不给输入框**（`st.chat_input` 不渲染），改成一条说明 + 排查提示。
让用户先问、再看到"知识库为空"，是白白浪费一次交互。

## 6. 多轮对话与会话体验

### 历史裁剪

| 层面 | 行为 |
| --- | --- |
| **展示** | 只渲染最近 **3 轮**（6 条），更早的折叠并显示"已折叠 N 条" |
| **传给模型** | 同样只取最近 3 轮，且**只取纯文本**（引用/耗时是给人看的，塞 prompt 只会浪费 token） |

**为什么"折叠"而不是"删除"**：本周不做指代消解（W8 才做），
所以历史在这里的作用只是"让对话连贯"，不是"让模型理解指代"。
把展示与喂模型分开，将来做滚动摘要时不用改渲染逻辑。

> ⚠️ **已知限制**：历史里出现"它/那个条款"时，模型仍无法关联到具体文档。
> 这是 W8 的范围，此处不假装支持。

### 三个会话操作

| 操作 | 行为 |
| --- | --- |
| 🧹 清空对话 | 清 `messages` + `timings`，保留索引 |
| 🗑 重建索引 | 清空向量库 + 清索引记录 + 清对话 |
| 📚 当前知识库 | 侧栏显示总块数 + 每个文件的页数/块数/状态 |

**「重建索引」必须清向量库**：改了 embedder 之后不清理，
新旧向量会混在一个库里。维度不同会直接报错（还好），
维度相同时更糟 —— **静默返回无法解释的结果**。

### 关于 GIF

任务要求"用 ScreenToGif 录 30 秒"。**我没有录**，理由是诚实的：
本机网关没有凭据，录出来的会是"上传成功 → 索引成功 → 提问 → **502 错误**"。

3. 录"上传 → 索引 → 提问 → 逐字出字 → 点开参考来源 → 截图耗时面板"六步

界面本身已经能跑（`http://localhost:8501`，实测 200），
所有状态机都有测试覆盖 —— 缺的只是"有凭据的那一次真跑"。

## 8. 架构：为什么 UI 只有"展示"

Streamlit 每次交互都**重跑整个脚本**。把业务逻辑写在 `app.py` 里会立刻变成灾难：
session_state 塞满中间变量、缓存键写错、重跑时索引被重复建。

所以分层是硬的：

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 编排 | `app/rag/query.py` · `indexing.py` | 检索、计时、调模型、解析引用 |
| 展示 | **`app/ui/streamlit_app.py`** | 排版、进度条、展开原文、四类错误提示 |
| 状态 | `st.session_state` | 对话历史、已索引文档、耗时记录 |

**UI 不 import 任何 rag 内部实现**（不碰 splitter / embedder 实现细节），
只用四个装配点：`get_embedder` / `get_store` / `Indexer` / `QAEngine`。

这样带来的直接好处：**21 条编排测试全部离线可跑，不需要 Streamlit**。
