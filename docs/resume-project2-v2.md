## 工业级质检 Agent（个人项目，11 周，Python / LangGraph / FastAPI）

**一句话**：在已有 RAG 质检系统上构建有状态 Agent（四工具 + 检查点 + 人机中断），
自建 20 任务评测集做量化评测，把"成功率"从不稳定的 70–100% 区间推到
**结构化归因 + 可复现测量**，并用两批实测证明确实有效的改进。

### Agent 可靠性（W9–W11，全部实测）

- **有状态图 Agent**：LangGraph 图版实现工具调用 + Sqlite 检查点 + 中断恢复；
  崩溃恢复实测精确从崩溃节点续跑（`learn/llm/w10_checkpointer.py`）；
  人机中断（interrupt）三条路径 —— approve / reject / revise ——
  皆有副作用恰好一次的断言（4 条测试）
- **五类错误分类 + 重试/降级矩阵**：参数错 / 权限错 / 超时 / 空结果 / 内部异常；
  每类定"可恢复吗、谁执行恢复、几次、用尽后"。
  关键设计：`retryable` 由**代码**判定而非模型猜——
  模型对"刚发生的超时"没有元信息；不可重试的错误一律不给退避秒数
  （自相矛盾的信号会让模型照着后者做）
- **20 任务评测集**（10 个 W10 回归 + 10 个新增，判据 01-01 冻结）：
  五类难度含 2 个需人工确认、4 个不可完成（信息缺失/能力外/需权限/需实时）。
  **任务成功率 90–100%（20 任务，含可靠性机制，降级计入失败）**；
  **编造型失败 0 例**（6 个不可完成任务 × 5 轮，口径 = 答案数值在成功工具
  返回里找不到出处即算编造，轨迹 `evidence_numbers` 可查）；
  **降级率 ~10%**（当前版本 20 任务）
- **三道防跑偏**（默认全关，可独立开关）：任务分解校验（执行前）、
  中间结果自检（纯规则、零 token）、语义等价判重（纯字符串、零 token）。
  成本实测：只有分解真的花钱（+50% token），另两道 0
- **预算与早停**：三道上限（token / 步数 / 墙钟）+ 优雅退出
  （已完成部分 + 原因 + 按类型给的不同建议）。
  **预算-成功率曲线**（6 任务 × 3 档）：5k=50%、**10k=83%**、15k=83%，
  即 **10k 是性价比拐点**——15k 多花 9.3% token 却没多赢任何任务
- **关键任务稳定性**：6 个高风险任务各跑 3 次，记录通过数与 token 区间；
  明确区分"这 3 次都过了"与"稳定 100%"（3/3 的 95% 置信下界约 0.37）
- **失败按四类归因**（描述不清 / 规划错 / 参数错 / 上下文问题），
  并区分「可修」与「需多轮记忆 / 外部系统 / 多模态 / 实时接入」的架构限制

### 改进实测（诚实版）

| 改动 | 层 | 收益 | 成本 |
| --- | --- | --- | --- |
| 报告工具描述要求回传文件路径 | 工具描述 | +1 任务（T7）| 0 |
| 缺失指标时不列其他指标数值 | prompt | +1 任务（T10）| +586 token/任务（+10.4%）|

**净变化：成本 +10.4%（5662 → 6248 token/任务），成功率 +2 个任务。**

必须一起说的是：**5 轮成功率区间是 70%–100%**。
最好的一轮（r2，20/20）是一次抽样；T7 跨 5 轮只过 1 次，
因为它取决于模型是否"顺手"多发一次通知——**那是任务定义模糊，不是能力不足**。
12 个任务稳定通过、**0 个稳定失败**、8 个波动。

### 可靠性机制失败模式（这是最有信息量的部分）

三次改动各自引入了一次回归，都源于同一个错误：**把某个环节的失败
当成整个任务的失败**。

1. 确认约束误用于全局 → T7/T8 被"先问"卡住（判据要求真的生成）；
2. 10k 全局预算 → T7 在收尾步触顶（报告已成功却没预算给答案）；
3. 降级语义过宽 → 一个已完成的报告任务因 notify 失败被连坐成 degraded。

第 3 条的修法：判断"只是收尾类工具失败（notify）+ 此前的必需动作都成功"
就保留 completed，把收尾失败写进答案供审计。

**教训**：可靠性机制的风险不在于它不生效，而在于它**生效得太广**。
每加一个机制都要问"它会不会把已经做对的事判错"。

### 诚实边界（主动交代）

- **20 任务是小样本**，4 类任务偏工业质检场景；跨域未验证
- **不是"已上线"** —— 服务化与并发（`query_progress` 接口已就绪，
  但 interrupt 尚未接进 app 的服务路径）是 W12 的目标
- **判据有已知缺陷**：不可完成任务的判据用"不许出现库内数值"防编造，
  无法区分"编造"与"引用查询结果做对比"（T10/N11 都因此误伤过）。
  行为侧已缓解，判据因冻结未改
- **降级率与成本是在特定预算档上测的**（10k/120s），换档会变
- **未验证多用户并发**；未做真实外部系统集成（ERP 类任务只能如实拒绝）
- 稳定性只跑了 3 次，不足以给出置信区间
