## 质检知识库 Agent（个人项目，Python / LangGraph / FastAPI）

**一句话**：在一个带引用溯源的 RAG 问答系统上，逐层加上「有状态 Agent、可靠性机制、
服务化、可观测」，每一层都用自建评测集量化收益与代价，并记录**哪些层被数据判定为不划算而关闭**。

### 一、RAG 全链路与评测体系（W4–W7）

- 链路：文档解析（页码贯穿）→ 切分 → 向量召回 → 精排 → 压缩 → 引用式生成
- **自建 120 条评测集**（80 事实 / 20 多跳 / 20 拒答），与 40 条调参集**零重叠**，
  出题期设泄题防线（拦 7 条）与 grep 门（拦 3 条假拒答）（#15 #16 #17）
- **Recall@5 56.0%**（100 可答题，bge FP16 · chunk500/overlap50 · k=5 · 阈值 0.575，冻结口径）（#1）
  - 事实子集 66.2%，多跳子集 15.0%，**差 51pp 且置信区间无重叠**——这是全项目最稳健的结论（#2 #3）
- **端到端答案得分 0.655**（judge 三档；judge 与人工一致率 **30/30**，协议为人工先判后对，
  rubric 经 sha256 冻结）（#4 #5）
- **拒答必须三分类报，禁单报一个百分比**：正确拒 6 / 误拒 12 / 幻觉 14（20 条拒答题）（#6 #7 #8）
- **单阈值无解**：可答题 top1 最低分与拒答题 top1 最高分**区间完全重叠（0.513–0.629）**，
  即分数特征不具备可分性——这是数据逼出的结论，不是调参没调好（#9）
- **失败归因四类**：检索未召回 53% / 多跳 22% / 生成 16% / 术语 9%
  （120 条 judge 理由审计后修正，初判 66% 被审计救回）（#10–#13）
- **分层单调下降 67% → 38% → 15%**：答对率随检索层加深而单调下降，
  是「检索质量决定生成上限」的量化证据（#14）

### 二、消融实验：把"加上就好"的直觉逐个证伪（W6）

严格累加四配置（40 可答 + 10 拒答，1165 块语料，k=5）（#21–#26）：

| 配置 | Recall@5 | 相对基线 | p50 延迟 | 结论 |
| --- | ---: | ---: | ---: | --- |
| 朴素向量 | 40.0% | — | 119 ms | 基线 |
| + 混合检索（RRF） | 35.0% | **−5.0pp** | — | **负结果，如实报**：两路候选独有占比 86%，RRF 偏好"共识"反而排掉正确块 |
| + Cross-Encoder 精排 | 57.5% | **+22.5pp** | 17,514 ms | 增益最大但**延迟 ×~140**、模型 2.27GB；p=0.0703 **未达显著**，只声明"方向明确" |
| + 上下文压缩 | 57.5% | ±0.0pp | — | 省 token **42.4%**（685→547），检索指标按设计不变 |

**最终四层全部默认关闭**，理由写进 README——收益最高的精排是量级延迟代价，
在单机 CPU 形态下不成立。**能说清"哪一层不用、为什么不用"，比全开更难。**

### 三、Agent 层：把"有时能过"变成"可测量"（W9–W11）

- **手写 ReAct 循环 → LangGraph 状态机重构**，同判据对照，10 任务 9/10 持平（#31）；
  检查点持久化 + 中断恢复（崩溃后精确从崩溃节点续跑）
- **20 任务评测集**（10 回归 + 10 新增，判据 01-01 冻结）：
  五类难度含 2 个需人工确认、4 个不可完成（信息缺失 / 能力外 / 需权限 / 需实时）（#29）
- **成功率 70%–100% 区间**（20 任务 × **5 轮**；含可靠性机制；**降级计入失败**）
  - 拆到单任务：**12 个稳过 / 0 个稳败 / 8 个波动**——「最好一轮 100%」是抽样，不作结论（#30）
- **编造型失败 0 例**（6 个不可完成任务 × 5 轮；口径 = 答案数值在成功工具返回里找不到出处；
  轨迹含 `evidence_numbers` 埋点可查）。**同时声明判据缺陷**：曾把"有出处的引用"误判为编造，已区分（#32）
- **降级率 ~10%**（2/20，10k 预算档；换档会变）（#33）
- **预算-成功率曲线**（6 任务 × 3 档）：5k=50% / **10k=83%** / 15k=83%
  → **10k 是拐点**，15k 多花 9.3% token 却零收益（#35）
- **早停省回 0**（零触发）——机制无效的诚实结论，保留在材料里（#36）
- 两条增量约束换 2 个任务：**成本 +586 token/任务（+10.4%）**（5662→6248）（#34）

### 四、可靠性：三个改动的三次回归（W11）

三次改动各自引入一次回归，根因同一个：**把某个环节的失败当成整个任务的失败**。

1. 确认约束误用于全局 → 两个任务被"先问"卡住
2. 10k 全局预算 → 报告已生成却没预算写最终答案
3. 降级语义过宽 → 一个已完成的报告因通知失败被连坐成 degraded

> **教训**：可靠性机制的风险不在它不生效，而在它**生效得太广**。
> 每加一个机制都要问：它会不会把已经做对的事判错。

### 五、服务化与并发（W12）

- 双容器 compose · API Key 鉴权 · **双层令牌桶限流**（全局 + 单 key）· 三层缓存
  （embedding / 检索 / 答案，均带**配置指纹**，换配置自动失效）· nginx 反代（SSE 不缓冲）（#37–#42）
- **压测三档（10/20/50 并发，hashing 热缓存口径）**（#37–#40）：

| 并发 | QPS | 检索 P50 | 错误率 / 5xx |
| ---: | ---: | ---: | ---: |
| 10 | 13.4 | 3–4 ms | 0% / 0 |
| 20 | 27.3 | 3–4 ms | 0% / 0 |
| 50 | 67.8 | 3–4 ms | 0% / 0 |

- **拐点不是过载，是限流配额**：50 并发档 **429 占 55.7%**——背压按设计生效，
  不是系统崩溃。**「错误率 0%」必须同时报这个数**，否则会被读成"系统扛得住"（#39 #40）
- `extract` P50 2.4–2.7s，瓶颈在**上游 LLM 网关**而非本地服务（#41）
- **口径限定**：以上全部是 **hashing 热缓存**形态；bge 形态未压测，**不写、不外推**（#37 处理列）

### 六、可观测与 MCP（W13）

- **trace 三级模型**（trace / span / generation），**12 span/请求**；
  三级而非两级的理由：span 描述"系统做了什么"，generation 描述"模型做了什么"——
  合成一级就无法回答"这次请求贵在检索还是贵在生成"
- **成本对账**：观测聚合侧 vs 直录账本侧逐 token、逐成本比对，**误差阈值 5%**。
  对账抓出两个真 bug——① extract 的成本**整体漏埋**（不对账则低估 45%）
  ② 成本公式分叉。**这是"对账不是为了好看，是为了抓漏"的实证**
- **4 条告警规则，阈值全部有实测出处**（不套行业默认值）：
  例如"缓存命中率 < 70% 持续 5min"——命中率塌了意味着指纹/key 逻辑变了
- **MCP 文件系统 Server**：自写 Server + 逐帧 client 验证协议交互；
  **五道闸路径安全**（`resolve()` 后校验、拒绝对路径、符号链接、扩展名与大小白名单），
  **5 条攻击测试全部被拒**（16 条测试覆盖）（#—, `docs/mcp-server.md` §八）
- 与 Function Calling 的分工：FC 决定"这次调不调、调哪个"，MCP 决定"能力怎么被任何宿主发现与执行"——
  两者正交、可叠加
