# 成本模型：规则版 vs LLM 版，以及重试的真实代价

> 由 `scripts/cost_model.py` 生成，数据来自**实测 token 数**
> （`scripts/token_result.json`，2026-10-26 测得）。
> 单价取示例锚点，**不是任何具体供应商的报价** —— 换供应商只需改两个参数。

```powershell
uv run python -X utf8 scripts/cost_model.py --price-in 2 --price-out 8
```

---

## 为什么"重试"必须单独算进成本

新手算 LLM 成本只看「单次价格 × 次数」。真实账本是这样的：

| 概念 | 是什么 | 谁决定 |
| --- | --- | --- |
| **尝试次数** | 一次用户请求里实际发了几个 HTTP 请求 | 重试策略 + 失败率 |
| **逻辑调用** | 用户视角「我请求了一次」 | 用户 |
| **token 消耗** | 每次尝试都**独立计费**，失败的也付钱 | 输入/输出长度 |

把三个混在一起，就会得出「重试只是多花一点时间」的错觉。
**实际上失败的尝试同样收费**，而且校验回灌是**一次全新的完整调用**（输入还要加上错误输出与纠正提示）。

本项目有**两层重试**，它们独立叠加：

1. **HTTP 重试**（`app/core/llm/retry.py`）：429/5xx/超时 → 指数退避 + 抖动
2. **语义重试**（`app/services/llm_extractor.py`）：Pydantic 校验失败 → 回灌错误让模型改，最多 2 轮

## 单次成本表

> 输入 **2.0** 元 / 百万 token，输出 **8.0** 元 / 百万 token
> 校验回灌每轮额外按 160 输入 token 计（错误输出 + 纠正提示的典型长度）

| 场景 | 尝试 | 回灌 | 总 token | 单次成本 | 每 1,000 次 |
| --- | ---: | ---: | ---: | ---: | ---: |
| **规则版**（兜底，纯 CPU） | 0 | 0 | 0 | **0** | **0** |
| 短文本 · 一次成功 | 1 | 0 | 198 | 0.000558 元 | 0.56 元 |
| 短文本 · 1 次回灌后成功 | 1 | 1 | 556 | 0.001436 元 | 1.44 元 |
| 短文本 · 2 次回灌后成功 | 1 | 2 | 914 | 0.002314 元 | 2.31 元 |
| 短文本 · 回灌用尽→降级 | 1 | 3 | 1,272 | 0.003192 元 | 3.19 元 |
| 标准合同 · 一次成功 | 1 | 0 | 316 | 0.001166 元 | 1.17 元 |
| 标准合同 · 1 次回灌后成功 | 1 | 1 | 792 | 0.002652 元 | 2.65 元 |
| 标准合同 · 2 次回灌后成功 | 1 | 2 | 1,268 | 0.004138 元 | 4.14 元 |
| 标准合同 · 回灌用尽→降级 | 1 | 3 | 1,744 | 0.005624 元 | 5.62 元 |
| 长合同 · 一次成功 | 1 | 0 | 1,996 | 0.004460 元 | 4.46 元 |
| 长合同 · 1 次回灌后成功 | 1 | 1 | 4,152 | 0.009240 元 | 9.24 元 |
| 长合同 · 2 次回灌后成功 | 1 | 2 | 6,308 | 0.014020 元 | 14.02 元 |
| 长合同 · 回灌用尽→降级 | 1 | 3 | 8,464 | 0.018800 元 | 18.80 元 |

### 三条从数字里读出来的结论

**① 回灌重试不是「多一点时间」，是「多几倍钱」。**
标准合同一次成功 0.001166 元，2 轮回灌后 0.004138 元 —— **3.5 倍**。
所以「提高首次成功率」比「加大重试」划算得多。这也是为什么实现里做了
**标量归一**（数字→字符串在本地转，不浪费一轮），以及 `response_format` 强约束。

**② 长文档的回灌代价最大（4.2 倍），因为输入本来就贵。**
一次长合同 1,996 token 里 96% 是输入；回灌一轮要把这 1,996 再加一遍。
→ 长文档更应该**先用规则版兜底**（规则版在结构化标签上表现不错），
LLM 只处理规则抽不到的部分。

**③ 规则版成本是 0，但质量不是免费的。**
降级省下全部 API 费用，代价是复杂字段准确率下降。
所以 `degraded: true` 必须暴露给调用方 —— **让省钱的代价可见**，
而不是悄悄给个低质量结果。

## 优化手段敏感性

基线：标准合同 · 一次成功（每 10,000 次 = 11.66 元）

| 手段 | 单次成本 | 每 10,000 次 | 节省 | 代价 / 备注 |
| --- | ---: | ---: | ---: | --- |
| 基线 | 0.001166 元 | 11.66 元 | — | 当前实测 |
| **prompt 精简 30%** | 0.001028 元 | 10.28 元 | **11.8%** | 只减输入；输入仅占总价 39%，所以 30% 精简只带来 11.8% 节省 |
| **结果缓存命中 50%** | 0.000583 元 | 5.83 元 | **50.0%** | 收益线性，**无质量风险** |
| **小模型分流 60%** | 0.000641 元 | 6.41 元 | **45.0%** | **有质量风险**：小模型在复杂字段上准确率会掉 |
| 缓存 50% + 精简 30% | 0.000514 元 | 5.14 元 | **55.9%** | 两者独立，收益近似相乘 |

### 为什么「prompt 精简 30%」只省 11.8%

因为**成本结构决定优化上限**。标准合同的输入占 39%、输出占 61%：
精简输入 30% → 只动到 39% 的那部分 → `30% × 39% ≈ 11.8%`。

这和上周（`learn/llm/03_cost_and_reliability.md`）的结论一致：
**输出单价通常是输入的 3–5 倍，所以「少让模型说话」比「少喂正文」更省。**
想通过精简 prompt 大幅省钱，得先让输出变短（比如限制摘要字数）。

### 为什么「缓存」是唯一纯收益的手段

它省 50% 且**没有质量代价** —— 因为返回的是同一个输入的同一份结果。

但有个前提必须说清：**"同一输入"必须真的可复现**。
前面实测过 `temperature=0` 也不保证每次一样（`learn/llm/01_params.md §5`），
所以缓存键要包含**输入文本内容**，命中就复用、不重新生成 ——
而不是"让模型再跑一次，期望结果相同"。

### 为什么「小模型分流」看着最香，实际要谨慎

45% 的节省接近缓存，但代价是**质量不确定**：
- 简单字段（合同编号、日期）小模型够用
- 复杂字段（甲方全称、条款归纳）小模型容易漏或编

可行的做法是**按字段分流**而不是按请求分流：
简单的 3 个字段走小模型，复杂的 1 个字段走大模型。
这样收益会低于 45%，但质量可控 —— **可解释的降级优于不可控的省钱**。

## 一个必须提醒的估算陷阱

如果把「规则版 vs LLM 版」直接比成本，会得出"规则版完胜"的结论（0 vs 0.001166）。
但这是**错的比较**，因为两者产出的东西不同：

| | 规则版 | LLM 版 |
| --- | --- | --- |
| 能抽的字段 | **只在规则表里**（合同编号/日期/金额/甲方 + 标签兜底） | 任意字段 |
| 复杂语义 | 抽不到（返回 null） | 能抽（但可能编造，有回指校验拦） |
| 换字段名 | 需要改代码 | 不用 |

**正确的比较是「同样效果下的成本」**：对规则表覆盖的字段，规则版免费且更快；
对表外字段，规则版给 null，LLM 版才有价值。
所以本项目的策略是**规则版兜底 + LLM 主力 + 降级标记**，
而不是二选一。

## 复现

```powershell
# 换单价（你的供应商报价）
uv run python -X utf8 scripts/cost_model.py --price-in 1 --price-out 4

# 重测 token 数（换模型/改 prompt 后必须做）
uv run python -X utf8 scripts/measure_tokens.py
```

> ⚠️ `scripts/cost_model.py` 里的 token 数是**硬编的实测值**。
> 换模型或改 prompt 后，必须重跑 `measure_tokens.py` 更新它 ——
> 用旧 token 数配新模型算出来的成本，看起来精确，实际是错的。
