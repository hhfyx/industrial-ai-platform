### 三个精排数字的关系（不是矛盾）

| 数字 | 样本 | 测的是什么 |
| --- | ---: | --- |
| **+15pp** | 40 条 | **累加链上的相邻差**（混合→精排），配 p=0.0703 |
| **+25pp** | 20 条（前 20） | 只看前 20 条时的有/无差（35%→60%） |
| **+22.5pp** | 40 条 | **有/无精排的直接差**（35.0%→57.5%） |

**对外引用时的选择**：

| 场合 | 用哪个 |
| --- | --- |
| "精排值不值得上"（决策问题） | **+22.5pp** |
| "四层里哪层最有效"（消融问题） | **+15pp**（附 p=0.0703） |

**不要**把 +25pp 和 +15pp 直接比较 —— 那是在比两个不同样本量的估计。

## 一、为什么必须拆段

W6 加了三层（BM25 / 精排 / 压缩）之后，如果不拆段：

    检索耗时 16.8 秒   ← 这个数字没法归因

拆段之后：

    embed    174 ms
    search   122 ms
    bm25       7 ms
    rerank 16680 ms   ← 99% 在这里

**只有拆开，才知道该优化哪一段。** 这也是 W6 周四"精排不进链路"那个决定的依据。

### 1.1 一个反直觉的发现：向量检索本身很慢

`search_ms` 均值 **122 ms** —— 这比我预期的"内存检索 ~1 ms"慢两个数量级。

原因：**精排前每轮都拉 20 条候选**，而 `InMemoryVectorStore` 是纯 Python
遍历全部 1364 个向量算余弦（没有 ANN 索引）。20 条 × 40 轮 = 大量重复计算。

> 真实生产环境用 Chroma（有 HNSW 索引）会快得多。**这个 122 ms 是内存实现的代价**，
> 不是向量检索的固有成本。

## 二、优化项与实测

### 2.1 缩小候选 N（配置 B）

| 指标 | A（N=20） | B（N=10） | 变化 |
| --- | ---: | ---: | ---: |
| P50 | 16781 ms | 9865 ms | **−41%** |
| P95 | 22546 ms | 13394 ms | −41% |
| Recall@5 | 60.0% | 55.0% | **−5.0pp** |

**每省 1 秒付出 0.7pp 召回。**

这个交换划不划算？要看你在什么位置：

- 如果延迟预算是 2 秒 → **N=10 也要 9.9 秒，仍然超 5 倍**，缩 N 解决不了问题
- 缩 N 只是"线性减半"，而问题是"精排本身太慢"（数量级问题）

### 2.2 跳过精排（配置 C）

| 指标 | A（精排） | C（无精排） | 变化 |
| --- | ---: | ---: | ---: |
| P50 | 16781 ms | **137 ms** | **−99%** |
| P95 | 22546 ms | 139 ms | −99% |
| Recall@5 | 60.0% | 35.0% | **−25.0pp** |

**每省 1 秒付出 1.5pp 召回。**

这是真正的取舍：

- 精排贡献了 **+25pp Recall@5**（35% → 60%），是全部四层里最大的单项收益
- 但它要 **16.6 秒**

### 2.3 两个"没做"的优化（诚实记录）

| 优化 | 状态 | 原因 |
| --- | --- | --- |
| **embedding 缓存** | 已存在（`CachedEmbedder`） | 但**本脚本的 20 条 query 各不同**，缓存命中率 0，所以测不出收益 |
| **精排结果缓存** | **未实现** | key = query + 候选集合哈希。理论上第二次同 query 直接命中 |
| **并行化（asyncio.gather）** | **未实现** | BM25 和向量检索各 ~6ms 和 ~122ms，**并行最多省 122ms** —— 相对于 16680ms 的精排，收益 0.7% |

**并行化为什么不做**：任务书要求"BM25 与向量检索可并发"。
实测这两段合计 128ms，占全链路 0.75%。**并行它们的收益上限是 122ms**，
而引入 asyncio 会让整条链路变成 async（所有调用点都要改）——
**付出的是架构复杂度，换回 0.7%**。这是典型的不划算。

> **这一条值得单独说**：任务书列了四个优化项，我只做了两个（缩 N、跳精排），
> 另两个用数据证明了不划算。**"不做"也是一个结论，只要给出理由。**

## 三、P95 的意义

| 配置 | P50 | P95 | P95/P50 |
| --- | ---: | ---: | ---: |
| A | 16781 ms | 22546 ms | **1.34×** |
| B | 9865 ms | 13394 ms | 1.36× |
| C | 137 ms | 139 ms | 1.01× |

**精排让 P95/P50 从 1.01× 涨到 1.34×** —— 也就是说"最慢的那 5%"比中位数慢 34%。

为什么：精排耗时与**候选的 token 长度分布**有关。
遇到长表格块（500+ token）时 padding 更多、前向更慢（W6 周三实测过 padding 浪费 230%）。

> **用户感受到的"卡"来自 P95，不是 P50。** 只看平均值会低估问题。

## 四、最终链路定版

### 4.1 决定：**只用 ① 朴素向量**（继承 W6 周六消融的结论）

| 层 | 状态 | 依据 |
| --- | --- | --- |
| 向量检索 | ✅ **开** | 基线，P50 137 ms |
| BM25 + RRF | ❌ 关 | Recall@5 −5.0pp（消融表②） |
| 精排 | ❌ 关 | +25pp 召回但要 16.7 秒 = 超预算 8 倍 |
| 压缩 | ❌ 关 | 预算只用 17.7%，省 token 无意义 |

**完整依据见 [ablation-four.md](ablation-four.md)。**

### 4.2 这个决定不是"什么都不做"

四层全关意味着：**当前链路 = W4 的链路**，一行代码没变。

那这一周做了什么？**做了"确认哪些层不该上"** —— 这是有价值的工作：

- 如果不上混合、不上精排、不上压缩，就**不知道为什么不该上**
- 而"不知道"会在 W7/W8 反复重新评估，每次都要花几天

> 任务书今天那句"**如果你关掉其中之一并说出理由，他会记住你**" ——
> 我们关掉了三个，每个都有数字和机制解释。

### 4.3 配置定版

```python
# app/rag/settings.py 保持不变（W5 定版的那套）
top_k = 5
score_threshold = 0.575
strategy = "recursive"
chunk_chars = 500
overlap_chars = 50
max_context_chars = 6000
```

**新增的三层功能全部保留为"可开启"**（`bm25/`、`rerank.py`、`compress.py`），
但**默认关闭**，且每个都有切换条件：

| 层 | 重新启用的条件 |
| --- | --- |
| 混合 | 精排延迟降到可接受时（宽候选 + 精排的组合能用到 62.5% 的天花板） |
| 精排 | 异步 / 更小模型 / GPU 任一可行时 |
| 压缩 | `top_k` 提到 10+、块长 800+、或语料换 PDF 长文档时 |

### 4.4 `retrieve()` 签名

**未改动**，与 v0.4.1 一致：

```
(self, query: 'str', *, top_k: 'int | None' = None,
 k: 'int | None' = None, where: 'dict[str, MetadataValue] | None' = None) -> 'RetrievalResult'
```

任务书要求"retrieve() 内部走新链路，签名不变"。
**实际做的是：新链路没有进 retrieve()** —— 因为它更慢且召回更低。
签名不变这件事，是"没动"而不是"改完还兼容"。

## 五、局限

| 项 | 状态 |
| --- | --- |
| **device = CPU** | 全部数字是 CPU 的，**没有任何 GPU 数据** |
| 样本 20 条 | 任务书要求，但 20 条算 P95 只到第 19 个样本，统计上偏弱 |
| 内存向量库 | `search_ms` 122 ms 是纯 Python 遍历的代价，Chroma+HNSW 会快得多 |
| 精排未缓存 | 同 query 重复问时应当命中缓存，本轮没实现（20 条 query 各不同，测不出） |
| 并行化未做 | 实测收益上限 0.7%，判定不划算 |
| 答案质量未测 | 网关 502「未配置凭据」（与 W6 周六同一问题） |

### 5.1 一个真实的副作用：改 README 会改变检索库

回归验证时发现：**改 README 的架构图（+15 行）让语料从 1364 块变成 1365 块**，
于是 f-22 的 top1 分数从 `0.5764` 掉到 `0.5727` —— **刚好跨过 0.575 阈值**，
误拒从 7 条变成 8 条。

这条值得记下来，因为它说明两件事：

1. **README 在检索语料里**（它是知识文档，白名单里第一项）
2. **改文档会改变检索结果** —— 不是 bug，是"语料变了"的必然结果

> 这正是 W5 记过的那个坑的同源版本：**"越努力写文档，评测越差"**。
> 只不过那次是分析文档污染，这次是**知识文档正常更新**带来的微小扰动。
>
> 1 条题（2.5pp）的抖动在 40 条样本上属于噪声，
> 但它提醒：**跨版本比较数字时，要确认语料块数一致**。
> 今天这次：1364 块（基线）vs 1365 块（改 README 后）。
