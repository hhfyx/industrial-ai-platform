# 面试预演：讲一个失败案例（W9 · 底稿）

> 用本周真实轨迹练"讲一个失败案例"。结构固定：**现象 → 排查 → 根因 →
> 修复 → 修复后证据 → 泛化教训**。全部有据可查（文件/行号/轨迹）。

---

## 案例一（主推）：模型说"工具不可用"，工具明明注册了

**现象**（周三描述 A/B 实验）：给循环接入 4 个质检工具后，模型第一步调
`search_knowledge_base` 失败，第二步换成驼峰 `searchKnowledgeBase` 再失败，
第三步放弃并报告"规范库检索工具当前无法调用"。但裸调工具函数全部成功。

**排查**（排除法三步）：
1. 怀疑 observation 包装让模型困惑 → 用 W2 原始回灌对照，同样失败 → 排除
2. 怀疑提示词措辞 → 改写成显式两步指令，仍失败 → 排除
3. 打印循环内回灌的 observation → `{"ok": false, "kind": "unknown_tool",
   "available_tools": ["calculate", "get_weather"]}` —— **根因现形**：
   循环执行层写死了 W2 的注册表，我传了新 schema 但执行函数还是旧的。

**根因**：schema（给模型看的）与 executor（实际执行的）不同源。
模型的"工具不可用"感知是**完全正确的**——在它的世界里那 4 个工具确实不存在。

**修复**：`run_react_loop` 增加 `executor` 参数；
`agent_registry.py` 把 schema 与执行函数绑成同一模块常量，主循环只从这里拿。

**修复后证据**：同一任务 3/3 选中正确工具（`qa_runs_w9/trajectories/`）；
测试锁住"unknown_tool 信封 + available_tools 列表"行为。

**泛化教训**：这是"单一事实来源"原则的执行层变体——我第一次在两份
schema 之间见过漂移（W2），这次在 schema 与注册表之间又见了一次。
**凡是"给模型看的东西"和"实际执行的东西"，必须同源，最好绑在同一个
模块里**。以及：模型的报错信息在排障时是证据不是噪音——它说工具不存在，
就先查"它的世界里工具列表是什么"。

## 案例二（备选）：假"已送达"——幂等拦截把未成功的投递当成已完成

**现象**（周六 T8）：模型尝试通知，收到"已投递过（首次 delivered=None）"
的拦截，于是在最终答案里报告"✅ 已送达"。**实际上首次投递从未成功**
（端点不可达，账本里只有 in_flight 记录）。

**排查**：轨迹里 audit notify 步骤的 observation → 拦截消息里的
`delivered=None` 说明首次没有结果。

**根因**：幂等拦截条件写的是"key 存在即拦"，把"意图已记录"（in_flight）
和"已确认送达"混为一谈。先落记录再执行的设计没错，错在**读取面的语义**。

**修复**：拦截条件改为 `result.delivered == True`；in_flight 放行
复用同 key 重发（接收端按 key 去重兜底，真重发也不会重复）。

**修复后证据**：r2 复跑 T8，模型如实报告"通知服务当前不可达……账本已记录，
恢复后不会重复发送"。三轮幂等测试（账本拦截 / 接收端去重 / 重试同 key）全绿。

**泛化教训**：幂等的本质是"重试不重复产生**效果**"，不是"重试不报错"。
区分**状态**（in_flight / delivered）比记录**事件**重要——账本记的必须是
状态机，不是流水。

## 案例三（快答备用）：重复调用检测被并行批重放绕过

**现象**（周二）：熔断器按"相邻连击"实现，演示场景里模型把一整批并行
调用原样重放（step1 查 4 城 → step2 同样 4 个），每个调用"不相邻"，全部放行。

**根因**：连击计数被批内其他调用稀释。

**修复**：升级为**全局出现次数计数**——同参数第 2 次出现（无论隔多远）
警告不执行，第 3 次熔断。模型随后换参数变体（去掉 unit 字段）想绕开，
但那是新 key，它自己的第 2 次出现照样被警告——**参数变体骗不过全局计数**。

**泛化教训**：重复检测必须在执行侧（"模型只是提议、执行在你这一侧"的
直接推论）；且检测维度要选**语义键**（规范化后的 tool+args），不选原始字符串。
