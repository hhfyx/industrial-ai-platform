# 两段式工程化：召回上限与 N 的权衡（W6 周四）

> 目标：把精排接成"检索 N → 精排 K"的两段式，并**先算出精排的天花板**。
> 代码：`scripts/rerank_pipeline.py`｜命令：`make recall-ceiling` / `make rerank-pipeline`

---

## 〇、一页纸

| 项 | 值 |
| --- | --- |
| **召回上限 Recall@20（纯向量）** | **50.0%** —— 精排的硬天花板 |
| **召回上限 Recall@50（纯向量）** | **62.5%** |
| **召回上限 Recall@20（混合 RRF）** | **62.5%** ← 比纯向量高 12.5pp |
| 精排后 Recall@5（N=20，纯向量） | **42.5%**（16/40 → 17/40） |
| 精排后 Recall@5（N=20，混合） | **47.5%**（19/40） |
| 单 query 延迟（N=20 / N=50） | 约 **10.5 s / 23.9 s**（全 40 条 p50，40/40 超 2 s） |

**一句话结论**：**主要瓶颈在召回层，不在精排层**。
纯向量的天花板只有 50%（N=20），意味着**即使精排完美，也只能做到 50%** ——
剩下 50pp 要靠召回补。而换混合路线后天花板升到 62.5%（+12.5pp），**这才是今天最大的收益来源**。

## 一、必答问题：该修哪一层（本周最重要的判定工具）

> 如果 Recall@5 只有 0.7，但 Recall@50 = 0.95，问题在**精排**（候选里有，排不上来）。
> 如果 Recall@50 只有 0.8，问题在**召回层**（混合/切分/embedding），
> 此时调精排参数是**徒劳**的。

这句话之所以是关键工具，是因为它把"效果不好"这个模糊感受，
拆成了**两个位置明确、修法完全不同**的层。判据只有两步：

### 1.1 判据（写成代码了，不是靠人记）

```python
# ① 天花板够不够高？
if Recall@50 < 0.85:
    → 主要瓶颈在召回层，调精排参数是徒劳的
# ② 天花板与当前 Recall@5 的差距够不够大？
elif Recall@50 - Recall@5 > 0.15:
    → 天花板够高且有空间，问题在精排/排序层
```

**顺序不能反。** 第一版我把判据写成 `if r50 - r5 > 0.15: 问题在精排`，
于是 62.5% 的天花板也被判成"问题在精排" ——
但 62.5% 的含义是"**即使精排完美，也只能到 62.5%**"，那明明是召回的硬上限。

### 1.2 本项目的实际判定

| 路线 | Recall@5 | Recall@50 | 精排空间 | 判定 |
| --- | ---: | ---: | ---: | --- |
| 纯向量 | 40.0% | 62.5% | +22.5pp | 天花板不够高 → **召回层是主瓶颈** |
| 混合 RRF | 40.0% | 77.5% | +37.5pp | 天花板仍不够高，但**空间大得多** |

**所以周四该做的事不是调精排参数，而是把混合路线用好。**

## 二、召回上限：本周最容易漏的一行

### 2.1 为什么它最容易漏

它看起来"只是又一个 recall 数"，但实际上它是**精排的物理上限**：

    gold 不在 N 条候选里 → 精排再怎么排，也不可能把它变出来

W6 周三已经踩过一次：10 条小样本里 **8 条** gold 根本不在候选 top20 内，
精排无从发挥。当时我看到的是"精排前后 Recall@5 没变"，
**如果就此下结论"精排没用"，那是把召回层的问题误判成精排层。**

### 2.2 完整 Recall@N 表

| N | 纯向量 | 混合 RRF | 增益 |
| ---: | ---: | ---: | ---: |
| 5 | 40.0% | 37.5% | −2.5pp |
| 10 | 42.5% | 52.5% | +10.0pp |
| 20 | **50.0%** | **62.5%** | **+12.5pp** |
| 30 | 60.0% | 72.5% | +12.5pp |
| 50 | **62.5%** | **77.5%** | **+15.0pp** |
| 100 | 72.5% | 82.5% | +10.0pp |

**两条曲线都是"越往后越平"**：纯向量 20→50 只涨 12.5pp，50→100 只涨 10pp。
这说明**召回不是"再多取几条就能捞回来"** —— 真没找到的，扩到 100 也还差 27.5pp。

### 2.2.1 ⚠ 一个口径 bug（我自己踩的，已修）

第一版 `_recall_at_n` 为了省事，只 `retrieve(max(ns))` 拉一次 100 条，
然后在结果上截不同长度。**对纯向量这是等价的**（top-k 是稳定前缀），
但**对混合 RRF 不等价** —— RRF 的融合池大小会改变名次本身
（同一块在池 100 和池 20 里，竞争名次倒数的方式不同）。

实测差异：

| 算法 | 混合 Recall@20 |
| --- | ---: |
| 拉 100 截前 20（错） | 67.5% |
| 独立检索 20 条（对） | **62.5%** |

差 2 条。更要紧的是：`_run_sweep` 里是"检索 N 条再精排"（独立检索），
所以**两个数必须同口径**，否则"天花板 → 精排后"的差值毫无意义。

修法：每个 N 独立检索。

### 2.3 混合在 N 上的优势远大于在 Recall@5 上的优势

这是个值得注意的对比：

| 指标 | 纯向量 | 混合 RRF | 差 |
| --- | ---: | ---: | ---: |
| Recall@5（排序质量） | 40.0% | 40.0% | **0** |
| Recall@20（召回广度） | 50.0% | **62.5%** | **+12.5pp** |

W6 周二我测过混合对 Recall@5 没有显著提升（八组 p 全 > 0.05），
当时结论是"基线保持纯向量"。**今天这个数据修正了那个理解**：

> 混合的价值不在"把 final top5 排得更好"，而在**"把正确答案捞进候选集"**。

它是为**精排提供更宽的输入**的，不是直接改善最终排序。这个定位在周二的
那组实验里看不出来 —— 因为那些实验都只看到 top5。

## 三、N → K 权衡（K 固定 5）

> **口径说明**：本节是**纯向量路线**，不受 §2.2.1 那个口径 bug 影响
> （纯向量 top-k 是稳定前缀，"拉 100 截 20" 与 "直接取 20" 等价）。
> 数字来自同一次全量运行。

| N | 天花板 | 精排后 Recall@5 | 提升 | p50 延迟 | 超 2s 条数 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 20 | 50.0% | **42.5%** | — | 10.5 s | 40/40 |
| 30 | 60.0% | 47.5% | +5.0pp | 17.4 s | 40/40 |
| 50 | 62.5% | 47.5% | +5.0pp | 23.9 s | 40/40 |

### 3.1 一个反直觉现象：N 越大，精排后反而越差（相对天花板）

天花板在升（50% → 60% → 62.5%），但精排后只从 42.5% 升到 47.5% 就停住了。
**N=30 与 N=50 的精排结果完全相同（47.5%）**，而天花板差了 2.5pp。

拆开看每一档的进出：

| N | 从 top5 掉出 | 新进 top5 | 净 |
| ---: | ---: | ---: | ---: |
| 20 | 3 | 2 | −1 |
| 30 | 5 | 5 | 0 |
| 50 | 6 | 5 | −1 |

**掉出的条数随 N 增长得比新进的快。** 而掉出的那几条有一个共同特征：

#### 根因：多跳题被"拆散"了

| 题 | 检索名次（两个锚点） | 精排后两个 gold 块的得分 |
| --- | --- | --- |
| m-04 | #7 / #6 | **0.9494** / 0.0280 → 一个第 1、一个第 9 |
| m-09 | #3 / #5 | **0.8227** / 0.2540 → 一个第 5、一个第 9 |
| m-10 | #3 / #5 | **0.7456** / 0.2582 → 一个第 4、一个第 5 |

**Cross-Encoder 是「单文档相关性」打分器** —— 它对每个 (query, doc) 独立打分，
**完全不知道"这道题需要两个块"**。所以它会：

- 把更像"部分答案"的那个块捧到第 1（0.95）
- 把只能答"另一半"的那个块压到第 9（0.03）

而多跳题的判据是**两个锚点都进 top5**，于是整题算未命中 ——
**检索时明明两个都在前 7 名内，精排后反而丢了。**

> 这是一个**结构性冲突**，不是参数没调好：
> 精排为"单块相关性"优化，而多跳题的正确性定义在"块的集合"上。
> 想解决它需要**成组打分**（对候选集合联合打分）或**按题类型分流**
> （多跳题禁用精排、或降低精排权重）—— 那是周四之后的事，今天只记录现象。

#### 按题型拆开：精排对事实型有效，对多跳型无效

| 题型 | n | 检索 top5 | 精排 top5 | 变化 |
| --- | ---: | ---: | ---: | ---: |
| 事实型 | 30 | 13 | **14** | **+1** |
| 多跳型 | 10 | 3 | 3 | 0 |

整体 +1 条，**全部来自事实型**。多跳型持平 —— 因为 m-01（#11 → #3）进了，
而 m-04、m-09 被"拆散"出了，**一进两出正好抵消**。

---

### 3.2 N 的选择依据

1. **效果**：N=20 天花板 50%，N=30 跳到 60%（+10pp），N=50 只到 62.5%（+2.5pp）
   → **30 是天花板的边际收益拐点**
2. **但精排的实际收益在 N=30 就到顶**（47.5%，与 N=50 相同）
   —— 因为 §3.1 的多跳拆散问题，更多候选挤掉的和捞回的差不多
3. **延迟**：N=20 10.5 s、N=30 17.4 s、N=50 23.9 s，**全部 40/40 条都超出 2 秒预算**

**结论：N=20 是"效果/延迟"最划算的一档**（天花板 50% 时精排拿 42.5%，
利用率 85%），而 N=30/50 多花的延迟没换来对应收益。

## 四、精排的边界 case（今天新增的实测）

### 4.1 **长 doc 截断：被截掉的内容完全不参与打分，且是"归零"不是"略低"**

同一句 golden 答案（「正文超长返回 422 INVALID_INPUT」）放在长文档三个位置，
三种策略各打一次分（`max_length=512`）：

| 策略 | 答案在开头 | 答案居中 | 答案在末尾 |
| --- | ---: | ---: | ---: |
| `tail`（保留开头） | **0.9235** | 0.0003 | 0.0003 |
| `head`（保留结尾） | 0.0003 | 0.0003 | **0.6463** |
| `middle`（保留中段） | 0.0003 | **0.7796** | 0.0003 |

**每一行只有自己覆盖的那一段有分，其余两段全部跌到 0.0003** ——
那是 sigmoid 之后的数值噪声，等价于"判为无关"。

**这不是"分数偏低一点"，是"从相关直接掉到无关"。**
一条"答案在块尾"的长块会被压到噪声水平，**被系统性排到后面**。

### 4.2 但当前语料几乎不触发截断

| 指标 | 值 |
| --- | ---: |
| 块数 | 1404 |
| 中位 token | **77** |
| 最长 token | 717 |
| 超过 512 token 的块 | **3 块（0.21%）** |

所以 `max_length=512` 下，三种策略的差异**在实际语料上几乎观察不到**。
真正会踩坑的场景：块长调大、语料换 PDF 长页、或 `max_length` 被调小。

产物里的 `truncated_pairs` 字段就是为了让这个风险**可见** ——
它是 0 时，"三种策略哪个好"这个话题今天不相关。

### 4.3 空 doc / 超短 doc：安全，不崩

| 输入 | logit | score | 判定 |
| --- | ---: | ---: | --- |
| 空串 `""` | −8.342 | 0.000238 | 不安全地低 = 正确（没有内容就是无关） |
| 只有空格 | −8.342 | 0.000238 | 同空串 |
| 单字 `"a"` | −8.527 | 0.000198 | 低 |
| 超短 `"422"` | −4.247 | 0.0141 | 低但**非零**（字面命中了错误码） |
| 正常块 | 2.964 | **0.951** | 高 |
| 2000 字长块 | 0.092 | 0.523 | 截断后仍命中 |

**空输入不抛异常、给低分**，这是对的 —— 空内容确实不该被判相关。
但要注意：**它的分数（0.0002）与"正常但不相关"的块（0.0003）在同一量级**，
所以不能用绝对阈值区分"空块"和"弱相关块"（又一次分数尺度问题）。

### 4.4 批量与单条一致性

**最大差异 3.85e-08** —— 批量结果与单条逐次结果一致到浮点精度。
这证明 `sort_by_length` 的组 batch 优化**不改变任何一对的分数**（见周三的说明）。

### 4.5 修了一个 API 隐患

`Reranker(truncation="tail")` 传字符串时，第一版能构造成功，
直到 `rerank()` 里 `self.truncation.value` 才抛
`AttributeError: 'str' object has no attribute 'value'` ——
**错误发生在离现场很远的地方，报的还是 attribute 而不是"参数类型错了"。**

现在 `__post_init__` 立刻规整成枚举，非法值直接抛并列出可用取值。

## 五、两组路线：纯向量→精排 vs 混合→精排

| 路线 | 天花板（N=20） | 精排后 Recall@5 | 结论 |
| --- | ---: | ---: | --- |
| `pure_vec` | 50.0% | 42.5% | 基线 |
| `hybrid_rrf` | **62.5%** | **47.5%** | 天花板 +12.5pp，精排后 +5.0pp |

### 5.1 精排在这两条路线上的表现

精排能做的只有"在已有候选里重排序"。所以：

- 纯向量路线：候选里只有 50% 有答案 → 精排把 40% 做到 **42.5%**（吃掉天花板的 42%）
- 混合路线：候选里 62.5% 有答案 → 精排把 37.5% 做到 **47.5%**（吃掉天花板的 42%）

**两条路线的"精排利用率"居然完全一样（各吃到天花板的约 42%）**，
所以混合带来的 5pp 提升**几乎全部来自天花板本身，而不是精排更准**。

这进一步印证了 §一 的判定：**收益在召回层**。
把精排接在混合后面，涨的那 5pp 是"多给了 12.5pp 天花板，精排按同样比例兑现"的结果。

> 顺带一个反直觉的点：混合路线的 **Recall@5（37.5%）比纯向量（40%）更低**，
> 但它的**天花板（62.5%）更高**，精排后也更高（47.5% > 42.5%）。
> **只看 Recall@5 会得出"混合更差"的错误结论** —— 这是周二的判断为什么需要今天来修正。

### 5.2 精排逐题的实际移动（全 40 条，N=20）

可精排的 20 条（gold 在 top20 内）里：

| 名次变化 | 条数 |
| --- | ---: |
| 往前挪 | **9** |
| 往后挪 | 2 |
| 没变 | 6 |
| **中位变化** | **−1 位** |

具体的新进/掉出：

- **新进 top5**：f-05（#13 → **#1**）、m-01（#11 → #3）
- **掉出 top5**：m-09（#5 → 未进）

净收益 **+1 条**（16 → 17）。

**这个 +1 不是"精排没用"**：9 条往前挪、2 条往后，方向是对的。
但**top5 只有 5 个位置、其中 16 条题已经命中**，剩下的名额只有 4 个，
却要容纳 60% 的未命中题 —— **能挤进来的天然有限。**

> 这正是"天花板"概念的用途：精排的**相对**改善（9 条挪前）与
> **绝对**收益（+1 条）差得远，因为位置是固定的。
> 想提高绝对收益，只能提高天花板 —— 也就是**修召回**。

## 六、代价与结论

### 6.1 成本

| 项 | 值 |
| --- | ---: |
| N=20 单 query | **10.5 s** |
| N=30 单 query | 17.4 s |
| N=50 单 query | **23.9 s** |
| 满载 40 条（N=20） | 约 7 分钟 |
| 满载 40 条（N=50） | 约 12 分钟 |

**全部 40/40 条都超过 2 秒预算**（不是个别超标，是全都超）。
所以精排不能进在线链路 —— 除非用异步 / 换小模型 / GPU。

### 6.2 周四的结论

1. **主瓶颈在召回层**：纯向量天花板 50%（N=20），完美精排也只能到 50%
2. **混合的收益在天花板，不在排序**：62.5% vs 50%（+12.5pp），
   而 Recall@5 反而更低（37.5% < 40%）。
   **只看 Recall@5 会得出"混合更差"的错误结论**
3. **精排对事实型有效、对多跳型有害**：事实型 13→14（+1），多跳型 3→3（持平）。
   多跳题被"拆散"（两个锚点得分 0.95 / 0.03），一进两出正好抵消
4. **N=20 是效果/延迟最划算的一档**：天花板 50% 时精排拿 42.5%（利用率 85%），
   N=30/50 多花的延迟没换来对应收益（都是 47.5%）
5. **长 doc 截断是"归零"不是"略低"**：答案在被截掉的那一段时，
   分数从 0.92 掉到 0.0003 —— 但当前语料只有 3/1404 块超 512 token，几乎不触发

### 6.3 周五/周六要接的

1. **精排的部署形态**（异步 / 更小模型 / GPU）—— 这决定 N 能取多大
2. **多跳题与精排的冲突**：需要成组打分或按题型分流，
   否则"精排提升事实型、拆散多跳型"会一直互相抵消
3. **混合接进主链**（周二没做，因为当时只看 Recall@5 就判了"无收益"；
   今天的数据说明那个判断不完整 —— 它的价值在候选集广度）
4. **W5 那 15 条的重标**仍未落地（周一推翻标签，到今天还没进归因表）

## 八、`retrieve()` 签名确认

本日改动**没有碰** `app/rag/retrieval.py` 与 `app/rag/pipeline.py`：

```
(self, query: 'str', *, top_k: 'int | None' = None, k: 'int | None' = None,
 where: 'dict[str, MetadataValue] | None' = None) -> 'RetrievalResult'
```

与 v0.4.1 一致。精排是**离线/旁路能力**，尚未接进在线检索链 ——
这是 §6.3 第 1 条要解决的问题，不是"已经接好了"。
