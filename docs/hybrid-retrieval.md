## 〇、一页纸

| 项 | 结果 |
| --- | --- |
| 合并比例 | 平均并集 **35.2 条/题**，交集 **4.8 条**，Jaccard **13.6%** |
| **独有占比** | **86.4%**（仅向量 43.2% + 仅 BM25 43.2%） |

但**融合后的排序没有带来统计上可辨的提升**，最好看的 45.0% 只是 3 赢 1 输。
在这种证据下换基线，等于用噪声决定架构。

## 一、必答问题：归一化为什么必须**按 query 内部**做

### 1.1 错在哪

反例（全库统一 min-max）：把全库所有 query 的分数一起归一化，共用同一个 `min`/`max`。

两类 query 的分数尺度本来就不同：

- 短 query（「TTFT」）的 BM25 分数可能全在 0~5
- 长 query（「多进程部署时本地模型怎么避免每个进程各加载一份」）可能全在 8~15

全局归一化后，**长 query 的分数被系统性压低**（它的 8 分在全局尺度上低于短 query 的 5 分），
于是它在融合里那一侧的 `α` 权重事实上变小了。

后果不是报错，而是：调参时看到"某些题变差"，去怀疑 α，
**真正的原因是归一化把 query 之间的尺度差压成了偏置。**

### 1.2 本仓库怎么保证这一点

不是靠注释，是靠**签名**：

```python
def normalize_within_query(scores: Sequence[float], method: str = "minmax") -> list[float]
```

它接受的是**一个 query 一路的分数列表**，调用的地方传进去的是
`vec_scores`（这个 query 的向量候选分数）与 `bm25_scores`（这个 query 的 BM25 候选分数）。
**函数拿不到全库上下文**，所以"做全库归一化"在接口层面就写不出来。

`tests/test_fusion.py::test_normalize_is_within_one_query` 用两个尺度差 5 倍的 query
证明这件事：按 query 内部归一后两个 query 的 top1 **都是 1.0**；
若按全局归一，短 query 的 top1 会被压到 0.5 以下。

### 1.3 这也是 RRF 更稳的原因

RRF 只读名次：

    rrf(d) = Σ_{路} 1 / (k + rank_路(d))      k = 60

第 1 名在两路都拿 `1/61`，与分数是 0.9 还是 30 **完全无关**。
所以它压根不需要归一化 —— 不存在"归一化做错"这个失效模式。

## 二、最易错：直接 `0.5*cos + 0.5*bm25`

### 2.1 实测两个量纲差多少

| 路 | top1 分数范围 | 均值 |
| --- | --- | --- |
| 向量（余弦） | 0.516 ~ 0.721 | **0.617** |
| BM25 | 6.90 ~ 27.15 | **14.91** |

`0.5×14.91 = 7.46` 对比 `0.5×0.617 = 0.309` —— **BM25 那侧大 24 倍**。

### 2.2 但它没有"完全支配"（这点我一开始说错了）

我原先写的是"向量被彻底淹没"，**实测不是这样**：

- `naive_a0.5` 与纯 BM25 的 top5 **有 20/40 题不同**
- 向量那 0.309 的贡献虽然压不过主排序，但**在 BM25 分数接近的候选之间仍在打破平局**

实测证据：`naive_a0.5` 比纯 BM25 多命中一条 `f-29`，正是因为向量的分在等分候选上起了作用。

**修正后的说法**：不归一化不等于"向量完全没用"，而是
**α 变成假的** —— 你扫 0.3 / 0.5 / 0.7 时，实际权重被 BM25 的量纲钉死在一个极小的区间里，
调 α 只带来微弱抖动。`naive_a0.5` 的 Recall@5 是 40.0%（16/40），
和纯 BM25 的 37.5%（15/40）几乎一样，就是这个结果。

> **教训**：技术结论也要实测。我按"24 倍量纲差必然完全支配"推理，被数据否掉了一半。

## 三、合并比例：混合有没有意义

| 指标 | 值 |
| --- | ---: |
| 平均并集 | **35.2** 条/题 |
| 平均交集（两路都召回） | **4.8** 条/题 |
| 交集占比（Jaccard） | **13.6%** |
| **独有占比** | **86.4%** |
| 其中仅向量 | 43.2% |
| 其中仅 BM25 | 43.2% |

**两路候选几乎不重叠。** 这意味着：融合有信息基础（不是把同一批块换个顺序），
但同时也意味着 **top5 里塞不下两路各想让进的东西** —— 候选并集 35 条，
最终只能取 5 条，必然大量丢弃。

这也解释了为什么融合的 Recall@5 没有明显提升：**信息是有，但 top5 装不下。**

## 四、五组（实为八组）对照

| 实验 | Recall@5 | 命中 | MRR | 相对基线 | top5 来源（both/v/b） |
| --- | ---: | ---: | ---: | ---: | --- |
| `pure_vec`（基线） | **40.0%** | 16 | 0.2367 | — | 0/200/0 |
| `pure_bm25` | 37.5% | 15 | 0.1871 | −2.5pp | 0/0/200 |
| `rrf`(k=60) | 35.0% | 14 | 0.2363 | −5.0pp | 155/29/16 |
| `rrf_closed`(k=10) | 35.0% | 14 | 0.2342 | −5.0pp | 147/32/21 |
| `naive_a0.5`（反例） | 40.0% | 16 | 0.1929 | +0.0pp | 0/0/200 |
| **`weighted_a0.3`** | **45.0%** | **18** | 0.2250 | **+5.0pp** | 102/19/79 |
| `weighted_a0.5` | 40.0% | 16 | 0.2383 | +0.0pp | 109/53/38 |
| `weighted_a0.7` | 40.0% | 16 | **0.2758** | +0.0pp | 102/90/8 |

### 4.1 逐组命中变化（50 条集 1 条 = 2pp，每条都要能指名）

| 组 | 新命中 | 丢失 |
| --- | --- | --- |
| `pure_bm25` | f-09 f-18 f-20 f-27 | f-06 f-12 f-16 f-29 m-09 |
| `rrf` | 无 | f-16 m-09 |
| `rrf_closed` | 无 | f-16 m-09 |
| `naive_a0.5` | f-09 f-18 f-20 f-27 | f-06 f-12 f-16 m-09 |
| `weighted_a0.3` | f-18 f-20 f-27 | m-09 |
| `weighted_a0.5` | f-27 | m-09 |
| `weighted_a0.7` | 与基线完全相同 | |

### 4.2 一个反直觉的观察：RRF 比基线**差**

RRF 在该强的地方（免疫量纲）表现最好，但它的 Recall@5 **比纯向量低 5pp**（2 输 0 赢）。

原因在 `top5 来源` 那列：RRF 的 top5 里 **155/200 个槽位是"两路都召回"的共识块**。
RRF 天然偏好共识（两路都召回的候选拿两份分），于是**只被一路召回的正确答案被挤掉了**
—— `f-16` 和 `m-09` 就是这么丢的，它们都只有一条路能召回。

这与 §三 的 86.4% 独有比例**直接冲突**：在一个"独有信息占 86%"的候选集上，
用偏好共识的融合方式，等于主动丢弃最有价值的那部分。

> **这是本周最有价值的一条机制解释**：不是"RRF 不好"，是
> **RRF 的共识偏好与本项目候选集的独有结构不匹配**。

## 五、显著性与基线定版

### 5.1 没有一组显著

配对 McNemar 精确检验（对比纯向量基线）：

| 对比 | 仅基线 | 仅本组 | p 值 | 判定 |
| --- | ---: | ---: | ---: | :---: |
| pure_bm25 | 5 | 4 | 1.0000 | 不显著 |
| rrf | 2 | 0 | 0.5000 | 不显著 |
| rrf_closed | 2 | 0 | 0.5000 | 不显著 |
| naive_a0.5 | 4 | 4 | 1.0000 | 不显著 |
| **weighted_a0.3** | **1** | **3** | **0.6250** | 不显著 |
| weighted_a0.5 | 1 | 1 | 1.0000 | 不显著 |
| weighted_a0.7 | 0 | 0 | 1.0000 | 不显著 |

Wilson 区间全部重叠：

    pure_vec        16/40 = 40.0%  [26.3%, 55.4%]
    weighted_a0.3   18/40 = 45.0%  [30.7%, 60.2%]
    rrf             14/40 = 35.0%  [22.1%, 50.5%]

**3 赢 1 输 = +2 条 = 5pp，这个数在 40 条样本上完全在噪声范围里。**

### 5.2 本周基线：保持纯向量

规则（跑之前定死，写在 `_pick_baseline` 的 docstring 里）：

1. **先看显著性**：没有组显著优于基线 → 就没有"更好的方案"，基线不该被动摇
2. 有显著优于基线的组时，按 `Recall@5 → MRR → 复杂度`
3. 复杂度 = 配置项个数（`pure_vec` 0 项、`rrf` 1 项、`weighted` 2 项）

**选它的理由**：没有任何融合组显著优于纯向量（p 全 > 0.05）。
保持纯向量意味着**零参数、零额外索引**，而换基线的收益在噪声里。

这不等于"混合没价值"—— 它说明**在这 50 条调参集上，混合的价值无法与噪声区分**。
W7 的 200 条集（不同文档出题、与这 50 条做模糊去重）才是回答这个问题的场合。

## 六、实现要点

| 点 | 做法 | 为什么 |
| --- | --- | --- |
| 候选只取一次 | 五组共用同一份 `candidates=20` 的两路候选 | 否则比较的是"候选数"而不是"融合方式" |
| `FusedHit` 独立类型 | 不复用 `SearchHit`/`BM25Hit` | 三种分数语义混在一个类型里，调用方迟早会乱比 |
| 保留两路名次 | `vec_rank` / `bm25_rank` 都存 | 没有它，"融合后这条是谁顶上来的"查不到 |
| 排序确定性 | 同分按 `(vec_rank, bm25_rank, chunk_id)` | 只按分数排会让重跑结果不稳定 |
| α 边界自检 | α=0 严格等价纯 BM25、α=1 严格等价纯向量 | 见下 |

### 6.1 一个被测出来的边界 bug

`α=0` 时向量的权重为 0，但它的候选归一化后仍可能是 1.0 ——
乘 0 得 0，与 BM25 侧归一化得 0 的候选**同分**，再被名次兜底一排序，
纯 BM25 的排名就被向量候选插队了。

`test_alpha_extremes_reproduce_pure_paths` 抓到了这个（`['b1','v1'] != ['b1','b2']`）。

修法：**权重为 0 的那一路，它的独有候选整个剔掉**。
这不只是数值巧合 —— 权重 0 意味着"这条路不参与决策"，它的独有候选就不该出现在结果里。

## 七、代价

| 指标 | 值 |
| --- | ---: |
| 语料 / 块数 | 1288 段 / 1363 块 |
| 两路各取 20 条候选 / 50 题 | **17~20 s**（其中向量 embed 是主要成本） |
| BM25 索引 | 1363 块 / 40130 token / 380.2 KB |
| 融合本身 | < 1 ms（纯 Python 字典操作） |

**融合的计算成本可以忽略，真正的成本是"两路都要跑"** ——
向量 embed 一遍 + BM25 一遍，比单跑向量多一次检索。
这是它复杂度上的主要代价，也是 §5.2 选纯向量的理由之一。
