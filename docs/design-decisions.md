# 设计决策记录：RAG 骨架

> 本文件记录**已做出的选择**，以及每个选择的代价。共 **6 条决策**（0~5 是主干，6 是被测试逼出来的一条）。
> 一条决策如果只写"为什么选它"，它就不是决策记录，是宣传。
> 所以每节都有一栏 **「代价是什么」** —— 那一栏比选它的理由更重要，
> 因为它决定了将来什么时候该推翻这个决定。
>
> 配套：[rag-architecture.md](rag-architecture.md)（三段全景）·
> 数字可复跑：`uv run python -X utf8 scripts/rag_cost_compare.py --json scripts/rag_cost_compare.json`

## 0. 必答题：长上下文能替代 RAG 吗？

**不能。三个理由，前两个可量化，第三个是结构性的。**

先给量级。文档按真实 A4 密度算（每页 1200 字，中文 0.676 tok/字 ——
密度来自 `scripts/token_result.json` 的实测）：

| 规模 | 全书字符 | 全书 token | 塞满 128k 窗口？ | 塞满 1M 窗口？ |
| --- | ---: | ---: | :---: | :---: |
| 50 页 | 6.0 万 | **88,758** | ✓（占 69%） | ✓ |
| 500 页 | 60 万 | **887,574** | ✗ | ✓（占 89%） |
| 5000 页 | 600 万 | **8,875,739** | ✗ | ✗ |

### 理由一：成本随长度**线性**涨，而 RAG 是**常数**

同一次提问，同样一份 50 页文档：

| | 输入 token | 单次成本（2 元/M 输入） | 每 1000 次 |
| --- | ---: | ---: | ---: |
| 全书塞入 | 88,758 | 0.179116 元 | 179.12 元 |
| RAG（取 4 块 ≈ 6000 字） | 8,876 | 0.019352 元 | 19.35 元 |
| **差** | **10.0x** | **9.26x** | **159.76 元** |

关键不在"10 倍"，在**这个倍数与提问次数相乘、且不随文档量饱和**：

```
全书塞入：输入 token ∝ 文档长度 × 提问次数        ← 两个方向都线性
RAG    ：输入 token = min(上下文预算, 文档长度)    ← 在上下文预算处饱和
```

所以 5000 页、每天 1 万次提问时，全书塞入这一项就是
`8.876M token × 10000 / 1e6 × 2 元 ≈ 177,515 元/天` —— 这还没算它根本塞不进窗口。

> **诚实边界**：仓库里的 `sample50.pdf` 每页只有 108 字（合成样本，为了让 review 可读），
> 用它算出来的倍数是 **1.0x**。这个"看不出差别"的结果我留在
> `scripts/rag_cost_compare.json` 的 `scenario_fixture` 里，没有删 ——
> 删了的话，上面那张 10x 的表就成了挑选过的证据。
> 结论的正确性依赖"真实文档每页 1200 字"这个假设，它写在脚本常量里、可改、可复算。

### 理由二：lost in the middle —— 塞得越满，中间越容易被跳过

这是**质量**问题，不是成本问题。已被反复验证的现象：把目标信息放在长上下文的
**中间**时，模型的召回显著低于放在开头或结尾（U 形曲线）。

它对本项目的意义：50 页文档塞满 128k 窗口的 69%，意味着**中间那一半内容
处在最容易被忽略的位置**；而 RAG 只放 4 块、占窗口 3%，每一块都在"高注意力区"。

量化代理指标（`scripts/rag_cost_compare.py::attention_budget`，**刻意简化，
不是注意力机制的真实复杂度**）：

| | 占窗口 | 相对 RAG 典型占用（3%）的稀释 |
| --- | ---: | ---: |
| RAG 取 4 块 | 3% | 1.0x（基线） |
| 50 页全书 | 69.3% | **23.1x** |
| 500 页全书 | 100%（已溢出） | 33.3x |

> 这个倍数只能说明"中间部分被读到的机会差一个量级"，不能当成精确的召回率下降值。
> 真实的召回退化要自己测 —— 那是 `docs/api-spec.md` 意义上的**未验证项**。

### 理由三：无法更新与溯源 —— 结构性，不可用成本换

前两条能用钱和更长窗口缓解，第三条不能。

| | 全书塞入 | RAG |
| --- | --- | --- |
| **文档改了一页** | 每次提问都要重新塞入**新版本全文**；如果做缓存，缓存失效的代价是整份文档 | 只重算那一页的块（`Chunk.id` 内容派生，未变的块 id 不变、不用重算） |
| **要加第 501 页** | 下一次提问的 prompt 变长（成本立即上涨） | 只索引新增块，已有向量不动 |
| **"这句是哪来的"** | 模型只能说"文档里说的"，**说不到页码**。让它自己报页码，它会报错，而且很自信 | 引用是我们自己掌握的映射：`[n] → Chunk(source, page)`，可核对 |
| **权限隔离** | 整份塞进去 = 整份都给模型看，无法"只让 A 部门看第三章" | 检索时按 `metadata` 过滤，**过滤发生在送进 prompt 之前** |
| **审计** | 无法回答"这次回答基于哪几段原文" | `Answer.citations` 是结构化记录，可落日志 |

**溯源这一条是硬的**：页码信息只存在于切分那一刻。事后想补，只能全量重新解析 +
重新切分 + 重新向量化 —— 这就是本骨架把 `page` 放进 `Document` 与 `Chunk` 的原因
（见 [rag-architecture.md §3](rag-architecture.md)）。

### 反过来：什么时候"整本塞进去"确实更好

不写这一节，上面的论证就成了单方面宣传。三种情况下确实该直接塞：

1. **语料小于 2 万 token 且几乎不变** —— 比如一份 5 页的产品说明。
   塞进去比建索引简单、少一次检索失败的可能、答案还更完整（不受 top_k 限制）。
2. **问题是"全局性"的** —— "这份合同一共有几个付款节点""全文的主旨是什么"。
   RAG 的 top_k 天然回答不了"全文统计"类问题，因为答案不在任何单一块里。
   本项目对此的答案是 **map-reduce 摘要**（`app/rag/summarize.py`），不是硬套 RAG。
3. **一次性任务** —— 临时分析一份文档，索引的构建成本高于收益。

**所以这个决定不是"RAG 更好"，是"面向知识库问答这个场景，RAG 的代价更小"。**
一旦场景变成"单份短文档、一次性问答"，正确的动作是绕过 RAG 直接塞 ——
这条写在这里，是为了将来有人（包括我自己）被"我们用了 RAG"绑架时能拿出来对照。

## 1. 决策一：为什么用 RAG，而不是微调 / 长上下文硬塞

### 选了什么

**RAG**。文档进索引，提问时检索 TopK 再生成。

### 为什么不微调

微调解决的是"**模型不会某种行为**"（格式、语气、领域表达习惯），
不解决"**模型不知道某条事实**"。本项目要回答的是后者：

| 需求 | 微调 | RAG |
| --- | --- | --- |
| 合同里"违约金千分之三"这条 | 要把这条事实训进权重，**且下次改合同就得重训** | 改一页，重索引那一页 |
| 答案要能点开原文第 7 页核对 | 做不到（权重里没有出处） | 天然（`Citation.page`） |
| 客户 A 的数据不能给客户 B 看 | 做不到（同一套权重） | 检索时按 `metadata` 过滤 |
| 幻觉率 | 微调**可能**降低，但不保证、也不能定位 | 可以做到"无命中就说没有"（`generate_answer` 的空上下文短路） |

微调还有一个本项目付不起的代价：**每次数据变更都要一次训练**。
我们的文档是会变的（合同改版、报告更新），而训练是小时级 + 要 GPU + 无法回滚单条数据。

### 为什么不长上下文硬塞

见第 0 节。一句话：**成本线性、注意力被摊薄、无法溯源与更新**。

### 代价是什么

1. **多了一整条链路要维护**：解析 → 切分 → 向量化 → 入库 → 检索 → 生成。
   六个环节，每个都可能坏，而且**坏了不报错，只是答案变差**（这是最贵的维护成本）。
2. **检索失败时，模型无从补救**。检索没命中，模型要么说"资料中没有"，
   要么编。微调至少在"模型知道这个领域"这点上更稳。
3. **多了一次延迟**：检索本身是毫秒级（本次实测 1 ms / 50 块），
   但 query 向量化是硬成本；接真模型后每次提问多一次 embed 调用。
4. **切分参数是个没有正确答案的超参**。500 字 / 50 重叠是**这一次的取值**，
   不是最优值。改它会让整库 id 失效（`Chunk.id` 含正文），必须重建索引。
5. **RAG 不适合全局性问题**（"全文一共几个付款节点"）。这类问题要用
   map-reduce 摘要，等于维护两套链路。

## 2. 决策二：为什么本地 embedding，而不是 API

### 选了什么

**本地 bge-small-zh-v1.5**（SentenceTransformer，512 维 / 512 token / 92 MB）。
`HashingEmbedder` 保留为离线占位实现（CI 与无模型环境的降级路径）。

> 详细实测见 [embedding.md](embedding.md)。本节只记**决策与代价**。

### 为什么

**① 索引是"批量、可重跑、无上限次数"的操作，API 的计费模型和它不匹配。**

先说不利的那面 —— **单看钱，API embedding 其实很便宜**：

| 规模 | 字符 | token（0.676 tok/字） | API 成本（按 0.5 元/M 假设） |
| --- | ---: | ---: | ---: |
| 50 页 | 6.0 万 | 88,758 | 0.044 元 |
| 5000 页 | 600 万 | 8,875,739 | **4.44 元** |

所以"省钱"**不是**主要理由，把省钱当理由会得出错误结论。真正的理由在下面三条。

**② 离线可测**。这是本项目的一条硬规矩（`tests/conftest.py`：
"拔掉网线，`pytest -q` 必须全绿"）。RAG 的 72 条测试里，
凡涉及向量化的都必须能在没有网络、没有 key 的机器上跑绿。
API embedding 会让这批测试变成"测供应商可用性"。

**实测支撑**：本机网关对 `/embeddings` 返回 `404 not_found`
（`text-embedding-3-small` / `bge-small-zh` / `embedding-3` / `text-embedding-ada-002`
四个模型名全部 404）。**如果当初选了 API，今天的整条 RAG 链路一行都跑不起来。**

**③ 重新索引不该被外部限额决定节奏**。5000 页 ≈ 15,000 块，按批 64 条算是
**235 次 embed 请求**。换成 API 就是 235 次外部调用，要处理限流、重试、部分失败、
以及"重跑到一半配额用完"的中间状态。本地推理只有"跑完"和"没跑完"两种状态。

**④ 数据不出本机**。文档是合同、工单、简历。索引阶段要把**全文**发出去，
这比把检索到的 4 块发给模型严重得多 —— 后者是有选择的，前者是全量。

### 代价是什么（本地模型的四项代价）

**① 占内存：约 400 MB 常驻。**
torch + 权重 + 工作内存。对一个本来 60 MB 的 FastAPI 服务是**6 倍**增长。
多副本时每个 worker 一份 —— 512 MB 的 pod 装不下。

**② 首次加载慢：16 秒（+ `import sentence-transformers` 65 秒）。**
线上第一个真实请求不该承担这 80 秒。所以给了独立预热入口
`BGEEmbedder.warmup()`，在 `on_startup` 里调一次；**测试不调**（不为测试付 17 秒）。

**③ 需要预热（"加载完" ≠ "就绪"）。**
首次 encode 比预热后慢 **7 倍**（77 ms vs 10.5 ms，来自图优化与内存分配）。
只加载不预热，监控里会出现一个查不出原因的 P99 尖峰。

**④ 镜像变大：`.venv` 从 ~136 MB 涨到 1036 MB。**
本项目镜像曾从 242 → 157 MB 瘦身（`docs/weekly/w1.md`），
装 torch 之后**这一项要重做瘦身账**。
现在的取舍是放进主依赖（`uv sync` 就能跑 `bge_prefix_ab.py`），
代价是 CI 拉 900 MB —— 而**没有一个测试需要它**（bge 测试全部 skip）。
一旦镜像大小变成硬约束，正确动作是切成 `[project.optional-dependencies]`
的 `embedding` 组，不是删模型。

**⑤ 质量由自己负责，而且默认更差。**
商用 API 的中文 embedding 通常比能塞进 CPU 的小模型强。
换本地方案就是主动放弃一部分召回率 —— **必须用评测集量化，不能靠"应该差不多"**。

**⑥ 换模型 = 全量重建索引。**
维度变、空间变，库里的旧向量一条都不能用。
反过来说，API 侧供应商悄悄升级模型时你**不会收到通知** ——
这既是缺点（不可控），也是优点（不用自己维护）。

**⑦ 必须批量，所以接口没有 `embed_one`。**
实测吞吐（CPU）：batch=1 **171** / batch=8 473 / batch=32 618 / batch=64 **719** 条/秒。
**batch=64 比 batch=1 快 4.2 倍。** 单条调用会把批处理收益归零，
所以在 `Embedder` 接口上就不提供单条入口。

### 当前这一格的两层实现

| 实现 | 语义能力 | 用途 |
| --- | --- | --- |
| `bge-small-zh` | ✅ 真语义 | **生产**（`EMBEDDER_IMPL=bge-small-zh`） |
| `hashing` | ❌ 只有字面相似 | CI / 无 torch 环境 / 降级 |

默认仍是 `hashing`：CI 要能在没有 torch、没有模型、没有网络的机器上全绿。
**`hashing` 下任何召回率数字都没有参考价值** —— 这条写在
`hashing.py` 的 docstring 里，换成 bge 之后才第一次有了有意义的检索指标。

### 未验证（不能编）

**API 侧的单条延迟与批量吞吐我没有测到** —— 端点 404。
[embedding.md §4](embedding.md) 的对比表里那两格写的是"未能实测"，
不是"大概多少"。编一个数填上去，将来会被引用。

## 3. 决策三：为什么先 ChromaDB，而不是 Milvus

### 选了什么

**先 ChromaDB（嵌入式）**。W4 周四已真正实现并验证（`app/rag/stores/chroma.py`）：
`PersistentClient` + `hnsw:space=cosine` + `where` 过滤，100 条入库、
10 条已知答案人工验收。`InMemoryVectorStore` 作为测试与快速实验的第二实现保留，
两者同一个 `VectorStore` Protocol。

> "决定用 ChromaDB"和"那天就 import chromadb"曾是两件事：骨架阶段只留了
> `get_store` 里的一个分支，理由是"从未被 import 过的适配器不是扩展点，
> 是未被验证的代码"。**周四需求变了（要持久化、要 where 过滤、要 100 条真数据），
> 适配器才被写出来并跑过** —— 周三那条注释当时是对的，
> 它防的正是"先写个空壳假装做完了"。

### 为什么

**① 规模差三个数量级。**

| | 本项目的量级 | Milvus 的设计目标 |
| --- | --- | --- |
| 向量数 | 50 页 → 150 块；5000 页 → **15,000** 块 | 千万～十亿 |
| 内存占用 | 15,000 × 512 维 × 4 B ≈ **30.7 MB** | 集群内存按 GB 起 |
| 部署 | `pip install chromadb`，进程内 | etcd + MinIO + Pulsar/Proxy，**至少 3 个容器** |

为了 30 MB 向量去跑一个 2 GB 起的集群，是**用运维复杂度换一个不存在的性能瓶颈**。

**② 嵌入式 = 少一个故障点。** ChromaDB 是库不是服务：没有"向量库连不上"
这一类故障，没有网络超时，没有健康检查。对一个还没上线的项目，
每少一个外部依赖，`pytest` 就多一分确定性。

**③ 两者的关键能力在当前阶段没有差异。** 我们需要的就是
`upsert` / `search(top_k)` / `count` / `clear` 四件事 —— 四个方法，
两边都有。Milvus 强的那些（分布式、GPU 索引、强一致副本）现在都用不上。

### 代价是什么

1. **单机、单进程写入**。ChromaDB 的持久化后端是 SQLite，写并发很差。
   **多个 worker 同时写会锁**。真上多副本时，这是第一个撞到的墙
   —— 而那正是该换 Milvus 的信号，不是"优化 Chroma"的信号。
2. **迁移是不可避免的，而且成本在"数据"上不在"代码"上**。
   代码侧换库只改 `get_store` 一行（`VectorStore` Protocol 就是为此存在）。
   但**已入库的向量要重算**：不同库的存储格式不通用，
   而且换库时往往会顺带换 embedder（维度变）→ 全量重建。
3. **元数据过滤能力弱**。ChromaDB 的 `where` 只支持有限的比较与逻辑组合，
   嵌套结构不支持 —— 这就是本骨架把 `Chunk.metadata` 收窄到
   `dict[str, str|int|float|bool]` 的原因：**结构上先保证可移植**，
   而不是等迁移时才发现"这个过滤写不了"。
4. **ChromaDB 的 API 在 0.x 阶段变动频繁**。适配层会被上游 version bump 打断，
   所以适配器要写得薄 —— 薄到"上游变了改一个文件"。
5. **放弃的是"提前验证分布式路径"**。如果将来一定要上 Milvus，
   索引侧的批量写、分片、ID 生成策略都要重新设计。
   但这个风险是有意的：**为一个未验证的需求提前设计，成本是确定的，收益是不确定的。**

## 4. 决策四：为什么是 500 字 + 50 重叠

### 选了什么

`ChunkSize(chunk_chars=500, overlap_chars=50)`。
中文分隔符优先级表：`\n\n → \n → 。！？； → ，`（**LangChain 的默认那套是英文的**）。

### 为什么是 500

**① 让"一个条款"整块落在一个 chunk 里。**
一份 A4 中文合同的一个条款段通常 **200–600 字**（`tests/fixtures` 的合成样本
每页 108 字，真实文档约 1200 字/页）。取 500 让大多数条款不被切断 ——
**切断条款是检索质量最直接的下水道**：命中的块只有半个条件句，模型只能猜。

**② 与 bge 的 512 token 上限留出余量。**
500 字 × 0.676 tok/字 ≈ **338 token**，远低于 512 —— 不会被静默截断。

**③ 与 top_k=5 的上下文预算匹配。**
5 × 500 = 2500 字 ≈ 1690 token，加系统提示词与输出仍安全（上限 6000 字）。

### 为什么是 50 重叠

必答题的完整论证在 [rag-query-chain.md §0](rag-query-chain.md)：
**防止关键信息正好被切在边界上断开。**

50 字 ≈ 半句话的量级 —— 足够让下一块看到"若甲方未按期付款"这个条件，
又不至于让两块内容大面积重复。

### 代价是什么

1. **索引冗余 9.4%（实测）**：2128 字 → 2328 字。同样的文字存两次、算两次向量。
2. **chunk 数变多**：与冗余率同比例，embedding 批次变多（300ms → 330ms 量级）。
3. **更容易命中重复内容**：相邻块共享一段文字，分数接近时 top_k 里会同时出现
   A 和 A 的尾巴，**浪费上下文窗口**。100 条语料上没造成明显问题，但这是真实风险。
4. **块平均比预算短（470/500）**：因为只合并**完整的原子片**、装不下就开新块，
   绝不截断句子。这是有意的取舍 —— 换"块尾永远落在句末标点"。

### **这一条是本文档里最不牢靠的**

`500` 与 `50` **都没有数据支撑**。它们来自"一个条款通常多长"这个量级直觉。
`docs/weekly/w4.md` 与 README 的"已知问题 #5"都把它列为待办：
**W5 要做 `overlap ∈ {0, 50, 100}` × `top_k ∈ {3, 5, 8}` 的矩阵，用数据替换直觉。**

> 写在这里的意义不是"我选对了"，是**别人接手时知道这个数字有多软**。

## 5. 决策五：为什么 `page` 必须进 metadata（不能事后补）

### 选了什么

`Document(page, pages)` 与 `Chunk(page, pages)` 从**解析阶段**就带页码；
`to_payload()` 把它压成扁平标量写进向量库元数据（`page` 用 `-1` 编码 `None`）；
检索回来时 `restore_location()` 还原。**切分只继承，不重新推断。**

### 为什么不能事后补

**① 信息在切分那一刻就销毁了。**

```
错误链路：全篇抽成一坨文本 → 按字数切 → 事后把块"对回"页码
                                                   ↑ 只能猜
```

猜法只有两种，两种都必错：

| 猜法 | 为什么错 |
| --- | --- |
| 按"平均每页多少字"折算 | 页密度不均匀：封面 3 字、密集表格 2000 字 |
| 按顺序累加 | 任何一页字符数不整除块长，误差就累积；50 页后能偏出好几页 |

更隐蔽：**页眉页脚被剔除过**，每页实际字符数被人为削掉一截，折算基准整体漂移。

**② 补的成本是全量重建。**
文本一旦切块、向量化、入库，页码只存在于切分那一刻的局部变量里。
上线后想加"点开原文第 N 页"，唯一出路是**全量重新解析 + 重新切分 + 重新向量化**。
按本项目量级：50 页 → 150 块（~1 秒）；5000 页 → 15000 块（~5 分钟 + 一次完整计费）。

**③ 溯源是 RAG 的核心价值之一**（见本文档第 0 节"理由三"）。
没有页码，引用只能说到"某份文档里说的" —— 那和"模型自己编的"在用户眼里没有区别。

### 代价是什么

1. **元数据体积**：每个 chunk 多 3 个字段（`page` / `pages` / `chunk_index`）。
   15000 条 × 约 30 字节 ≈ 450 KB，可忽略。
2. **跨页段落必须记 `pages` 元组，不能只记起始页。**
   只记 `page=6` 是"半个真话"：用户点进 p6 找不到后半截，点进 p7 又找不到前半截 ——
   这正是 demo 现场最容易被点穿的地方。代价是多一个字段、多一点扁平化复杂度。
3. **非分页格式要编码 `None`**（`-1`），编解码只允许各出现一次
   （`to_payload` / `restore_location`），否则两边会各自漂移。
   `tests/test_rag_skeleton.py::test_metadata_roundtrip_through_store_encoding` 守着。
4. **DOCX / Markdown 的 `page` 是 `None`**。这不是遗漏 ——
   Word 的"页"是渲染结果，文件里没存。硬编 `page=1` 会让"第 3 页"变成谎言。

## 6. 决策六（补充）：为什么阈值挂在 embedder 上而不是全局常量

这条是 W4 周五**被测试逼出来**的，值得单列：它推翻了我的第一版设计。

### 最初的选法（错的）

全局 `DEFAULT_MIN_SCORE = 0.35`。结果两条用 `HashingEmbedder` 的端到端测试挂了：
正确命中的答案（分数 **0.247**）被误判成"未找到"并拒答。

**不是测试写错了。** 量化之后（`scripts/embedding_score_probe.py`，4+4 条标注对）：

| embedder | 相关（min~max） | 无关（min~max） | 可分？ |
| --- | --- | --- | :---: |
| bge-small-zh | 0.578~0.676 | 0.253~0.367 | ✅ 空隙 0.367→0.578 |
| hashing(64) | 0.148~0.478 | -0.098~**0.149** | ❌ **重叠** |
| hashing(256) | 0.088~0.484 | 0.000~**0.148** | ❌ **重叠** |

hashing 的"相关最低" ≤ "无关最高" —— **完全重叠**。
任何单一阈值都会同时误杀真答案和放过无关内容。

### 改成什么

`Embedder.recommended_min_score`，每个实现自带：

| embedder | 值 | 理由 |
| --- | ---: | --- |
| `bge-small-zh` | **0.40** | 空隙中点 0.472，**往下取** —— 宁可少拒不误拒 |
| `hashing` | **0.0** | 分布无可分界线，**诚实关掉闸门** |

**为什么往下取不取中点**：误拒真答案（用户看到"知识库没有"而其实有）
比放过一条弱相关（模型还有机会说"材料不足"）更伤。这个不对称是有意的。

### 代价是什么

1. **阈值是"从 8 条样本反推的量级"，不是调好的参数。**
   正确的做法是按 embedder 跑标注集、在 ROC 上取工作点 —— 需要评测集（W5）。
2. **hashing 等于没有拒答闸门**。它会对着完全无关的问题硬答
   （`min_score=0.0` 意味着闸门不生效）。这是"承认这个模型做不到"，
   **不是"设计上的优雅降级"** —— 线上必须显式告知用户当前是字面检索。
3. **阈值不能区分命中与未命中。**
   W4 周四的 10 条验收里，未命中的两条最高分（0.5087 / 0.6514）
   比命中者的最低分（0.466）**还高**。它只负责挡住"库里完全无关"，
   **不负责提高准确率** —— 把它当"质量旋钮"调，越调越糟。
