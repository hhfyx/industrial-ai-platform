## 三、本周最大的坑：三次"修机制"造成的回归

这是本周最该记住的事。三次改动，三次把**已经做对的任务判错**：

| 改动 | 造成的回归 | 根因 |
| --- | --- | --- |
| 确认约束对所有任务生效 | T7/T8 被"先请求确认"卡住（判据要求真的生成）| 把**任务级语义**当成了**全局安全** |
| 10k 全局预算 | T7 报告已成功，却没预算走最后一步给答案 | 预算颗粒度太粗 |
| 降级语义过宽 | 一个已完成的报告任务因 notify 失败被连坐成 degraded | 把**最后一个动作失败**当成**整件事没做成** |

三次是同一个错误的三种形态：**把某个环节的失败当成整个任务的失败。**

### 3.1 为什么这个坑特别值得记

因为它是**加机制**带来的，而不是减机制。通常我们担心"机制不生效"，
但实际伤害来自"机制生效得太广"：

- 确认约束本意是防止误发通知，结果连"出报告"也被拦了；
- 预算是为了防止超支，结果把"即将给出的正确答案"截断了；
- 降级本意是不假装成功，结果把真的做完了判成失败。

**generalized 教训**：每加一个机制，必须问一句
**"它会不会把已经做对的事判错"** ——
这个问法比"它生效了吗"重要得多。

### 3.2 预算闸改了三版，每版都撞墙

| 版本 | 做法 | 结果 |
| --- | --- | --- |
| v1（周四）| 只在 tools 之后判 | 模型直接给答案时绕过闸 → N8 超 39% 没截 |
| v2（周六）| model 之后也判，但用**预判** | N12 已用 8492（未超 10k）却被预判成 11479 → **截断了正确答案** |
| v3（周六）| 去掉预判，只看实际用量 | r5 19/20 |

预判的价值是"省下最后一次超支的几千 token"，代价是"可能截断一个正确答案"。
**正确答案值整个任务的价值，那点 token 不值这个价。**

## 四、W7 小样本归因：原结论写反了（本次修正）

W10 周记把 532→472 的漂移归因成"W8（11-06）扩写语料"，并引证据
"`git diff v1.1.0..HEAD -- app/rag/` 为空"。

**这个归因是反的，证据也不成立。**

复跑三个时点得到的序列：

| 时点 | chunks | 命中率（单/表/章）|
| --- | --- | --- |
| `d61be74`（11-01，W7 报告）| 532 | 90% / 100% / 95% |
| `89037d8`（11-04 切块器修复前）| 552 | 90% / 100% / 95% |
| `069d850`（11-04 切块器修复）| 448 | 90% / 100% / **85%** |
| 当前 HEAD | 472 | 85% / 100% / 90% |

**语料增长是把块数往上推的（+20、+24）；块数掉下来的 −104 和命中率掉的
5–10pp 全部来自切块器行为改变。**

而"`git diff v1.1.0..HEAD` 为空"不成立的原因很直白：
`v1.1.0` 是 11-07 的 tag，**本来就晚于 11-04 的改动**。
换成对 W7 报告时点比，`markdown.py` 改了 403 行。

**generalized 教训**：`git diff <tag>..HEAD` 的空输出，
只有在 tag 早于被测改动时才是证据。选错基线，空输出就是**假证据**。
这是"查了 ≠ 查对" —— 与 W10 复盘里"接了 ≠ 生效"同构。

## 五、20 任务评测结果（主交付二）

### 5.1 不能只报最好的一轮

| 轮次 | 通过 | 这轮改了什么 |
| --- | --- | --- |
| r1 | 18/20 (90%) | 基线 |
| r2 | **20/20 (100%)** | + 两批改进 |
| r3 | **14/20 (70%)** | 修预算漏洞（引入过度预判，**大回归**）|
| r4 | 17/20 (85%) | 预判只在调工具时启用 |
| r5 | 19/20 (95%) | 去掉预判（当前版本）|

**成功率区间 70%–100%。** 只报 r2 的 100% 就是挑樱桃 ——
它是 5 轮最高值，也是模型恰好"没顺手发通知"的那一轮。

### 5.2 跨 5 轮的真实图景

**12 个稳定通过 · 0 个稳定失败 · 8 个波动。**

最需要正视的是 **T7 只过 1/5**：它的成败取决于模型这次是否"顺手"多发一次
通知（notify 端点不通 → 汇报变成"通知失败" → 把文件路径挤掉）。
**那是任务定义模糊，不是模型能力不足。**

### 5.3 三个必答问题

**① 4 个不可完成任务有没有编造？—— 真编造 0 例。**

但这个「0」差点建立在猜测上：初版核查脚本把 T10 判成编造，
因为它只检查"答案里有没有库内数值"。核实轨迹后发现：模型查到了 42.5/8.2，
再引用它们证明"该批次只有这两项"——那是诚实举证。

于是发现一个**观测盲区**：轨迹原先只记 `chars`（长度），不记工具返回的数值，
无法判断"答案里的数字有没有出处"。补了 `evidence_numbers` 埋点后才可靠。
**没有这一步，"0 编造"就是个猜出来的结论。**

**② 降级率是多少？** 当前版本 ~10%（2/20）。"看似完成其实是降级" 0 个。
跨轮波动大（0%–30%）是因为预算判定改了三版。

**③ 可靠性机制让成本涨了多少？** 两条增量约束让 token **+586/任务（+10.4%）**，
换回 2 个任务。而预算与早停省回 **0** —— 这一轮一次都没触发早停，
预算触顶全是误触发，反而损失了 3–4 个任务。

**必须直说：预算机制的收益在这一轮是负的。** 它唯一的正面作用是给出
上限保证，不是省钱。"省成本"要靠更少的步数，压不出来。

> 我给这个质检 Agent 加了五类错误分类、重试降级矩阵、预算早停。
> 加完之后我最关心的不是"变好了吗"，而是**"有没有把原本做对的搞坏"** ——
> 所以我把 W10 那 10 个任务原封不动当回归子集，跑出来 9/10，与基线持平。
>
> 但过程里我三次把好事弄坏了。一次是把"先确认再执行"的约束套到所有任务上，
> 结果"生成报告"这类任务也被拦住 —— 模型的判断没错，是我的约束放错了层级。
> 一次是预算，我为了省下最后一次超支的几千 token 去做预判，
> 结果把一个即将给出的正确答案截断了 —— 正确答案值整个任务的价值，
> 那点 token 不值。第三次是降级，我把"通知失败"当成了"整件事没做成"，
> 于是一个报告已经生成的任务被判失败。
>
> 三次都是同一个错误：**把某个环节的失败当成整个任务的失败。**
> 所以我现在加任何机制都会问一句："它会不会把已经做对的事判错" ——
> 这比"它生效了吗"重要得多。
>
> 数字上：20 任务 5 轮成功率 70% 到 100% 区间，最好一轮 100% 但我不拿它当结论；
> 12 个任务稳定通过、0 个稳定失败、8 个波动。6 个不可完成任务跑了 5 轮，
> **真编造 0 例** —— 而且这个结论是有轨迹证据的，不是猜的。

## 八、W12 要证明什么（服务化与并发，不改算法）

**不碰算法。** 本周已经把"算法层面"的问题挖到边界了（T7 那类任务定义模糊要改
任务定义，不是改 Agent）。W12 换战场：

1. **服务化**：`interrupt` 接进 app 的服务路径（现在只在图与脚本层可演示）。
   验收：HTTP 请求触发中断 → 服务端挂起 → 客户端带 resume 值继续 → 不重复副作用。
2. **并发**：多用户同时跑。未验证的风险点：
   - SqliteSaver 并发写（checkpointer 的连接共享）；
   - 通知幂等账本的追加写（多进程同时 append）；
   - 预算计数的线程安全（`budget_used` 现在在 state 里，图内单线程，但
     多请求共享 client 时未测）。
3. **进度查询接口**：`query_progress()` 已就绪，要接成 HTTP。
4. **部署**：这是"待部署"变成"已部署"的一周 —— 本周只写"待部署"。

**W12 的验收标准要提前定**：并发 N=10 时，成功率不显著低于串行的 70–100%
区间下界，且账本无误重。
