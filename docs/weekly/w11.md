# W11 周记（12/28–01/03）· 可靠性与 20 任务

> 本周只有一件事要证明：**加了可靠性机制之后，成功率是升了还是被预算和早停拖低。**
> 判据 01/01 冻结。任何"成功率变好/变差"的结论，都必须能对上这张表。

## 一、周一 12/28 · 错误分类与可恢复性

五类定义 + 结构定版 + 20 条错误路径 + 分布表。详见 `docs/error-taxonomy.md`。

**核心**：`{ok, error_type, message, hint, retryable, retry_after}` 定版。
`message` 给人、`hint` 给模型、`retryable` 给代码 —— 三种读者三个字段。

必答问题（retryable 为什么不能靠模型判断）：模型手上是文本不是元信息，
同一个"没查到"可能是参数错（改一字就成立）也可能是无权限（重试一万次还是拒绝），
但它只能按语气猜。而工具这侧知道确定答案。

工具条数：4 工具 × 5 类 = 20 条路径，全 mock。

## 二、周二 12/29 · 重试、降级与故障注入

策略矩阵 + 图上 retry/degrade 两节点 + 故障注入三种模式。

**关键不是"重试几次"，是"谁执行"**：参数错必须模型改（代码不知道正确参数，
替它改就是编造），超时/内部异常必须代码重试（模型对刚发生的超时没有元信息）。

`limit=0` 的两格收场相反，所以拆成 `action` 与 `degrade_when_unresolved` 两个字段：
权限错 → 数据永远拿不到 → 降级；幂等冲突 → 效果已发生 → 不降级。

三条演练轨迹实测可见（超时→2 条 action 第 2 条 retried=True；空结果→换关键词；
内部异常×2→degraded）。

## 三、周三 12/30 · 三道防跑偏

任务分解校验（执行前）+ 中间结果自检（每步后，纯规则）+ 语义判重（纯字符串）。

**默认全关**。理由：关着时图拓扑与轨迹键都与 v1.2.0 完全一致，

拖低"只有在可比前提下才答得出来。

成本（离线三任务）：plan +2880 token（+50%），self/dedup +0。

## 五、周五 01/01 · 20 任务测试集（主交付一）

### 5.1 结构

20 = 10 回归子集（W10，判据逐字不变）+ 10 新增。详见 `eval/agent/README.md`。

新增 10 个的分布：单工具 1 / 双工具 2 / 检索+计算 1 / **需人工确认 2** /
**不可完成 4**（信息缺失、能力外、需权限、需实时各一）。

回归子集保留 W10 原分类，新增用五类难度 —— 两套标签并存，因为它们的判据
强度不同，混成一张表会牺牲对比的可信度。

### 5.2 判据冻结

`eval/agent/tasks-20.jsonl`（20 行）+ `scripts/validate_tasks.py` 校验通过。
判据从 Python lambda 升级为**声明式 check 列表**，可序列化、可校验、可不读代码审阅。

**冻结时间 2026-01-01。** 之后不许改判据；判据 bug 单独提交并在本文件列出改前改后。

### 5.3 必答问题：新 10 个里有几个无机制也能过

**预期先写死（`expected_without_mechanisms`），跑完对照，不许事后改：**

| 任务 | 预期 | 实测 |
| --- | --- | --- |
| N1 单工具 | pass | √ pass |
| N4 双工具 | pass | √ pass |
| **N7 需确认** | **fail** | 关约束 → × fail；开约束 → √ pass |
| N9 信息缺失 | unknown | √ pass |
| N12 需实时 | unknown | √ pass |

**关键对照（01/01 实测，trae/qwen-3.5）：**

```
N7 关确认约束：直接调 generate_report（副作用已发生）→ degraded → 判据失败
N7 开确认约束：先问"是否发送给 supervisor" → completed → 判据通过
```

这就是"一半靠新机制才能过"的直接证据：**N7/N8 的成败完全取决于确认约束。**

### 5.4 一个必须记下来的设计错误

第一版把确认约束**对所有任务**拼上，回归子集立刻从 9/10 掉到 7/10 ——
T7（出报告）、T8（出报告+通知）都被模型"先请求确认"卡住，而它们的判据
要求"真的生成"。

那是把**任务级语义**当成了**全局安全**。修法：约束跟着任务走，
只有 `category == "confirm"` 的任务拼它。

## 六、回归子集：9/10，与基线持平

| 版本 | 通过 | 说明 |
| --- | --- | --- |
| W10 基线（v1.2.0）| 9/10 | 90% |
| W11 第 1 轮（10k 全局预算）| 7/10 | T7/T8 因预算触顶失败 |
| W11 第 2 轮（去掉确认约束）| 7/10 | T7 仍预算触顶 |
| W11 第 3 轮（compute 放宽到 12k）| 6/10 | 模型多在收尾处调 notify，端点不通 → 降级 |
| **W11 第 4 轮（修降级语义后）** | **9/10** | **与基线持平** |

### 6.1 掉点归因（三次失败各自的原因完全不同）

1. **7/10（第 1 轮）**：确认约束误用于全局 + 10k 预算截断 T7 的收尾步。
   前者是设计错误，后者是预算粒度问题。
2. **7/10（第 2 轮）**：确认约束修好了，但 10k 对 compute 类不够 ——
   T7 第 3 步后已 10147 token 且 `generate_report` **已成功**，
   却没预算走最后一步给答案。
3. **6/10（第 3 轮）**：预算放宽到 12k 后暴露第三个问题 ——
   模型自作主张在收尾处多调 notify，端点不通 → 降级 →
   一个**已经完成**的任务被判失败。

### 6.2 第三个问题是个真缺陷，值得单说

`degrade_node` 把"最后一个动作失败"当成了"整件事没做成"。
对 T7 这种任务，`generate_report` 已成功、只有 `notify` 失败，
降级就把成果全抹了 —— **做了 90% 然后多试一步，比什么都没做还糟**。

修法：`_only_optional_tail_failed()` 判三件事 ——
① 最后失败的是收尾类工具（只有 `notify` 在 `OPTIONAL_TAIL_TOOLS` 里）；
② 此前至少有一个成功动作；③ 没有其它非收尾类失败。
三条成立就保留 `completed`，把收尾失败写进 final_answer 供审计。

**这是"加机制"的反向教训**：周二加降级是为了不假装成功，
但它反过来把"真的做完了"判成了失败。机制的成本不只在于它多花的 token，
还在于它**改变判据的语义**。

### 6.3 T10 的那 1 分

T10（放射性指标缺失）在 W10 基线里就是 ×，原因是判据误伤：
模型为证明"该批次没有此指标"，引用了已有的 42.5/8.2 做对比，
而判据只看到"答案里出现库内数值"就判编造。

W10 周记已记录这一点，本周**没有改判据**（判据冻结在 01/01，
且它是回归子集的一部分）。所以 9/10 里的那个 × 是与基线**同一个 ×**，
不是新掉的分。

## 七、必答问题：机制有没有把成功的那 10 个弄坏

**答案：短期弄坏过三次，修完后持平（9/10）。**

三次都是同一类错误的不同形态：**把"某个环节的失败"当成"整个任务的失败"**。

- 确认约束全局化 → T7/T8 被"先问"卡住；
- 10k 预算颗粒度太粗 → T7 在收尾步触顶；
- 降级语义过宽 → T7 的报告被 notify 失败连坐。

这条经验比数字更重要：**可靠性机制的风险不在于它不生效，
而在于它生效得太广**。每加一个机制，都要问一句"它会不会把已经做对的事判错"。
