## 二、本周最大的坑：把"响应体大小"当成了"序列化成本"

周四的分段表说"序列化/中间件占 ~50%（~2ms）"，周五照着它做了两处优化：
响应瘦身（500→120 字）+ cold 端点接缓存。**归因矩阵三组实测：QPS 与 P95
全部在噪声内，A3 的 P50 反而 +1ms。**

归因错误在"归因"不在"优化"：

- 那 ~2ms 是 pydantic 校验 + FastAPI 请求解析 + 中间件的**固定开销**，
  响应体里的 1.5KB 字符串本身 <0.5ms —— 序列化 1.5KB 很便宜；
- 把"最大的段"直接当成"删掉它的内容就能省"——只有当段的成本
  **随目标物线性变化**时才成立，框架固定开销不满足这个前提；
- 缓存接入省的是"一段已经便宜的路"（hashing 全链路 <1ms）——
  **它假想的收益建立在我自己写的成本直觉上，而不是实测数字上**。

**generalized 教训**：分段表告诉你"哪段最贵"，但**不告诉你那段
为什么贵**。优化之前必须先问：这段的成本随什么变量变化？
响应体大小？请求频率？连接数？答不上来就先做个微基准，
别拿分段表当优化清单。

### 2.1 为什么这个坑与 W11 的坑同构

W11 三次"修机制"把好事判错，是把**环节失败**当成**任务失败**；
W12 优化无效，是把**段的归属**当成**段的成因**。两次都是
**一个结论走完了整条推理链，中间没有实测验证**。
W11 的修正靠"轨迹证据"；W12 的修正靠"归因矩阵"——
它们是同一个习惯的两个形态：**结论与证据之间必须有可复跑的桥**。

## 三、本周做对的三件事

1. **压测有预测**（周四复盘）：五条预期两条错，错在成本模型而不是数字
   —— 错得有价值，直接指出周五该验证什么。
2. **429 记 success 不记 failure**：限流背压混进错误率，会让"背压 vs 故障"
   永远分不清 —— 这个判读约定让"50 并发错误率 0%"成为可说的结论。
3. **两处优化如实写"无效"**：performance.md 的归因节标题就是
   "诚实版：优化无效"。**压测报告里没有无效优化 = 没有真压测**。

## 五、60 秒稿（面试用）

> 这周我把两周前还在脚本里跑的 Agent 变成了一个有 API 契约的服务：
> 鉴权、双层限流、三层缓存、双容器编排、压测基线。
>
> 数据上：检索层 27 QPS 无损，P50 全档恒定 4ms，错误率 0%；
> 50 并发时唯一出现的"错误"是 429——55% 是限流器在挡人，
> 5xx 是零，队列过载自动背压、排空自恢复。
>
> 但这周我最有价值的产出是一条**失败的优化**。分段表说序列化占 50%，
> 我照着做了响应瘦身和缓存接入——归因矩阵三组实测，QPS 和 P95
> 全在噪声里。为什么无效？因为那 2ms 是框架的固定开销，
> 不随响应体大小变化——**分段表告诉你哪段最贵，不告诉你那段为什么贵**。
> 我把"最大的段"直接当成了"删内容就能省的段"，中间没有验证
> 成本随什么变量变化。
>
> 所以我现在的流程是：分段 → 微基准确认成本变量 → 优化 → 归因矩阵
> 分批测 → 每处贡献一个数，没效果的如实写"无效"。
> **压测报告里没有失败的优化，等于没有真的做实验。**

## 七、W13 要证明什么（可观测 + MCP，不改算法）
