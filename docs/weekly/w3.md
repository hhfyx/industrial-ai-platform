## 二、自测错题：三道必须秒答

### B1 · Function Calling 是谁在执行？

**不是模型。模型只告诉你「想调什么」，执行永远在你这侧。**

证据在周二就和周二记的一样硬：`tool_calls` 里**只有函数名和参数 JSON，没有任何函数体**。
`TOOL_REGISTRY[name](**args)` 是我们自己的 Python 在跑。

这条认知的价值不在"知道"，在**它决定了 W9 Agent 的设计**：

| 推论 | 落到代码上 |
| --- | --- |
| 注册表即**权限边界** | 没注册的工具，模型想到了也调不到 |
| 执行点即**审计点** | 每次工具调用是一行可记的日志 |
| 上限即**安全阀** | `max_iterations` 防无限循环烧钱 |

**秒答版**：

> 模型负责"拟提议"，我们负责"真执行"。所以工具层的每一行代码都是安全边界 ——
> 参数校验、异常兜底、调用次数上限，都不能指望模型自觉。

### C6 · 流式里的错误怎么处理？

分三层，每层管不同的事：

| 层 | 问题 | 做法 |
| --- | --- | --- |
| ① **首字节之前** | 模型还没开始吐，出错就是普通 HTTP 错误 | 正常返回 4xx/5xx JSON，**这时候还能改状态码** |
| ② **首字节之后** | 已经发了 `200 + text/event-stream`，**状态码改不了了** | 发一个 `event: error` 帧，然后在流里结束 |
| ③ **客户端断开** | 用户点了停止 | 监听 ASGI `http.disconnect`，**别用 `request.is_disconnected()`** |

**第 ③ 条是本周实测最大的坑**：`request.is_disconnected()` 在生成器里**恒返回 `False`**，
因为 `StreamingResponse` 占用了 `receive` 通道。表现是"用户走了，后端还在烧 token"。

**秒答版**：

> 流式错误要分"是否已发首字节"。已发之后状态码就锁死了，
> 只能用 SSE 的 error 帧；而客户端断开必须监听 ASGI 的 `http.disconnect` 事件，
> `request.is_disconnected()` 在流式响应里不可用。

### G2 · 哪些文件不能动？

**只有一个是绝对红线：[`docs/api-spec.md`](../api-spec.md)（v1 契约，现 v1.1）。**

它冻住的证据不是"我们决定不动"，而是**换实现时它一行都没改**：

| 换过什么 | api-spec.md 改了吗 |
| --- | --- |
| 规则版 → LLM 版抽取器 | ❌ 没改 |
| 新增 `degraded` 字段（v1.1） | ✅ 改过一次（**唯一一次**，且向后兼容） |
| 换成 `structured_call` 底座 | ❌ 没改 |
| prompt 模板 v1 → v2 → v1.1 | ❌ 没改 |

**"向后兼容"的判据很具体**：`degraded` **只在 `true` 时出现**，
正常结果里**没有这个键**（api-spec §2.5）。所以老调用方不读它也不会坏。

另外两条不能乱动的：

- `app/schemas/extract.py` —— 它是 api-spec 的**可执行版本**，改它等于改契约
- `tests/test_api.py` —— 契约测试。**它挂着的时候不要改它来让测试过**

**秒答版**：

> 只有 `docs/api-spec.md` 不能动。判据是"换实现时它改没改" ——
> 规则版换 LLM 版、加 structured_call 底座、模板三个版本演进，它一行没改。
> 唯一的改动是 v1.1 加可选 `degraded`，且只在 true 时出现，向后兼容。

## 三、本周学到的四条（比交付物更值钱）

### 3.1 判定/统计口径比模型先出错，一周犯了**五次**

| 哪天 | 错误 | 后果 |
| --- | --- | --- |
| 周二 | 拒绝率用二元口径 | 三项指标**假性打平**，看起来"严格版没用" |
| 周四 | "不确定+引用"判成矛盾 | 把**模型的正确行为**判成错 |
| 周六 | 汇总只算成功条目 | 摘要"1.0 vs 1.0 无差异"，实际是 **0.90 vs 0.30** |
| **周日** | **成本/token 比值用总量，未按成功样本归一** | **摘要 v2 "省 62%"，实际贵 37%** |
| **周日** | **用 1 条样本断言"扁平 schema 也失败"** | **补跑 10 条发现是 8/10 成功，整节结论方向错** |

**规律：当模型的行为看起来不合理时，先怀疑自己的判定口径。**

前四次是**统计口径**问题（分母错了），第五次是**样本量**问题（代表性错了）。
两者都属于"我以为在核对事实，其实在核对自己的假设"。

#### 第四次：成本指标被失败率污染（这次最容易被面试问）

`summary.json` 里原报 `token_ratio: 0.38`、`total_cost_cny: 0.294 → 0.134` ——
字面读是"v2 省了 62% 的钱"。

**但失败的请求不产出 token。** 按"每条成功"重算：

| | 总成本 | 成功条数 | **每条成功成本** |
| --- | ---: | ---: | ---: |
| v1 | 0.293938 | 9 | **0.03266 元** |
| v2 | 0.134136 | 3 | **0.04471 元** |

**→ v2 实际贵 37%，不是省 62%。"总成本更低"只等于"有 7 次没跑起来"。**

同一口径下 token 也是：

| | 每条成功 token | |
| --- | ---: | --- |
| v1 | 4459 | |
| v2 | 6022 | **v2 多 35%**（原报 0.38x，"省 62%"） |

#### 还有一处更隐蔽的同类污染（方向相反，更该警惕）

`extract` 的 `token_ratio` 原报 **1.01** —— 看起来"两版一样贵"。
按成功归一后是 **0.418** —— **v2 实际省 58%**。

原因：v1 有 1 条失败样本，它在**修复轮里烧了 23270 completion token**
（v2 只有 6900）。那笔巨额消耗被算进了 v1 的总分母，让 v1 显得"很贵"，
于是 v2 的优势被**稀释**了。

> **方向对我不利的污染（摘要）和对我有利的污染（抽取），我一开始只发现了前者。**
> 这说明"污染"不是"让结果变好看"的代名词 —— 它会**双向**扭曲，
> 所以不能靠"感觉这个数不对"来发现问题，得靠**口径本身写死在代码里**。

#### 修法（已落到代码）

1. `ab_test.summarize()` 同时输出 `total_*`（辅，标注污染风险）与 `*_per_ok`（主，按成功归一）
2. `delta` 里**只用 `cost_ratio_per_ok` / `token_ratio_per_ok`**，
   原来那个 `token_ratio`（总量口径）改名为 `token_ratio_total_uncontrolled`
3. 两臂失败率不同时，控制台**主动打印警告**
4. `rebuild_summary.py` 从已有 CSV 重算 —— **改统计口径不该重花 API 的钱**

#### 可推广的两条规则

> **① 任何"总量"指标，只要分母与"成功样本数"有关，就必须按成功样本归一。**
> 成本、token、延迟都属此类。
>
> **② 对比两个版本时，先看两臂的失败率差。差得多，所有总量指标都不可信。**

**为什么这条比 A/B 分数更容易在面试里被问**：分数是"你的实验做得怎么样"，
而成本口径是"你会不会算账" —— 后者是工程判断力，前者只是执行力。

### 3.2 框架的简洁性，建立在它对你环境的假设上

LangChain 的 `with_structured_output` 隐含假设：**网关会按 schema 出**。

**我的网关是"部分满足"这个假设**：

| schema 形状 | 成功 |
| --- | ---: |
| 嵌套 `{fields: dict, ...}` | **0/10** |
| 扁平 `{字段1: str, 字段2: str}` | **8/10** |

我要的是嵌套（字段数运行时才知道），恰好是失效的那一档。

**这不是框架烂，是"有效区间不重叠"** —— 而且这个结论我自己修正过一次：
初版基于**1 条**样本写"扁平也失败、网关根本不强制格式"，
补跑到 10 条才发现是 8/10 成功。**见 §3.1 的第五个同类案例**。

更普适的判断力：**别问框架"能不能做"，问它"在你的具体输入形状上，做出的成功率高不高"。**

### 3.2.1 补一条：1 条样本可以说"这条能过"，不能说"这一类都能过"

| 我最初的说法 | 依据 | 实际情况 |
| --- | --- | --- |
| "本网关根本不强制任何格式，扁平也失败" | **1 条**扁平输入 | **扁平 8/10 成功** |

**样本不足时的错误，不会以"我不确定"的形式出现，而会以"确定的错误结论"的形式出现。**
这和第 3.1 节那四次口径错误是同一类：**我以为自己在核对事实，其实在核对一个样本。**

> 这也解释了为什么本周我反复强调"dump 原文核对" ——
> 但 dump 原文只能防"读错已采集的数据"，
> **防不住"用 1 条样本代表一整类"**。后者要的是补跑，不是核对。

### 3.3 同一个坑踩了两次，说明我没把教训写成约束

`max_tokens`：
- 周四：2048 → 4096（摘要思维链 4621 字符打满）
- 周六：4096 → 8192（摘要思维链 9405 字符打满）

**两次都是"以为 JSON 短就够用"，两次都是思维链先吃光。**

现在教训写在了源码注释里，并且写成了一条可推广的规则：

> **预算按最重的那个任务定，不按典型任务。** `max_tokens` 是上限不是预留，
> 调大不额外花钱（`usage.completion_tokens` 只算实际产出）。

### 3.4 契约修复的杠杆 >> 提示词优化

extract 的 +63pp，**几乎全部来自"字段槽位能对上"**，不是措辞。

| 改动 | 效果 |
| --- | --- |
| v1 固定槽位 `主体/时间` → v2 任意字段清单 | **+63pp** |
| v1 → v2 的措辞优化（分类的反向边界等） | 0pp |
| CoT 提示 → few-shot（周一） | +20pp |

**改契约和改措辞不是一个量级的杠杆。**
所以遇到"模型表现不行"，第一反应应该是查**接口对不对**，而不是改 prompt。

## 四、本周的"负收益"结论（同样重要）

不是所有实验都该赢。本周明确了三处**不该做的事**：

| 做法 | 结果 | 结论 |
| --- | --- | --- |
| 给推理模型加 CoT 提示 | 12/20 → 12/20，token 5 倍 | **别加** |
| v2 的"分步结构"（qa/summarize） | qa −3.7pp、summarize −60pp | 推理模型自己已在分步 |
| Self-Consistency 5 次投票 | +2pp，成本 5 倍 | 不划算 |

**共同点：它们都在"模型已经会做"的动作上再加一层。**

## 五、下周（W4）开工清单

### 5.1 ⚠️ 首要技术决策：摘要类任务不能挂在 `reasoning=high` 上

**这是本周最该带进下周的一条技术决策，不是实验结论。**

摘要任务在当前配置下的延迟（周六实测，`--fresh`）：

| | v1 | v2 |
| --- | ---: | ---: |
| 平均延迟 | **22.9 秒** | **25.4 秒** |
| **P95 延迟** | **55.1 秒** | 28.8 秒 |

**无论 v1 还是 v2，P95 都在 28 秒以上，v1 更是 55 秒。** 这个延迟不适合线上 ——
而 W4 要建 RAG 链路，**生成层会直接继承这个延迟**（摘要本来就是 RAG 的输出形态）。

根因不在模板，在 `reasoning=high`：思维链在摘要任务上能写到 9000+ 字符
（这还导致 `max_tokens` 被两次打爆，见 §3.3）。

**建议的决策方向（下周开工第一件事，需实测验证）**：

| 方案 | 做法 | 预期 |
| --- | --- | --- |
| **A（首选）** | 摘要类任务降 `reasoning_effort` 到 `none`/`low` | 延迟砍到秒级；质量掉多少需实测 |
| B | 摘要换非推理模型（如 `buddy/glm-5.3-flash` 一类） | 彻底摆脱思维链，但要重跑精度对比 |
| C | 保留 `high`，但把 `timeout` 提到 60s + 前端明示"需要 20-60 秒" | 不解决根本问题，只改观感 |

**验收方式**：同一批 10 条摘要，A/B/C 各跑一遍，记录 **P95 延迟 + 要点召回**，
用本周已建好的 `ab_test.py`（注意用 `cost_ratio_per_ok` 口径，见 §3.1）。

> **为什么写进开工清单而不是留在报告里**：如果下周直接开建 RAG，
> 大概率会把"摘要很慢"当成"RAG 很慢"，然后在错误的地方优化。
