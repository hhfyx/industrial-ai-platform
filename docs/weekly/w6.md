## 二、周一：BM25 落地

### 2.1 做成了什么

| 项 | 结果 |
| --- | --- |
| BM25 索引 | 1592 块 / 46994 token / **重建 794 ms** / 落盘 **444.8 KB** |
| 词典 | 31 词（4 个工业术语已就位，但语料里出现 0 次） |
| 停用词 | 68 个（**故意保留「不」「没」**，它们在本项目有语义） |
| 对照（全量 40 条） | 向量 16 / BM25 14 / **差异 10 条** |
| 测试 | `tests/test_bm25.py` 14 条 |

命令：`make build-bm25` / `make bm25-audit` / `make bm25-compare`

### 2.2 三个技术决定

**① 型号/标识符必须整体成一个 token。**
第一版只做了词典，然后发现 `INVALID_INPUT` 被切成 `invalid`/`input`、
`bge-small-zh` 被切成 `bge`/`small`/`zh`。
这两个词都极常见、IDF 很低，而**型号匹配正是 BM25 相对向量检索唯一的结构性优势** ——
切碎等于把优势自己拆掉。加了一层标识符保护网后才修好。

**② 不 pickle `BM25Okapi` 对象，只存原始输入。**
它内部缓存 `idf`/`doc_freqs`，那是从 corpus 派生的中间状态。
把派生状态存进文件 = 把缓存当源码，版本升级或参数微调时旧值会悄悄生效。
只存 token 流 + 参数，加载时用当前代码重建（0.4 秒，比重建全部索引便宜得多）。

**③ 索引文件存「分词器指纹」。**
这一项是本周最隐蔽 bug 的守门人：词典改了而索引没重建时，
索引里是旧词边界、查询用新词边界，两侧不一致 ——
不报错、只是分数系统性偏低，而人会去怀疑"BM25 不适合中文"。

### 2.3 本节最值得记的一条：**W5 的标签被推翻了**

W5 归因表把 15 条错例判成「② 术语/同义词未命中」，占 50%，是最大的一块。
本周按判据逐条查了"query 与 gold 块有没有稀有公共 token"：

| 情况 | 条数 |
| --- | ---: |
| 含稀有标识符（BM25 该强） | **0** |
| 只共享「模型/输入/上限/文档」这类高频普通词 | 12 |
| 连一个公共 token 都没有 | 3 |

**0 条真有字面锚点。** 那 15 条根本不是"术语没对上"，
按"加个更好的分词器"去修是**两个方向都不对症**。它们该被拆成：
- 只共享普通词 → 长块降权 / 表格路由（W5 已记的猜想）
- 零公共 token → 向量侧（更强模型 / 查询改写）

这也解释了为什么 BM25 只赢 4 条而不是预期的十几条：**它该赢的地方，这批题里没有。**

> **教训**：一个占 50% 的归因类别如果是错的，它会把后面所有改进方向都带偏。
> 而"错"不一定表现为数字难看 —— 它表现为**数字看着合理、方向却不对**。
> 拆标签的成本很低（一条判据 + 一个脚本），收益是整周的改进方向。

### 2.4 「工业文档里 BM25 收益更大」这个预期：**本周无法验证**

任务给的预期是对的，但当前语料是技术文档：

    景深 0 次   光通量 0 次   背光 0 次   同轴 0 次   公差 4 次

词典里那 4 个工业术语进了词典，语料里一次都没出现。
所以这句话**今天没有数据支持**，只能等真工业语料。已验证的是
型号/标识符这条路（与"工业型号编码"是同一类信号）。

## 三、周二：混合检索，以及一个"不许不信数据"的时刻

### 3.1 做成了什么

| 项 | 结果 |
| --- | --- |
| 合并比例 | 并集 **35.2** 条/题、交集 **4.8** 条、Jaccard **13.6%** |
| **独有占比** | **86.4%**（两路候选几乎不重叠 → 混合有信息基础） |
| 最好的数 | `weighted_a0.3` Recall@5 **45.0%**（18/40） |
| 纯向量基线 | **40.0%**（16/40） |
| **显著性** | **八组全部 p > 0.05 —— 没有任何一组显著** |
| 本周基线 | **保持纯向量**（0 参数、0 额外索引） |
| 测试 | `tests/test_fusion.py` 20 条 |

### 3.2 三条结论

**① RRF 比纯向量差 5pp，而这有机制解释。**
不是"RRF 不好"，是它**天然偏好共识**：top5 里 155/200 个槽位是两路都召回的块。
而本项目的候选集是 86.4% 独有 —— 用偏好共识的方式融合，等于主动丢掉最有价值的部分。
`f-16` 和 `m-09` 就是这么丢的（它们都只有一路能召回）。

**② 好看的 45.0% 是 3 赢 1 输。**
`weighted_a0.3` 相对基线 +5pp，但配对 McNemar p = 0.625。
在 40 条样本上，+2 条完全在噪声里。**如果我不做检验，这个数会被当成"融合有效"的证据。**

**③ 基线保持纯向量。**
规则跑之前就写死了：先看显著性，没有显著更好的就不动摇基线。
换基线的收益在噪声里，代价是链路复杂 + 每次请求多跑一路检索。

### 3.3 我一开始说错了一件事

周一我在文档里写"`0.5*cos + 0.5*bm25` 会让 BM25 **完全支配**"。实测不是：

- 量纲确实差 **24 倍**（向量均值 0.617 vs BM25 均值 14.91）
- 但 `naive_a0.5` 与纯 BM25 的 top5 **有 20/40 题不同** ——
  向量那点小分仍在**打破 BM25 的等分候选**

修正后的说法：不归一化不等于"向量没用"，而是 **α 变成假的** ——
调 0.3/0.5/0.7 只带来微弱抖动，而人会以为"α 调了没差别是两路贡献相近"。

> **教训**：技术推理也要实测。我按"24 倍差必然完全支配"链式推理，被数据否掉了一半。
> 这类"看起来必然"的推理，恰恰最容易被自己的量纲直觉骗。
