## 二、周一：BM25 落地

### 2.1 做成了什么

| 项 | 结果 |
| --- | --- |
| BM25 索引 | 1592 块 / 46994 token / **重建 794 ms** / 落盘 **444.8 KB** |
| 词典 | 31 词（4 个工业术语已就位，但语料里出现 0 次） |
| 停用词 | 68 个（**故意保留「不」「没」**，它们在本项目有语义） |
| 对照（全量 40 条） | 向量 16 / BM25 14 / **差异 10 条** |
| 测试 | `tests/test_bm25.py` 14 条 |

命令：`make build-bm25` / `make bm25-audit` / `make bm25-compare`

### 2.2 三个技术决定

**① 型号/标识符必须整体成一个 token。**
第一版只做了词典，然后发现 `INVALID_INPUT` 被切成 `invalid`/`input`、
`bge-small-zh` 被切成 `bge`/`small`/`zh`。
这两个词都极常见、IDF 很低，而**型号匹配正是 BM25 相对向量检索唯一的结构性优势** ——
切碎等于把优势自己拆掉。加了一层标识符保护网后才修好。

**② 不 pickle `BM25Okapi` 对象，只存原始输入。**
它内部缓存 `idf`/`doc_freqs`，那是从 corpus 派生的中间状态。
把派生状态存进文件 = 把缓存当源码，版本升级或参数微调时旧值会悄悄生效。
只存 token 流 + 参数，加载时用当前代码重建（0.4 秒，比重建全部索引便宜得多）。

**③ 索引文件存「分词器指纹」。**
这一项是本周最隐蔽 bug 的守门人：词典改了而索引没重建时，
索引里是旧词边界、查询用新词边界，两侧不一致 ——
不报错、只是分数系统性偏低，而人会去怀疑"BM25 不适合中文"。

### 2.3 本节最值得记的一条：**W5 的标签被推翻了**

W5 归因表把 15 条错例判成「② 术语/同义词未命中」，占 50%，是最大的一块。
本周按判据逐条查了"query 与 gold 块有没有稀有公共 token"：

| 情况 | 条数 |
| --- | ---: |
| 含稀有标识符（BM25 该强） | **0** |
| 只共享「模型/输入/上限/文档」这类高频普通词 | 12 |
| 连一个公共 token 都没有 | 3 |

**0 条真有字面锚点。** 那 15 条根本不是"术语没对上"，
按"加个更好的分词器"去修是**两个方向都不对症**。它们该被拆成：
- 只共享普通词 → 长块降权 / 表格路由（W5 已记的猜想）
- 零公共 token → 向量侧（更强模型 / 查询改写）

这也解释了为什么 BM25 只赢 4 条而不是预期的十几条：**它该赢的地方，这批题里没有。**

> **教训**：一个占 50% 的归因类别如果是错的，它会把后面所有改进方向都带偏。
> 而"错"不一定表现为数字难看 —— 它表现为**数字看着合理、方向却不对**。
> 拆标签的成本很低（一条判据 + 一个脚本），收益是整周的改进方向。

### 2.4 「工业文档里 BM25 收益更大」这个预期：**本周无法验证**

任务给的预期是对的，但当前语料是技术文档：

    景深 0 次   光通量 0 次   背光 0 次   同轴 0 次   公差 4 次

词典里那 4 个工业术语进了词典，语料里一次都没出现。
所以这句话**今天没有数据支持**，只能等真工业语料。已验证的是
型号/标识符这条路（与"工业型号编码"是同一类信号）。

### 2.5 代价列

| 指标 | 值 |
| --- | ---: |
| BM25 重建 | **794 ms**（1592 块） |
| 其中分词 | 约 700 ms |
| 落盘体积 | **444.8 KB** |
| 检索耗时 | < 5 ms |
| token/块（avgdl） | 29.52 |

对比向量索引 122.6 ms / 1592 块：BM25 慢 6.5 倍，但两者都是**一次性索引成本**。

## 三、周二：混合检索，以及一个"不许不信数据"的时刻

### 3.1 做成了什么

| 项 | 结果 |
| --- | --- |
| 合并比例 | 并集 **35.2** 条/题、交集 **4.8** 条、Jaccard **13.6%** |
| **独有占比** | **86.4%**（两路候选几乎不重叠 → 混合有信息基础） |
| 最好的数 | `weighted_a0.3` Recall@5 **45.0%**（18/40） |
| 纯向量基线 | **40.0%**（16/40） |
| **显著性** | **八组全部 p > 0.05 —— 没有任何一组显著** |
| 本周基线 | **保持纯向量**（0 参数、0 额外索引） |
| 测试 | `tests/test_fusion.py` 20 条 |

### 3.2 三条结论

**① RRF 比纯向量差 5pp，而这有机制解释。**
不是"RRF 不好"，是它**天然偏好共识**：top5 里 155/200 个槽位是两路都召回的块。
而本项目的候选集是 86.4% 独有 —— 用偏好共识的方式融合，等于主动丢掉最有价值的部分。
`f-16` 和 `m-09` 就是这么丢的（它们都只有一路能召回）。

**② 好看的 45.0% 是 3 赢 1 输。**
`weighted_a0.3` 相对基线 +5pp，但配对 McNemar p = 0.625。
在 40 条样本上，+2 条完全在噪声里。**如果我不做检验，这个数会被当成"融合有效"的证据。**

**③ 基线保持纯向量。**
规则跑之前就写死了：先看显著性，没有显著更好的就不动摇基线。
换基线的收益在噪声里，代价是链路复杂 + 每次请求多跑一路检索。

### 3.3 我一开始说错了一件事

周一我在文档里写"`0.5*cos + 0.5*bm25` 会让 BM25 **完全支配**"。实测不是：

- 量纲确实差 **24 倍**（向量均值 0.617 vs BM25 均值 14.91）
- 但 `naive_a0.5` 与纯 BM25 的 top5 **有 20/40 题不同** ——
  向量那点小分仍在**打破 BM25 的等分候选**

修正后的说法：不归一化不等于"向量没用"，而是 **α 变成假的** ——
调 0.3/0.5/0.7 只带来微弱抖动，而人会以为"α 调了没差别是两路贡献相近"。

> **教训**：技术推理也要实测。我按"24 倍差必然完全支配"链式推理，被数据否掉了一半。
> 这类"看起来必然"的推理，恰恰最容易被自己的量纲直觉骗。

### 3.4 语料污染：同一个坑的第二次

跑第一版时块数 1650，基线是 1592 —— 因为我**当天新写**的 `docs/bm25.md`
和 `docs/weekly/w6.md` 进了检索库，**而 w6.md 正文里就写着「Recall@5 40.0%」**。

这不是 W5 那种"竞争文档"，是**泄题**：答案直接躺在库里。

修法按**目录**而不是按文件（`ANALYSIS_DIRS = ("docs/weekly/",)`），
因为周报每周新增一份、每份都在复述当周结论，逐个加名单必然再漏。

> **这是同一个坑的第二次**（W5 漏 `retrieval-tuning-token-grid.md`，W6 漏当天的 `bm25.md`）。
> 两次主指标都几乎不变，所以**没有任何数字会报警** —— 只能靠规则与测试守。

## 四、周三：Reranker，以及一个"超标一个量级"的延迟

### 4.1 三个延迟数字

| 指标 | 值 |
| --- | ---: |
| 模型加载（一次性） | 12.3 s |
| 单对 | **172 ms** |
| batch=32 吞吐 | 1.1 对/秒 |
| **Top20 端到端** | **8.9 s** |
| **Top50 端到端** | **16.4 s** |

任务书写的是「单 query 超 2 秒就立刻记下来」——实测 **Top50 是 16.4 秒，超 8 倍**。
按 2 秒预算倒推，CPU 上只能精排 **4~5 条**。

### 4.2 批量越大越慢（反直觉，且有明确根因）

| batch | 按检索顺序 | 按长度排序 |
| ---: | ---: | ---: |
| 1 | 548.7 ms/对 | 430.8 |
| 8 | **1021.8** | **482.7** |
| 16 | **1767.2** | 1010.6 |
| 32 | 1168.6 | 891.0 |

根因是 **padding 浪费 230%**：候选里有一条 542 token 的表格块，
按顺序切 batch 时同组其余 31 条全要补到 542，而它们中位只有 113 token。
按 token 长度排序组 batch 后有 2 倍提速 —— **但 CPU 上仍不如单条**。

这与 W2 测 embedder 时"batch=64 快 4 倍"的结论**相反**：
embedder 是短文本+小模型，reranker 是长文本+大模型。

### 4.3 小样本：2 条变好、0 条变坏，但 8 条精排根本救不了

| 指标 | 值 |
| --- | --- |
| 变好 | 2 条（f-05 从 #13 → **#1**、f-08 从 #19 → #6） |
| 变坏 | 0 条 |
| MRR | 0.0129 → **0.1167** |

**但 8 条"没变"全部是 gold 根本不在候选 top20 内** ——
精排是重排序，不是召回，它变不出正确答案。

这正好和 §4.1 的"只能精排 4~5 条"构成同一个矛盾的两面：
**候选窗口太小救不了召回，窗口太大又扛不住延迟。**

### 4.4 试卷里的必答问题：分数不能跨 query 比较

实测 8 条 query 的 top1 分从 **0.002 到 0.842**，跨度 **0.840** ——
同一模型、同一批候选，只换 query 就整体平移。
所以绝对阈值（"分数 > 0.5 就算相关"）毫无意义，必须按 query 内归一化。

**这是本周第五次遇到"分数尺度"问题**（Chroma distance、BM25 无界、
加权融合量纲、RRF 免疫量纲、Cross-Encoder）。每次结论都一样：
**跨分布比较绝对分数，是这类系统里最容易犯且最难发现的错。**

### 4.5 语料污染：同一个坑的**第三次**

跑第一版块数是 1404，而昨天基线 1363 ——
因为**昨天新写的 `docs/hybrid-retrieval.md` 进了检索库**。

三次全是同一个循环：**我在写分析文档，然后在用它污染评测。**

| 轮次 | 漏了什么 |
| --- | --- |
| W5 周日 | `retrieval-tuning-token-grid.md` |
| W6 周一 | `bm25.md` + `weekly/w6.md`（当天新写） |
| W6 周三 | `hybrid-retrieval.md`（昨天新写） |

这次终于改成**名字模式**（`retrieval-*` / `bm25*` / `hybrid-*` / `eval-*` /
`strategy-*` / `rerank`），新写一份 `reranker.md` 会自动被排除，不改任何名单。
并用 `test_new_analysis_doc_is_excluded_without_touching_any_list`
拿**还不存在**的文件名去问规则 —— 我用移除 `rerank` 前缀的方式验证过它会红。

> **教训**：前两次我都写了"下次按规则判"，但两次都还是补名单。
> 第三次才真的把判据改成模式。**"知道该怎么做"和"做了"是两件事** ——
> 前两次的修法只是把下一次漏的时间推后了一点。

## 五、周四：一个改变全周判断的数字

### 5.1 召回上限：纯向量 50%，混合 68%

| N | 纯向量 | 混合 RRF | 增益 |
| ---: | ---: | ---: | ---: |
| 5 | 40.0% | 40.0% | 0 |
| 10 | 42.5% | 50.0% | +7.5pp |
| 20 | **50.0%** | **68.0%** | **+18.0pp** |
| 30 | 60.0% | 68.0% | +8.0pp |
| 50 | **62.5%** | **77.5%** | **+15.0pp** |
| 100 | 72.5% | 82.5% | +10.0pp |

**这一行是本任务书里最容易漏、也最重要的一行。** 它说的是：

    纯向量路线下，即使精排完美，Recall@5 的上限也只有 50%

所以**主瓶颈在召回层，不在精排层**。周三我看到"精排前后 Recall@5 没变"
差点得出"精排没用"的结论 —— 那是把召回层的问题误判成精排层。

### 5.2 这个数字**修正了周二的判断**

周二测混合时，八组全部 p > 0.05，结论是"没有一组显著，基线保持纯向量"。
今天的数据说明**那个判断不完整**：

| 指标 | 纯向量 | 混合 RRF | 差 |
| --- | ---: | ---: | ---: |
| Recall@5（排序质量） | 40.0% | 40.0% | **0** |
| Recall@20（召回广度） | 50.0% | 68.0% | **+18pp** |

> **混合的价值不在"把 final top5 排得更好"，而在"把正确答案捞进候选集"。**
> 它是为精排提供更宽输入的，不是直接改善最终排序。

周二所有实验都只看 top5，所以看不出来。**这不是周二做错了，
是周二的实验范围不够回答今天这个问题。**

### 5.3 精排是有效的，但绝对收益被 top5 位置钉死

全 40 条、N=20，可精排的 20 条里：

| 名次变化 | 条数 |
| --- | ---: |
| 往前挪 | **9** |
| 往后挪 | 2 |
| 没变 | 6 |
| 中位 | **−1 位** |

新进 top5：f-05（#13 → **#1**）、m-01（#11 → #3）；掉出：m-09（#5 → 未进）。
**净收益 +1 条**（16 → 17，40.0% → 42.5%）。

方向是对的（9 挪前 / 2 挪后），但**top5 只有 5 个位置、16 条已命中**，
剩 4 个名额要容纳 60% 的未命中题 —— 能挤进来的天然有限。

> 这就是**相对改善（9 条）与绝对收益（+1 条）差得远**的原因。
> 想提高绝对收益只能提高天花板，也就是**修召回**。

### 5.4 长 doc 截断：被截掉的部分"归零"，不是"略低"

同一句 golden 答案放在长文档三个位置，三种策略各打一次分（`max_length=512`）：

| 策略 | 答案在开头 | 答案居中 | 答案在末尾 |
| --- | ---: | ---: | ---: |
| `tail` | **0.9235** | 0.0003 | 0.0003 |
| `head` | 0.0003 | 0.0003 | **0.6463** |
| `middle` | 0.0003 | **0.7796** | 0.0003 |

**每一行只有自己覆盖的那一段有分，其余两段全部跌到 0.0003**（sigmoid 后的噪声）。
一条"答案在块尾"的长块会被压到噪声水平并**系统性排后**。

但当前语料只有 **3/1404 块**超过 512 token（中位 77 token），
所以默认配置下几乎不触发 —— 产物里的 `truncated_pairs` 就是让这个风险可见。

### 5.5 空 doc / 超短 doc：安全

空串 → 0.000238、超短 `"422"` → 0.0141、正常块 → 0.951。
**空输入不抛异常、给低分**。批量与单条一致性 **3.85e-08**。

顺手修了一个 API 隐患：`Reranker(truncation="tail")` 传字符串原本能构造成功，
直到 `rerank()` 才抛 `AttributeError: 'str' object has no attribute 'value'` ——
**错误发生在离现场很远的地方，报的还是 attribute 而不是参数类型错**。
现在 `__post_init__` 立刻规整并校验。

## 六、周五：压缩做完了，然后决定不用它

### 6.1 决策

**压缩不接入最终链路。** 任务书预判过这个结果（"可能结论是不进"）。

| 项 | 结论 |
| --- | --- |
| 压缩能力 | ✅ 已实现、可注入、21 条测试 |
| 默认启用 | ❌ 不启用 |
| 理由 | **上下文预算根本没用满** |

**理由不是"压缩不好"，而是"现在没有需要压缩的问题"** —— 这两者完全不同。

### 6.2 决定性的那个数字

| 指标 | 值 |
| --- | ---: |
| top5 上下文 p50 | **1060 字符** |
| 最短 / 最长 | 588 / 1600 |
| 预算 `max_context_chars` | 6000 |
| 超预算题数 | **0/40** |
| **平均预算使用率** | **17.7%** |

任务书预估"5 块 × 500 token ≈ 2500 token"，而实测 5 块合计约 **700 token** ——
**差 3.5 倍**。原因：`chunk_chars=500` 是**上限**不是均值，
实测块长中位数只有 **131 字符**。

省下的 token 在预算没用满时，换不来任何东西。

### 6.3 成本-质量权衡曲线（三个数字）

| keep_ratio | 节省 token | 答案句存活 | 锚点存活 |
| ---: | ---: | ---: | ---: |
| 0.3 | **45.6%** | **25.0%** ⚠ | 50.0% |
| 0.5 | 37.5% | 37.5% ⚠ | 62.5% |
| 0.7 | 19.2% | 62.5% | 87.5% |
| 1.0 | −1.0% | **100%** | **100%** |

这条曲线说明：**省 45% token 的代价是丢掉 3/4 的答案句**。
如果只报"省了 45.6%"就是灾难 —— 而任务书那句
"不能只报省了 40% token 就完事"正是针对这个。

### 6.4 两个统计 bug，都在"存活率"判定上

**① 把"召回未命中"算成了"答案句被删"。**
第一版 `keep=1.0`（完全不压缩）只有 44.4% 存活 —— 而它必须是 100%。
原因：那些题的 gold 块根本没进 top5，压缩输出里当然没有。

**这和周四"天花板"是同一条教训**：统计压缩风险前，先确认候选里有 gold。

**② 锚点跨句子边界导致假失败。**
`keep=1.0` 时锚点存活率只有 50%。原因：`quote` 跨越句号时，
保序重组用空格拼句子会让子串匹配失效 —— **而内容一个字都没少**。

这正是任务书警告的那件事。修法是按片段判断（切片后每片都能找到）。

> **教训**：一个"看起来很合理"的指标，如果基线（不压缩）不等于满分，
> 那它测的就不是我以为的东西。**先验证基线再相信曲线。**

### 6.5 设计决定：压缩不改可检索身份

任务书要求"今天就定"的那条已落地：

| 层 | 用什么 | 压缩影响 |
| --- | --- | --- |
| 切分 / 索引 / 检索 / Recall | `Chunk.text` | ❌ |
| **只在这里**：拼 prompt | `build_context(texts=...)` | ✅ 唯一入口 |

用"id → 文本"映射而不是传压缩后的 `Chunk` —— 因为换 text 会让
`Chunk.id`（`sha256(源+页+正文)`）跟着变，**引用就回查不到原文了**。

双重防护：`Chunk` 是 frozen dataclass（写回直接 `FrozenInstanceError`）
+ `test_compress_does_not_mutate_chunk`。我注入过危险回退验证，两层都会拦。

### 6.6 什么情况下该重新考虑

写进文档了，为了半年后不用靠回忆：`top_k` 提到 10+、块长调到 800+、
**语料换成 PDF/工业长文档**（最可能）、出现 lost-in-the-middle 症状、
上下文成本成为账单可见项。

## 七、周日：延迟打点，以及「三层全关」的最终定版

### 7.1 四段占比：时间几乎全在精排

| 段 | 均值 | 占比 |
| --- | ---: | ---: |
| query 编码（bge） | 173.8 ms | 1.0% |
| 向量检索 | 122.0 ms | 0.7% |
| BM25 | 6.5 ms | 0.0% |
| **精排** | **16679.5 ms** | **98.2%** |

**98.2% 的时间在精排。** 其余四段加起来 302 ms。

顺带一个发现：`search_ms` 122 ms 比预期（内存检索 ~1 ms）慢两个数量级 ——
因为 `InMemoryVectorStore` 是纯 Python 遍历 1364 个向量，没有 ANN 索引。
**这是内存实现的代价，不是向量检索的固有成本**（生产用 Chroma+HNSW 会快得多）。

### 7.2 三档对比与「每省 1 秒的代价」

| 配置 | P50 | P95 | Recall@5 | 每省 1 秒代价 |
| --- | ---: | ---: | ---: | --- |
| A 候选 20 + 精排 | 16781 ms | **22546 ms** | 60.0% | — |
| B 候选 10 + 精排 | 9865 ms | 13394 ms | 55.0% | **0.7 pp/秒** |
| C 候选 20 无精排 | **137 ms** | 139 ms | 35.0% | **1.5 pp/秒** |

**精排贡献 +25pp Recall@5（35%→60%），是四层里最大的单项收益 —— 但它要 16.6 秒。**

### 7.3 两个「没做」的优化（诚实记录）

任务书列了四个优化项，我做了两个，另两个用数据证明不划算：

| 优化 | 判定 | 依据 |
| --- | --- | --- |
| embedding 缓存 | 已存在，测不出 | 20 条 query 各不同，命中率 0 |
| 精排结果缓存 | 未实现 | 同 query 重复问才有效，本轮场景测不出 |
| **并行化（asyncio.gather）** | **不做** | BM25+向量合计 128ms，占全链路 **0.75%**。并行收益上限 122ms，而把整条链路改 async 要动所有调用点 —— **付出架构复杂度换 0.7%** |

> **「不做」也是一个结论，只要给出理由。** 这一条值得单列，因为它容易被
> 「任务书要求了所以要做」的惯性推着做完，然后没人问收益。

### 7.4 最终定版：三层全关

| 层 | 状态 | 依据 |
| --- | --- | --- |
| 向量检索 | 开 | 基线，P50 137 ms |
| BM25 + RRF | 关 | Recall@5 −5.0pp |
| 精排 | 关 | +25pp 召回但要 16.7 秒 |
| 压缩 | 关 | 预算只用 17.7% |

**这意味着：当前链路 = W4 的链路，一行代码没变。**

那这周做了什么？**做了「确认哪些层不该上」** —— 如果不上，就不知道为什么不该上；
而「不知道」会在 W7/W8 反复重新评估，每次都要花几天。

三层功能全部保留为「可开启」，每层都写了重新启用的条件。

### 7.5 一个真实副作用：改 README 会改变检索结果

回归验证时发现：改 README 架构图（+15 行）让语料从 **1364 块变成 1365 块**，
于是 f-22 的 top1 分数从 `0.5764` 掉到 `0.5727` —— **刚好跨过 0.575 阈值**，
误拒从 7 条变成 8 条。

这不是 bug，是「语料变了」的必然结果（README 是知识文档，在白名单里）。
但它提醒：**跨版本比较数字时必须确认块数一致**。

> 这和 W5 那个「越努力写文档，评测越差」是同源问题 ——
> 只不过那次是分析文档污染，这次是**知识文档正常更新**的微小扰动。

## 九、W7 要评什么

### 9.1 评测集：200 条，必须从不同文档出题

W5 就记过的纪律：**50 条题面不得进入 200 条，哪怕换个问法**。
同一事实被问过一遍，人对它的"难易感"就变了。

**按新归因分布配额**（见 `docs/error-attribution.md` §5.1）：

| 类别 | 建议占比 |
| --- | ---: |
| ⑤ 长块/表格 | ~25%（本项目表格块 320 个，覆盖严重不足） |
| ③ 多跳 | ~20%（现有多跳 10 条，1 条 = 10pp，太脆弱） |
| ⑦ 语义区分度 | ~20%（换 embedder / 加精排的主战场） |
| 拒答 | ~20%（阈值问题的唯一验证场） |
| ① 切分断语义 | ~10% |
| ⑥ 零交集 | ~5% |

### 9.2 必须回答的问题

1. **精排的 +15pp 在 200 条上是否显著？**（现在 p=0.0703，样本不足）
2. **换更强 embedder 能否替代精排？**（精排 16.7 秒 vs 换模型可能只要几十 ms）
3. **表格块单独路由**能否解决 ⑤ 类 8 条？
4. **长块降权**这个从 W5 就记着的猜想，终于可以测了

### 9.3 不该再做的事

- 不再调 RRF 权重（已经证明 RRF 在本项目的候选结构上偏好共识，是结构问题不是权重问题）
- 不再加新的检索层（四层已经很清楚了：只有精排有量级收益，而它太慢）
- 不在 CPU 上继续压精排延迟（17 秒 → 15 秒没有意义，要的是量级变化）

## 十、本周方法论上的四条

1. **先算天花板，再谈优化。** 周四那个 Recall@50=62.5% 改变了整周方向 ——
   在知道它之前，我差点去调精排参数。
2. **指标的基线必须是"不优化时满分"。** 周五两个 bug 都是这个：
   不压缩时答案句存活率只有 44%、锚点存活只有 50% —— 那说明指标本身错了。
3. **"不做"要给出数字理由。** 并行化收益 0.7%，所以不做；
   如果只说"没必要"，半年后会被重新捡起来做一遍。
4. **同一个坑会咬五次。** 语料污染从 W5 到周六共 5 次，前 4 次都靠"补名单"，
   第 5 次才反转成白名单。**"知道该怎么做"和"做了"是两件事**。
