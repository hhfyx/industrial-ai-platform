## 二、必答问题的最终答案

**那 2 个不可完成任务，Agent 说出来做不到了吗？→ 是。两个都是。**

- T9（不存在的批次）：not_found 回灌后如实回答，还列出已知批次帮纠错。
- T10（不存在的指标）：0 行 → 主动全查确认 → "没有放射性指标的检测记录"。无编造。

**这个答案的意义**：W11 的 20 任务可以放"不可完成"类。
诚实退出不是靠 prompt 祈祷出来的，是**工具语义设计**出来的——
not_found 作为独立 error_type（修正动作菜单里"如实告知"那一项）
+ 0 行结果带 hint（"0 行就是答案，不要编造"）。

**T10 记 × 的真相**：判据误伤——我的 `_honest_refusal` 把"答案里出现
库内真数值"当编造信号，但模型引用 42.5/8.2 是为了对比说明"只有这两项"。
判据不改（纪律），教训入档：**编造检测要区分"引用查询结果"与"无中生有"**。

## 三、本周最大的坑（面试可讲的那个）

**tools 与 executor 不同源——模型"看到的工具"和"实际执行的工具"是两套。**

周三做描述 A/B 实验时，模型的反应怪异：先调 `search_knowledge_base` 失败
（unknown_tool），换驼峰变体再失败，最后如实报告"工具不可用"。裸调工具函数
却全部成功。追出的根因：`react_loop` 的执行层写死了 W2 注册表
（weather/calculate），传入 QA schema 后**模型看到 4 个新工具、执行层只认
2 个旧的**——模型说"工具不可用"是完全正确的感知，错在我的组装。

修复与制度化：`run_react_loop` 增加 `executor` 参数，
`agent_registry.py` 把 schema 和执行函数绑成同一模块的常量——
**从根上让"给模型看的"和"实际执行的"出自一处**。

**为什么它是 W9 最重要的坑**：它是 W2"schema 由 Pydantic 生成防漂移"
教训的**执行层变体**——漂移不只发生在两份 schema 之间，也发生在
schema 与注册表之间。同一条原则（单一事实来源）在三个位置被犯了三次
（两份 schema、schema 与校验模型、schema 与注册表），每次都是"两边分开
写迟早漂移"这一句话。

## 五、给 W10 留的话（要证明什么）

**W10 的主题是状态机带来的可中断 / 可恢复 / 分支，且成功率不能比本周差。**

具体到本周遗留（也是 W10 的验收输入）：

1. **投递失败的自动恢复**：账本里 `in_flight` 记录目前无人补投
   （模型只能如实报告"端点不可达"）。W10 要证明：状态机能把
   "中断点"记下来，重启后从断点恢复，且**不重复投递**（幂等账本已就位）。
2. **分支**：本周循环是单向链（Thought→Action→Obs→…），没有分支回溯。
   W10 的分支能力要过 T6/T7/T8 同款任务——复杂任务 4-5 步的形状不能变差。
3. **基线对比口径**：`run_eval_agent.py` + `eval_tasks.py` 原样复用，
   换执行器即可同判据对比（基线：9/10 · 2.4-2.6 步 · 7.1-8.1k tok）。
4. **只读结论**（W10 资料未动手）：状态机的核心增量是"每一步是可持久化的
   状态转移"，这与本周"轨迹 JSON 可回放"天然同构——轨迹 schema 可能
   直接升级为状态存档。
