## 二、本周最大的坑：**内存测量错了两次，差点把部署结论做反**

这是本周唯一"错误结果看起来非常合理"的一次，值得单独记。

### 事情经过

周六决定"免费层能不能跑 bge"时，我写了 `scripts/measure_memory.py` 测内存。
第一次跑出来：**所有阶段都是 ~1 MB，结论"免费层完全够"**。

如果信了它，今天就会给免费层配上 bge，然后在线上随机 OOM ——
而那时"部署完成"已经写进 README 了。

### 两个独立的错误源

**错误源 1：`tasklist` 的 CSV 里，内存字段含逗号**

```powershell
"python.exe","44520","Console","2","5,648 K"
#                                  ↑ 引号里的逗号
```

我用 `line.split(",")` 解析，`parts[-1]` 得到的是 `" K"` 而不是 `"5,648 K"`。
用 `csv.reader` 才对（它正确处理引号）。

**错误源 2：`.venv\Scripts\python.exe` 是 launcher，`Popen.pid` 不是被测进程**

```
Popen.pid        = 44520   ← launcher，一直 5.6 MB
子进程自报 os.getpid() = 31272   ← 真正加载了 torch 的那个
```

用 `Popen.pid` 查内存，量到的是空壳。
修法：让探针脚本第一行打印 `os.getpid()`。

### 修完之后

| 阶段 | 工作集 | 增量 |
| --- | ---: | ---: |
| baseline | 21.5 MB | 0 |
| + torch | 75.3 MB | 53.8 MB |
| + sentence-transformers | 198.5 MB | 177 MB |
| + 模型加载 | 431.7 MB | 410 MB |
| + 一次 encode | **548.4 MB** | **527 MB** |

结论变成：**527 MB 的模型栈 + Streamlit(~100MB) + Chroma(~50MB) = 免费层没有余量。**
→ 降级为 `hashing`，且降级在 UI 里显式可见。

### 为什么这条比"修复 bug"更值得记

**它的错误结果不是崩溃，是"数字变小了"。** 而"更小"看起来永远是好事。
这与 W3 那条 `connect_ex` 用反是同一种：**验证手段本身也会错，
而且错的时候不会报错，只会给出一个你愿意相信的答案。**

交叉验证才兜住它：单独跑一次得到 561 MB，脚本跑得到 527 MB（增量口径）—— 量级吻合。

## 三、本周第二个坑：拔网测试卡住 90 秒

验收要求"拔网 `pytest -q` 全绿"。我用死代理模拟断网，
结果 `test_embedding.py` **卡住不返回**。

原因不是测试写得不对：`huggingface_hub` 加载模型前会**先连网校验 commit hash**，
网络不可达时走重试 —— 而模型其实早在本地缓存里。

修法：`conftest.py` 加 session 级 autouse fixture，**缓存存在时强制
`HF_HUB_OFFLINE=1`**。同一个加载从"挂 90 秒"变成 2 秒。

> 这条的教训是**验收手段要提前跑**。我如果周日 17:00 才发现，
> 就只剩 30 分钟改，而没有时间重跑全量验证。

## 四、本周必答题汇总（都带实测数字）

| 问题 | 答案 | 证据 |
| --- | --- | --- |
| 长上下文能替代 RAG 吗 | 不能：成本线性（10x）、lost in the middle（稀释 23x）、无法溯源 | `scripts/rag_cost_compare.json` |
| 页码为什么会错位 | 因为切分之后才去猜。解析阶段就落 page，切分只继承 | 3 条测试守着 |
| 为什么必须归一化 | 归一化后内积 == 余弦（差 1.7e-17）。忘了会让排序被向量长度污染 | `scripts/embedding_norm_mechanism.json` |
| Chroma 的 `distances` 是什么 | **`1 - 余弦相似度`，越小越像，范围 [0,2]** | `test_distance_is_one_minus_similarity` |
| chunk_overlap 解决什么 | 防关键信息被切在边界。代价：冗余 9.4% + chunk 变多 + top_k 重复 | `scripts/chunking_compare.json` |
| **1.5 秒里检索占多少** | **9ms，占 0.36%~0.80% → 优化检索对首字毫无帮助** | `scripts/rag_bench.json` |

### 最后那条怎样改变了我的判断

我原以为"检索应该是延迟的一大块"。实测把它压到 1% 以下，意味着：

- ❌ W8 **不该**做"换更快向量库 / 加 IVF / 缓存 query"
- ✅ W8 该做模型侧：换更快模型 / 缩 prompt / 预生成首句
- ⚠️ **W5 调 TopK 不能拿延迟做依据**（5→10 只多约 1ms，但对质量影响是实质的）

**如果没有打点，这个判断会错一整周的方向。**

## 五、本周学到的五条

### 1. 「先写空壳适配器」是负资产

周三我只在 `get_store` 留了一个分支、没写 `ChromaStore`，理由写的是
"从未被 import 过的适配器不是扩展点，是未验证的代码"。
周四需求一到，真正实现并跑过 —— 周三那条注释当时是对的。

**推论**：接口可以提前定（因为改接口成本高），**实现不要提前写**（因为没跑过的实现等于不存在）。

### 2. 名字冲突比想象中贵

`summarize.Chunk` 与 `schema.Chunk` 两个东西同名但生命周期完全不同。
改名花了 4 个文件的机械劳动，但**不改的代价是**"想给检索块加个 score
时发现自己要动摘要链路的类型"。名字是认知边界，不是审美。

### 3. 测试数据本身会错，而且错得最隐蔽

三次踩到：
- 语料重复（5 份文档内容相同）导致 top3 被同一段占满 → 假"未命中"
- gold 抄错了（"2 名工程师" 在语料里不存在）→ 假"检索失败"
- "完全不存在的内容" 里的"不"字命中了 CHUNK 的"不超过" → 测的是别的东西

修法：脚本开头 `assert_gold_exists()`。**测试数据出错不报错，只让所有结论失真。**

### 4. 阈值必须与环境绑定，不能全局

全局 `MIN_SCORE=0.35` 把 `hashing` 的正确命中（0.247）拒掉了。
harness 的相关/无关分数**完全重叠**（0.148~0.478 vs ≤0.149），
任何单一阈值都无意义。

**推论**：凡是挂"绝对数值"的判断（阈值、超时、批量大小），
问到"这个数对谁成立"比问到"这个数是多少"更重要。

### 5. 「效果不好的证据」比"效果好的宣称"值钱

README 里那节「v1 已知问题」是本周真正的交付物：
14 条问题，按阻断/能力/工程分级，每条写清现状、原因、怎么修，
还给了"如果只有一天怎么排优先级"。

**面试官不会问"为什么召回率不高"（第一次都这样），
会问"你知道它哪里不好吗"。**

## 八、本周自我评价

**做得对的**

- **每次"验证"都换第二种方法复核**：内存测两次（561 / 527 量级吻合）、
  归一化内积 vs 余弦两种算法、Chroma distance 用构造向量验。
- **负收益结论如实记录**：LangChain 切中文失败、默认分隔符不切、
  完整 requirements 装不完 —— 都写在文档里。
- **区分"已实现"与"已验证"**：README 的"已知问题"把 14 条按严重度分级，
  未验证的单独一节。
- **把"降级"做进代码而不是文档**：`deploy_config.py` + 测试守着，
  而不是在 README 里写一句"免费层请用 hashing"。

**做得不够的**

- **真模型始终没跑通**。网关凭据是环境问题，但"一周的 RAG 交付里没有一次
  真实问答"是硬缺陷 —— 它让所有质量结论都悬空。
- **两个主交付的"链接"与"GIF"都是空的**。README 里"在线体验"那一栏只能写
  "未创建"，这不是完整交付。
- **评测集只有 10 条人造语料**，`overlap=50` / `top_k=5` 全凭直觉 ——
  却已经在 6 处文档里被当成默认值使用了。
- **内存测量写错两次才交叉验证**，第一次就该问"这个数字合理吗"。

**下周要改的**

- 任何"XXX 占多大比例"的结论，**先确认分子分母都来自同一次实测**。
- 任何"方案 A 更好"，先问"它在什么条件下不成立"。
- **把"未验证"在每天的交付里就标出来**，不要留到周复盘才发现。
