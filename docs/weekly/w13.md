## 二、本周最大的坑：对账抓出自己埋的雷（两个真缺口）

周二 20 条验证的第一轮对账：`calls=10`，而 extract 明明发了 10 条请求——
**extract 的 10 笔调用在对账里凭空消失**。

排查：六个 LLM 入口里，extract 走的是 `llm_extractor` 自建的
`_request`，不走 structured.py——我给五个入口埋了直录，漏了第六个。
**extract 成本整体低估 45%**（0.0093 / 0.0447）。第二轮修复后又抓出
第二个缺口：token 逐位一致但 `cost_diff=1.0`——`tracing.record_usage`
和 `metrics.compute_cost` 各有一套单价（一套默认 0），同一笔调用两个价。

**generalized 教训**：这两个缺口都不是"写错了"，是**"埋点完整性"
没有独立验证手段**——五个入口都埋了、测试全绿，但没人验证"每个
真实 LLM 调用都留了痕"。对账（聚合侧 vs 直录侧逐 token 比对）就是
这个验证手段：**不对账，你会漏掉重试、judge 调用、流式 usage 三类
漏记，每一项都能让成本低估 30%——而简历上的"成本下降 X%"就建立在
偏低的基数上。**这与 W11 的"轨迹证据"、W12 的"归因矩阵"同构：
结论与事实之间必须有可复跑的桥，对账是成本数字的那座桥。

## 三、本周做对的三件事

1. **对账锚点选"逐笔直录"**：本机网关没有账单端点（探测 5 个全 404），
   改为六个入口每次调用原样落 `usage_ledger`（只 INSERT）——锚点的
   语义是"发生过的事实"，聚合算错可以重建，账本改过就不再是锚点。
2. **告警阈值全部有实测出处**：检索 P95 阈值 20ms = W12 基线 10ms × 2，
   不是行业默认 3s（在本系统永不触发 = 自称有监控）。规则清单
   `RULES` 文档与代码共用，`test_rules_have_rationale` 固住"没有
   rationale 的规则不许存在"。
3. **行为层与协议层分离**：fs 工具是纯函数 + W11 错误信封（不 import
   mcp），协议层只做 `_unwrap`——测试不依赖 SDK，错误结构与 W9
   逐字段对齐，四要素描述模板直接复用。

## 四、必答三问（周六的收口）

1. **看板 30 秒指出"哪里慢"？** 能——四块布局打开即见最慢接口标注，
   下钻到 span 明细（实测 traces_wed 的 120ms 慢请求：embed/vector
   span 0-1ms、根 span 120ms = chaos 注入延迟，非检索段）。
2. **5 条攻击全拒？** 是——../ 逃逸 / 绝对路径 / 符号链接 / 超大 /
   越权写全部拒绝且 error_type 可读。过程中修复两个真实盲区：
   Windows 上 `/etc/passwd` 的 `is_absolute()=False`（补 `/` 前缀判断）；
   m-08 式"字符串前缀假象"（回归钉测试固住 resolve 纪律）。
3. **trace 能回答"贵在哪"？** 能——generation span 记 token/成本/ttft，
   trace_summary 聚合，对账保证数字可信。实测 20 条请求 0.0447 元，
   Agent 占 79%（agent.model_step 0.0352），extract 占 21%。

## 五、vLLM 概念验证（限时 40 分钟，两个数字 + 一句结论）

**实测**（本机网关 buddy-pool/glm-5.3，远程推理服务形态）：
吞吐 ≈ **31 tok/s**，首 token（非流式上界）≈ **2.0s**。

**为什么不自建**（量化，不是态度）：本机 RTX 4050 6GB 显存跑 vLLM
只能载 ≤3B 小模型——质量撑不起本平台的抽取/Agent 任务；而 vLLM 的
核心价值（连续批处理、PagedAttention）要在**高并发多租户**下才能
兑现，本平台实测流量 <0.1 QPS，服务层 P50 恒定 3-4ms，瓶颈从来不在
推理吞吐。**vLLM 适合的场景**：自持模型权重、批量离线推理、或多
租户高并发摊薄 GPU 成本。我的场景三者都不占——用网关 API，把
工程时间花在可观测与服务化上（这正是本周做的事）。
