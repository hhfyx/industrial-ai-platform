# 部署变体口径（deploy-variant.md）

> **这份文档回答一个问题：你说的那个数字，是哪一版系统的？**
>
> 本项目有**三条运行形态**。它们的检索能力不同，因此**同一句"Recall@5"不能
> 随便套在任何一个形态上**。简历、README、面试口述引用任何数字之前，
> 先到这张表里对号入座。
>
> 维护纪律：**新增部署形态或更换组件时必须更新本表**；
> 数字与口径不一致的 README 段落按本表为准修正。

## 三、简历采用规则（定案）

> **推荐：简历写评测版数字 + 注明"线上演示为轻量变体"。**

模板句式（可直接抄）：

> 「自建 120 条黄金评测集（含调参隔离与 judge 校准 30/30），Recall@5 56.0%；
> 已部署公网演示（Streamlit Cloud），线上因免费层内存约束降级为字面检索，
> 降级在 UI 显式可见；容器部署版与评测配置完全一致。」

**三条红线（写了就是给自己埋雷）**：

1. **不要把 56.0% 标在 Cloud 链接旁边当它的能力**——面试官打开链接问一句
   换说法的问题，答不上来，数字就成了负资产。
2. **不要说"线上是语义检索"**——免费层无 torch，hashing 是字面匹配。
   降级可见是设计，不是遮掩；说破了是加分，被戳穿是减分。
3. **不要引用未实测的数字**——评测集冷启动耗时、免费层并发上限、
   生成服务的单张推理耗时，全部处于"格子空着"状态。空格子不填。

## 四、形态间的能力差异速查（面试追问用）

**Q：为什么 Cloud 不装 bge？**
bge + torch 实测增量 528MB，叠加框架开销撞 1GB 上限（见
deploy-notes §内存实测）。三个替代方案里 hashing 是"确定的代价 vs
不确定的收益"——ONNX 未验证、API embedding 有出网与限流问题。

**Q：容器版和评测版真的完全一致吗？**
embedder、切分参数、top_k、阈值四项一致；差异只有两处且与检索无关：
LLM 端点（网关 vs 本机）与会话持久化介质（同是 sqlite）。
所以**检索层指标可外推，端到端得分需注明 LLM 不同**（judge 口径里
生成模型是变量之一，跨 LLM 比较要重测）。

**Q：W8 的多轮改写在 Cloud 上有意义吗？**
改写层在（代码同源），但**字面检索下改写的收益前提不成立**——
改写把「它的分布」扩成完整问题，收益依赖语义向量；
hashing 下扩写与否都是字符重叠。所以 hit@5 提升只声明给 B 线。
