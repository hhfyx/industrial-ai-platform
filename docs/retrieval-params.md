# 检索参数定版：TopK、过滤、阈值、拒答

> 本文是 **W5 周四**（2026-11-19）实测记录。
> 昨天的 token/切分网格在 [retrieval-tuning.md](retrieval-tuning.md)，
> 今天的四个参数都进了 `app/rag/settings.RagConfig`。

---

## 〇、先说三件最有用的事

1. **`k` 选 5 的依据是边际收益拐点，不是召回率。** 3→5 每 100 token 换 1.93pp 召回，
   5→8 掉到 0.63pp。而 **k=10 的 Recall@5 与 k=5 必然相等**（前 5 条是同一批）
   —— 这件事用代码逐条验证过，见 §1.2。
2. **元数据过滤是今天最确定有效的功能，但它写错时会静默失效。**
   实测三种场景加过滤后命中率：单文档 65%→**90%**（+25pp）、
   仅表格 80%→**100%**（+20pp）、按章节 55%→**95%**（+40pp），
   **丢失命中全部为 0**。而四种写错方式（拼错键名、拼错文档名、
   文档名带目录、用了默认策略不产生的字段）**全部静默返回 0 条**，
   与"确实没有相关内容"无法区分。现在改成抛异常，见 §2。
3. **阈值挡不住"碰巧词面相近"的无答案问题，而"证据形态"也挡不住。**
   后者是今天试了又撤掉的方案：它误拒 40% 真答案。当前 0.40 只挡住 5 条无答案里的 1 条。
   **这是本次最诚实的负面结论**，见 §3 与 §4。

## 一、TopK 扫描：k ∈ {3, 5, 8, 10}

### 1.1 数据

chunk=500 / overlap=50 / 20 条 gold，索引 532 块，同一份索引跑四个 k：

| k | Recall@k | MRR | 上下文 token | 噪音条数 | 涉及文档数 | 命中前的废 token |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 3 | 55.0% | 0.417 | 804.5 | 2.45 | 2.05 | 72.5 |
| **5** | **65.0%** | **0.439** | **1321.7** | **4.35** | **3.25** | **166.9** |
| 8 | 70.0% | 0.445 | 2109.5 | 7.30 | 4.80 | 242.7 |
| 10 | 75.0% | 0.450 | 2608.8 | 9.25 | 5.60 | 373.0 |

**边际收益**（这才是选 k 的依据）：

| 区间 | Δ召回 | Δtoken | Δ噪音 | 每 100 token 换来的召回 |
| --- | ---: | ---: | ---: | ---: |
| k=3→5 | +10.0pp | +517.2 | +1.9 | **+1.93 pp** |
| k=5→8 | +5.0pp | +787.8 | +3.0 | **+0.63 pp** |
| k=8→10 | +5.0pp | +499.3 | +2.0 | +1.00 pp |

### 1.2 必答题：k=10 相比 k=5，Recall@5 会下降吗

**不会 —— 而且这不是经验，是结构上的不可能。**

`store.search(vector, top_k=10)` 的前 5 条，与 `top_k=5` 返回的，
是同一批（同样的向量、同样的库、同样的排序）。所以 `Recall@5` 在 k=10 下
与 k=5 下**必然相等**。

这条不用推理，脚本直接验了（`topk_scan.check_prefix_invariant`）：

```
必答题的结构前提（大 k 的命中位置必须与小 k 一致）：
  ✓ 成立 —— 所有 k 的前缀命中位置逐条相同
```

**那 k 变大带来的是什么**：只有"原本排在第 6~10 位的答案现在能进 top_k"这一件事
（Recall@k 从 65% 涨到 75%），代价是：

- 上下文 token 从 1321.7 涨到 2608.8（**+97%**）
- 噪音条数从 4.35 涨到 9.25（**+113%**）
- 涉及文档数从 3.25 涨到 5.60（**上下文被稀释**）

所以**选 k 从来不是看召回，是看这三个代价**。答不出这一点，
就会得出"k 越大越好"的结论 —— 而那是把"多给点总没坏处"当成了原则。

### 1.3 为什么是 5（而不是 3 或 8）

**选 5 的理由是拐点，不是最优值。**

- 3→5 是唯一一段"高性价比"区间（1.93 pp/100token）
- 5→8 掉到 0.63 —— 同样的 token 只能换到三分之一的召回
- 8→10 又回到 1.00，但那时基数已经很大（2608 token / 9.25 条噪音）

⚠️ **20 条样本上这个曲线不显著**（见 [retrieval-tuning.md](retrieval-tuning.md) §6：
1 条翻转 = 5pp，McNemar p 全部 = 1.0）。所以 5 不是"被证明最优"，
而是"在拐点上、且维持现状成本最低"：改成 8 要多付 60% 上下文和 68% 噪音，
换来的 5pp 落在置信区间里。

**噪音口径必须说清**（否则数字会被误读）：金标每条只有一个 anchor，
所以 relevance 只有 0/1，`precision@k` 的上界被钉死在 `1/k`、报出来只是 k 的函数。
所以这里报 `k - relevant`（实测噪音条数）与 `distinct_sources`（稀释程度）——
两个都随 k 线性增长，但后者反映"检索在聚焦还是散射"。

**复现**：`uv run python -X utf8 scripts/topk_scan.py`

## 二、元数据过滤：**写错条件不能静默返回空**

### 2.1 问题是什么（实测的四种静默失败）

`VectorStore.search(vector, where={...})` 对"写错的条件"和"真的没有匹配"
返回同一个东西：空列表。实测（532 块）：

| where | 返回条数 | 真实含义 |
| --- | ---: | --- |
| `{}` | 5 | 正常 |
| `{"source": "sse.md"}` | 5 | 正常 |
| `{"source": "不存在的文档.md"}` | **0** | 文档名打错，或该文档确实不在库里 |
| `{"section_path": "x"}`（recursive 下） | **0** | **该字段根本不存在，条件永远不成立** |
| `{"blockk": "table"}` | **0** | **键名拼错了** |
| `{"block": "table"}` | 5 | 正常 |

后三行是灾难：用户以为"这份文档里没有相关内容"，实际是"你查询的字段不存在"。

**其中 `section_path` 那条不是笔误，是真实的接口陷阱**：实测

```
recursive 策略切出 532 块，metadata 键：block / chunk_strategy / code_language
                                    / heading_level / page_chars / splitter
heading   策略切出 520 块，额外有：section_path / heading_title / section_chars …
```

`section_path` **只由 heading 策略写入**，而默认策略是 recursive
（`chunking/factory.DEFAULT_STRATEGY`）。所以在默认配置下，
**任何按章节过滤的调用都会静默返回空**。

### 2.2 解决：检索前校验，三级失败各自说清

新增 `app/rag/filters.py`，`guard_where()` 在检索前做三件事：

| 抛什么 | 什么时候 | 错误信息里有什么 |
| --- | --- | --- |
| `UnknownFilterKey` | 键不在索引里 | 可用键列表 + 拼写候选 |
| `FilterKeyNotPopulated` | 键在但全为空 | **需要哪种切分策略** |
| `UnknownFilterValue` | 值不在该键取值里 | 接近的候选值 |

**为什么不违反"检索段不产生新信息"**：校验读的是**索引时已写下的元数据**，
不重写 query、不做二次摘要。它只把"沉默的失败"变成"响亮的失败"。

**代价**：schema 需要一次 O(n) 扫描（Chroma 实测 532 块 ~20 ms，比一次
`embed_query` 还便宜，但它是 O(n) 的）。所以分成两个入口：

| 入口 | 何时 | 代价 |
| --- | --- | --- |
| `schema_from_store(store)` | 建索引后 / 启动时一次 | O(n) 一次 |
| `guard_where(schema, where)` | 每次检索 | O(#keys)，纯内存 |

`Retriever` 懒算并缓存 schema，索引变更后调 `refresh_filter_schema()`。

### 2.3 三种过滤场景的实测：**加过滤前后命中率**

这一节是任务验收里「测三种场景：**加过滤前后命中率**」的实际数据。
上一轮只证明了"过滤器能缩小结果集"，没测命中率 —— 而那是两件不同的事。

口径：同一条 gold，跑两次（不加过滤 / 加过滤），比 `hit@5`。
**特别记录"救回"与"丢失"两个方向**：只看净变化会漏掉"过滤弄丢了原本能命中的"。

| 场景 | 条目 | 过滤前 | 过滤后 | Δ | 救回 | 丢失 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| **单文档**（`source`） | 20 | 65.0% | **90.0%** | **+25.0pp** | 5 | **0** |
| **仅表格**（`block=table`） | 5 | 80.0% | **100.0%** | **+20.0pp** | 1 | **0** |
| **按章节**（`section_path`） | 20 | 55.0% | **95.0%** | **+40.0pp** | 8 | **0** |

三条都只涨不跌，且**丢失命中全是 0** —— 这是过滤"安全"的直接证据：
它没有把任何一条原本能答对的问题挤出去。

除了命中率，排名也在改善（本来就命中、但排位更靠前）：

| 场景 | 排名上升 | 排名下降 |
| --- | ---: | ---: |
| 单文档 | 3 条 | 0 |
| 仅表格 | 3 条 | 0 |
| 按章节 | 4 条 | 0 |

排名上升直接影响两件事：**MRR**（答案排更前）和**上下文成本**
（排在后面的块会被 `max_context_chars` 挡掉）。

**逐条看，单文档过滤救回的 5 条长这样**：

```
rg-06     未命中 →  top4    ← 过滤救回
rg-08     未命中 →  top1    ← 过滤救回
rg-14     未命中 →  top3    ← 过滤救回
rg-15     未命中 →  top5    ← 过滤救回
rg-19     未命中 →  top3    ← 过滤救回
```

这 5 条的共同点：**答案确实是唯一的那一块，但它被别的文档里语义相近的块挤出了 top5**。
过滤掉别的文档后它立刻浮上来 —— 这说明"未命中"有时不是检索不行，
是**同主题文档互相干扰**。

**三个必须说清的边界**：

1. **「仅表格」只有 5 条**（`eval/table-gold.jsonl`，本轮新造）。
   主 gold 集刻意避开了表格行，用它测 table 过滤会得到 0 条样本 ——
   而"0 条样本"与"过滤没用"是两件完全不同的事。5 条里 1 条 = 20pp。
2. **「按章节」用的是单独建的 heading 索引**，基线也是同一份 heading 索引。
   否则 Δ 里会混进"recursive vs heading"的策略差异，那不是过滤的效果。
   0 条被跳过（所有 gold 的 anchor 都唯一落在某一节里）。
3. **过滤是"用户知道在哪儿"时的手段，不是默认动作。**
   真实使用里用户不给文档名，所以 90% 这个数字**不代表线上命中率** ——
   它代表的是"如果过滤条件正确，上限能到多少"。这正好是 §2.1 那条
   "条件写错会静默返回空"为什么要修的原因：**收益这么高的功能，
   一旦条件写错就静默失效，等于白做。**

### 2.4 「过滤条件写错时会不会静默返回空」

逐个试，同时记录**绕过校验时**与**过校验后**的行为：

| 写错的方式 | 原样查库（旧行为） | 过校验（现在） |
| --- | ---: | --- |
| 键名拼错（`blockk`） | **0 条** | 抛 `UnknownFilterKey` |
| 文档名拼错（不存在的文档） | **0 条** | 抛 `UnknownFilterValue` |
| 文档名带目录（`docs/sse.md`） | **0 条** | 抛 `UnknownFilterValue` |
| recursive 下用 `section_path` | **0 条** | 抛 `UnknownFilterKey` |
| 合法条件（对照） | 5 条 | 通过，5 条 |

**四类写错全部静默返回 0 条**，与"确实没有相关内容"完全无法区分。
其中「文档名带目录」最容易踩：gold 集里写的正是 `docs/sse.md`，
而块的 `source` 只有 `sse.md`（loader 用 `file_path.name`）。

> 这个映射在 `filter_eval.gold_source_to_chunk_source()` 里显式处理，
> 并有测试断言"每条 gold 的 source 都能在语料里找到对应块"。
> **不改成"统一存相对路径"**：`doc_id` 由 source 派生，改了等于全量重建索引。

**新增接口**：`ChromaStore.describe_metadata()` —— 让"怎么取 schema"
留在库内部（Chroma 是一次 `get`，将来 pgvector 可以是一条 `SELECT DISTINCT`）。

**复现**：`uv run python -X utf8 scripts/filter_eval.py`

## 三、阈值粗标：命中 vs 未命中的分数分布

### 3.1 方向先说清：这里是 `score`，不是 `distance`

任务的写法是「`distance > threshold` → 拒答」（距离，越小越像）。
本项目 W4 就把口径统一成了**相似度**（`SearchHit.score`，越大越像，[-1, 1]），
`ChromaStore` 内部做 `1 - distance`。

所以判据是 **`score < threshold` → 拒答**，方向相反。
**改这个方向不会报错，只会让拒答逻辑整体反转** —— 越不像的越会被答。

### 3.2 分布图（20 条有答案 + 5 条"库里没有"）

```
  相似度区间     有答案        无答案
  0.30-0.40     █0            ░1
  0.40-0.45     █0            ░1
  0.45-0.50     █0            ░1
  0.50-0.55     ██2           ░0
  0.55-0.60     ███3          ░1
  0.60-0.70     █████████████13  ░1
  0.70-0.80     ██2           ░0
```

| | 最低 | 最高 |
| --- | ---: | ---: |
| 有答案（20 条） | **0.5412** | 0.7036 |
| 无答案（5 条） | 0.3945 | **0.6577** |

**两组重叠，区间 [0.5412, 0.6577]。** rf-02（React 路由懒加载）拿到 **0.6577**，
比 17/20 条真答案还高 —— 它在 `SETUP.md` 里捞到了讲 Streamlit 前端配置的一节。
"前端 + 配置 + 加载"词面全撞上，bge 认为语义相近。
**语义相近不等于能回答**，这是 embedding 检索的原理性边界。

### 3.3 阈值扫描

| 阈值 | 误拒（该答却拒） | 误放（该拒却答） | 合计错 |
| ---: | ---: | ---: | ---: |
| 0.40（当前默认） | 0/20 | **4/5** | 4 |
| 0.45 | 0/20 | 3/5 | 3 |
| **0.50** | **0/20** | **2/5** | **2** |
| 0.55 | 2/20 | 2/5 | 4 |
| 0.60 | 5/20 | 1/5 | 6 |
| 0.65 | 17/20 | 1/5 | 18 |

**错误最少的是 0.50（0 误拒 + 2 误放）**，但：
**20+5 条样本里 1 条 = 4pp，这个最优点仅供周五 50 条集参考，不当定论。**
而且 0.50 与 0.40 的差别只有 2 条，落在样本噪声内。

**为什么没改默认值**：改成 0.50 会让当前 20 条真答案里最接近阈值的
（rg-17 = 0.5412）只余下 0.04 的安全边际。在不知道真实语料分布的前提下，
**为一个不显著的 2 条改善去削掉真答案的安全边际，是不划算的**。

## 四、拒答策略：一次被撤销的尝试

### 4.1 实现的东西（保留的部分）

`app/rag/refusal.py`：拒答分两种，各带针对性建议，**且都不调模型**。

| 结果 | 判据 | 建议 |
| --- | --- | --- |
| `empty` | 一条没命中 | 确认文档已导入 / 换问法 / 指定文档 |
| `low_score` | top1 < 阈值 | 换问法 / 缩小范围（附实际分数） |
| `answer` | top1 ≥ 阈值 | —— |

分工（这一点踩过坑）：

| 对象 | 内容 | 谁用 |
| --- | --- | --- |
| `Answer.text` | **恒等于 `REFUSAL_TEXT`** | 对话历史、等值断言 |
| `Refusal.text` | `REFUSAL_TEXT` + 建议 | CLI / UI 展示 |
| `Refusal.advice` | **结构化列表** | UI 渲染成按钮 |

试过把建议拼进 `Answer.text`，被 `tests/test_rag_query_timing.py` 的等值断言
当场抓住 —— 而那条断言是对的：拒答文案进对话历史，必须可等值比较。
**建议属于展示层，不该污染数据层字段。**

### 4.2 试了又撤掉的：证据形态判据

想法：无答案的检索应该"更散/更平"，所以加 `weak_evidence` ——
文档数 > 3 或 top1-top2 分差 < 0.02 就拒答。

**实测把它否掉了**：

| 判据 | 应命中（20 条） | 应拒答（5 条） | 可分？ |
| --- | --- | --- | :---: |
| `score_margin` | 0.0012 ~ 0.1208 | 0.0041 ~ 0.0311 | ❌ 完全嵌套 |
| `distinct_sources` | 2 / 3 / 4 份都有 | 2 / 4 份都有 | ❌ 完全重叠 |

真答案里最"平"的那条（rg-14，分差 0.0012）**比所有无答案问题都平**。
按分差拦等于随机拒掉一半真答案。

三条流水线的实际后果（`scripts/refusal_demo.py`）：

| 流水线 | 误拒 | 误放 |
| --- | ---: | ---: |
| **纯阈值（现方案）** | **0/20 (0%)** | 4/5 (80%) |
| 阈值 + 形态（已撤销） | **8/20 (40%)** | 2/5 (40%) |

**用 8 条真答案换 2 条误放，是明确的倒退。** 所以形态判据被删掉了 ——
包括 `RefusalKind.WEAK_EVIDENCE` 枚举与两个判据常量。

`tests/test_refusal.py` 里有一条专门断言**形态判据不许被加回来**（读源码查枚举与常量），
因为那种回归只有跑 25 条标注才能发现。

### 4.3 拒答可演示（任务验收项）

```
$ uv run python -X utf8 scripts/refusal_demo.py

应拒的 5 条：答了就是误放
  rf-01  0.5625   2 份   answer  ← 误放！
  rf-02  0.6577   2 份   answer  ← 误放！
  rf-04  0.3945   —     low_score

拒答文案示例
  ── rf-04（low_score，top1=0.3945）
     知识库中未找到相关内容。

     我没有在你的知识库里找到能回答这个问题的内容，因此不作回答。
     如果这个问题确实应该有答案，请确认相关文档已经导入。

     · 最相关的一条相似度只有 0.394，低于可信阈值 0.40
     · 换个问法，或补充更具体的限定词
     · 缩小范围：先指定文档或章节再问
```

**"不许把低分结果硬塞给模型"是满足的**：两条闸门都在 `generate_answer`
之前判断，拒答路径用 `_NullClient`（`app/cli/ask.py`）——走到模型就会抛
`AssertionError`。测试 `test_stream_refuses_below_threshold` 用 `_ExplodingClient` 证同一件事。

### 4.4 那 4 条误放怎么办（诚实地说：检索层解决不了）

rf-01/02/03/05 都是**语料里碰巧有词面相近的段子**。这不是阈值问题，
换任何阈值都会牺牲真答案（§3.3）。

正确的解法不在检索层，按性价比排序：

1. **知识库补齐** —— 用户问 React，是因为库里没有前端文档。这是数据问题。
2. **生成层的"材料里没有"** —— `generation.ANSWER_PROMPT` 第 3 条已在做。
   模型看到"Streamlit 前端配置"而问题问 React 路由，它是能说"材料没提到"的。
3. **拒答样本扩到 20+ 条** —— 现在 5 条里 1 条 = 20pp，任何判断都不可靠。

**把检索层阈值当成这类问题的解，是拿用户的真答案去换。**

## 五、config 定版

### 5.1 新增 `app/rag/settings.RagConfig`

五个参数 + 上下文预算，**一处定义**：

| 参数 | 默认 | 来源 |
| --- | --- | --- |
| `top_k` | 5 | §1 的边际拐点 |
| `score_threshold` | 0.40 | `embedding/bge.py` 的实测反推 |
| `strategy` | recursive | 与 `chunking.factory.DEFAULT_STRATEGY` 一致（测试守着） |
| `chunk_chars` | 500 | 昨天 token 审计：0.19% 越界 |
| `overlap_chars` | 50 | 昨天网格：0、50、100 分不出差异，维持现状 |
| `max_context_chars` | 6000 | 原有值 |

**为什么值得单独一个文件**：昨天发现 `chunk_size` 同时存在于 `ChunkSize` 与
`ChunkingConfig`，实测同一批 322 段文档**旧链路切 351 块、新链路切 353 块，
逐块文本不同**。改一个参数在两个入口上切出不一样的东西，两边都不报错。

与 `core/config.py` 的分工：那里管进程级基础设施（LLM 凭证/超时/日志），
这里管检索质量参数（会随实验每周变）。**不重复定义**：环境变量统一走 `RAG_` 前缀
（与 `deploy_config.EMBEDDER_ENV` 同一命名空间）。

### 5.2 签名不变（任务的硬要求）

`Retriever.retrieve(query, top_k=None, k=None, where=None)` —— 老调用全部有效：

```python
retrieve(q)  # 读 config
retrieve(q, top_k=8)  # 显式覆盖
retrieve(q, k=8)  # 别名，仍然有效
retrieve(q, k=3, top_k=5)  # 抛（两个不同答案）
```

构造器默认值从 `top_k=DEFAULT_TOP_K` 改成 `top_k=None`（`None` = 读配置）。
`retrieval.DEFAULT_TOP_K` 保留为 `settings.DEFAULT_TOP_K` 的**别名**，
老 import 不会坏。

`tests/test_rag_skeleton.py::test_default_top_k_is_single_sourced` 相应更新：
现在断言"两个构造器的 `top_k` 默认必须是 `None`"，而不是"必须等于 5"——
**不能放宽成"只要等于 5 就行"**，那样有人再写死一个 5 会照样通过，
而那正是这条测试要防的事。

### 5.3 环境变量覆盖

```bash
RAG_TOP_K=8
RAG_SCORE_THRESHOLD=0.5
RAG_STRATEGY=heading
RAG_CHUNK_CHARS=400
RAG_OVERLAP_CHARS=20
RAG_MAX_CONTEXT_CHARS=3000
```

格式错误**直接抛**（`RAG_TOP_K=eigth` → `ValueError`）。
静默回退的表现是"配置改了但没效果"，而那种会让人去查环境变量有没有生效。

## 六、诚实边界

| 边界 | 具体是什么 | 影响 |
| --- | --- | --- |
| **样本量** | 20 条有答案 + 5 条无答案 | 1 条 = 4~5pp。阈值"最优 0.50"与"当前 0.40"差 2 条，落在噪声内 |
| **无答案样本只有 5 条** | 每少一条 = 20pp | "误放率 80%"这个数字本身极不稳定 |
| **`k` 的结论不显著** | 同昨天的网格（McNemar p=1.0） | 5 是拐点，不是被证明的最优 |
| **过滤只在内存库上端到端验过** | Chroma 的 `describe_metadata()` 实现了，但 25 条标注没在 Chroma 上跑 | 过滤的 schema 提取有单测，端到端的命中率数字是内存库的 |
| **`section_path` 只在 heading 下可用** | 默认策略是 recursive | 要用章节过滤，索引必须换策略（要重建） |
| **「仅表格」场景只有 5 条** | 主 gold 集刻意避开表格行，另造了 `eval/table-gold.jsonl` | 1 条 = 20pp。100% 这个数字的置信区间很宽 |
| **过滤命中率不是线上命中率** | 三条场景都假设"用户知道在哪个文档/章节" | 真实提问不给范围。90%/95% 是上限，不是预期值 |
| **拒答的 4 条误放没解决** | 检索层解决不了，见 §4.4 | 需要补语料 / 靠生成层"材料没提到" |
| **阈值方向** | 本项目是 similarity，任务写的是 distance | 判据方向相反，已确认不是 bug |

### 下一步（按性价比排序）

1. **把无答案样本扩到 20+ 条** —— 当前 5 条使所有拒答结论都不可靠。
   这件事的收益高于调任何阈值。
2. **在有答案 + 无答案上各跑 50 条**（周五的 50 条集），
   然后按 ROC 取工作点，而不是看"错误数最少的那一行"。
3. **把过滤命中率搬到 Chroma 上复验** —— 内存库与 Chroma 的
   `where` 语义理论上一致（有单测比对），但 90%/95% 这两个数字
   只在内存库上测过。上线前值得复现一次。
4. **`section_path` 进默认策略** —— 现在默认 recursive 拿不到章节维度，
   而章节过滤是三个场景里提升最大的（+40pp）。要么改默认策略，
   要么让 recursive 也写一个降级版的 `section_path`（如"第一段"）。
5. **把 `chunk_size` 的两份定义合并**（`ChunkSize` 与 `ChunkingConfig`）。
   `RagConfig.chunking_config()` 已经是唯一翻译点，但 `Indexer` 的默认
   splitter 仍然是旧的 `RecursiveSplitter(ChunkSize())` —— 这条是技术债。
