> 测试：`tests/test_embedding.py`（24 条）·
> 数据可复跑：`scripts/bge_prefix_ab.py` · `scripts/embedding_*.json`

## 0. 必答题：为什么必须归一化

### 数学上的那一步

```
余弦相似度  cos(θ) = (a·b) / (|a| × |b|)

L2 归一化后  |a| = |b| = 1
所以          cos(θ) = a·b          ← 余弦 == 内积
```

实测（`tests/test_embedding.py::test_normalized_dot_equals_cosine`）：
两者差的绝对值是 **1.7e-17**，纯浮点噪声。所以生产代码可以用 `dot`
（走矩阵乘法，一条指令）替代手写循环 —— **前提是先归一化**。

### 忘了会发生什么

这不是"精度差一点"，是**排序被向量长度污染**。

构造两个候选（`scripts/embedding_norm_mechanism.json`）：

| 候选 | 模长 | 余弦（真相关度） | 内积 |
| --- | ---: | ---: | ---: |
| A：方向很像查询 | 0.5 | **0.6000** | 0.3000 |
| B：方向只是有点相关 | 9.0 | 0.1498 | **1.3482** |

- 按**内积**排 → **B 胜**（长向量把"相关度低"完全盖住）
- 按**余弦**排 → **A 胜**（方向更接近的那个）

**同一个候选集、同一个模型、只差一次归一化，结论相反。**

### 为什么它是"最易漏"

因为它**不报错**。症状是"命中率莫名其妙地差一点"，于是你会：

```
调 chunk_size → 没变好 → 调 top_k → 没变好 → 换模型 → 没变好
→ 改 prompt → 还是没变好 → 开始怀疑"RAG 是不是不适合这个场景"
```

时间全花在别的变量上。

### 所以本项目的做法：让"忘了"在结构上不可能

| 手段 | 位置 | 效果 |
| --- | --- | --- |
| 归一化写进 `Embedder` **契约** | `embedding/base.py` | 每个实现都必须自己归一化 |
| 相似度**只有一个入口** | `embedding/vector.py::cosine` | 没有"直接算内积"的旁路可走 |
| `cosine` 内部**再除一次模长** | 同上 | 即使输入没归一化，结果仍正确（幂等） |
| 对**每个**实现断言模长 == 1 | `test_every_embedder_returns_normalized_vectors` | 新实现忘了 → 测试立刻红 |

> 第三条看起来多余（两个实现都归一化了），但它是**保险**：
> 第三个 embedder 未必。除一次模长成本 O(d)，bug 成本是几天。

## 1. 向量空间与余弦：手写 vs numpy

要求是"手写一个余弦函数与 numpy 结果对照"。实测（`test_cosine_matches_numpy`）：

| 维度 | 手写 | numpy | 差值 |
| ---: | --- | --- | --- |
| 3 | -0.734976197186852 | -0.734976197186852 | 0 |
| 8 | 0.209221018693187 | 0.209221018693187 | 0 |
| 512 | -0.026343594872384 | -0.026343594872384 | **1.39e-17** |

手写实现**不使用** `np.dot` / `np.linalg.norm`，全部用 Python 内建循环 ——
这样它才是"我理解了公式"的证明，而不是"我调对了库"。
numpy 只作为**对照基准**出现在测试里，生产代码不依赖它。

### 向量空间的一句话解释

文本 → 512 个数。**语义相近的文本，这 512 维向量的方向相近**（长度无关）。
"方向相近"量化为夹角余弦：1 = 同向（几乎同义），0 = 正交（无关），-1 = 反向。

为什么用余弦不用欧氏距离：欧氏距离会被向量长度影响，而长度在 embedding 里
**没有语义含义**（它是模型训练的副产物）。余弦只看向量方向，天然免疫。

## 2. 跑通 bge：512 维、512 token（两个 512 不是一回事）

实测：

```
model.get_embedding_dimension() == 512
model.max_seq_length          == 512
```

| | 含义 | 超了会怎样 |
| --- | --- | --- |
| **维度 512** | 每条向量 512 个数 → 存储成本 | 换维度 = **全量重建索引** |
| **max_seq_length 512 token** | 输入的 token 上限 | **静默截断**，不报错 |

**两个 512 很容易被混成"512 维 512 字"**，但它们完全不相干。

按中文 0.676 tok/字（`scripts/token_result.json` 实测）算，512 token ≈ **757 字**。
本项目切块 500 字 ≈ 350 token，**在安全范围内**。

> ⚠️ **已知损失**：表格块不切（`splitters/recursive.py`），一张 2000 字的大表
> 会被截断到前 757 字。这是有意的取舍（切碎表格的代价更大），
> 但它是**真实的损失**，不是"应该没事"。

### 维度 vs 存储成本

512 维、fp32（4 字节）→ 每条 2 KB：

| 规模 | 向量数 | 512 维 fp32 | 512 维 fp16 | 1536 维 fp32 |
| --- | ---: | ---: | ---: | ---: |
| 50 页 PDF | 150 | 0.29 MB | 0.15 MB | 0.88 MB |
| 5000 页知识库 | 15,000 | **29.3 MB** | 14.6 MB | 87.9 MB |

**结论**：在本项目的量级下（15000 条 = 29 MB），维度带来的存储压力**可以忽略**。
所以选 512 维不是"省空间"，是"够用且延迟低"。
真要省，fp16 砍一半，但那会引入精度损失 —— 29 MB 不值得。

## 3. query 侧指令前缀：加 vs 不加

### 用法（bge-zh v1.5 官方约定）

```
query   = "为这个句子生成表示以用于检索相关文章：" + 原始问题
passage = 原文，不加任何前缀
```

只写在模型 README 里，**代码层不强制**。忘了加不会有任何报错。

所以本项目把它做成**接口级**的事：

| 方法 | 谁调 | 加不加前缀 |
| --- | --- | --- |
| `embed(texts)` | 索引链路（passage） | ❌ |
| `embed_query(queries)` | `Retriever`（query） | ✅（bge）/ ❌（hashing） |

`Retriever` **只调 `embed_query`** —— 让"忘加前缀"在结构上不可能发生。

### 实测：差异有数据

走真实链路（`RagPipeline` + `Retriever.embed_query`），20 段合同语料，
两个查询集各 18 / 14 条（`scripts/bge_prefix_ab.json`）：

| 集合 | 前缀 | hit@1 | hit@3 | MRR |
| --- | --- | ---: | ---: | ---: |
| **easy**（查询词与原文高度重叠） | 不加 | 0.889 | 0.944 | 0.931 |
| easy | **加** | 0.889 | 0.944 | 0.931 |
| **hard**（换说法，几乎不共享关键词） | 不加 | 0.714 | 0.929 | 0.813 |
| hard | **加** | **0.786** | 0.929 | **0.849** |

**hard 集 hit@1 +7.1pp，MRR +0.036；easy 集完全不变。**

逐条变化（hard 集）：

| 查询 | 不加 | 加 | 变化 |
| --- | ---: | ---: | --- |
| 钱什么时候能到账 | 2 | **1** | ✅ 改善 |
| 机器放在哪幢楼 | 2 | **1** | ✅ 改善 |
| 换人做行不行 | 1 | 2 | ❌ 变差 |
| 这个活儿交给谁干 | 19 | 17 | ➖ 都失败 |
| 其余 10 条 | 1 | 1 | — |

### 结论怎么说才诚实

1. **收益集中在 hard 集**：easy 集（字面就能命中）加不加一样 ——
   前缀不改字面匹配能力，它改的是"语义检索的方向性"。
2. **不是普涨**：14 条里 2 条改善、1 条变差、11 条不变。
   **净收益 +1 条（hit@1 从 10/14 到 11/14）**。
3. **样本只有 14 条，这个 +7.1pp 的置信区间很宽**。
   1 条命中/未命中就能让它变成 ±7pp。要下"前缀真的有用"的结论，
   至少得跑到 100 条以上、并且跑多次看区间 —— 见 §6 未验证项。
4. **但加前缀仍然是对的**：它是模型的训练约定，不加等于主动偏离训练分布；
   而且在 hard 集上有明确改善。**成本为零**（多 20 个字符的输入）。

## 4. API embedding vs 本地：三列对比

| 维度 | 本地 bge-small-zh-v1.5 | API（如 text-embedding-3-small） |
| --- | --- | --- |
| **向量维度** | **512**（固定，换模型=重建索引） | 1536（可降到 512/256，但服务端会变） |
| **单条延迟** | **10.5 ms P50 / 11.2 ms P95**（CPU，预热后） | **未能实测** —— 见下方"未验证" |
| **批量吞吐** | batch=1: 171 / 8: 473 / 32: 618 / **64: 719** 条/秒 | **未能实测** |
| **成本** | **0 元/次**（电费）。代价：模型 92 MB + 进程常驻 ~400 MB | 按 token 计费（本项目 5000 页 ≈ 60 万字符 ≈ 89 万 token） |
| **依赖网络** | ❌ 完全离线 | ✅ **必须联网**（还有限流、鉴权、供应商变更） |
| **数据出境** | ❌ 不出本机 | ✅ **全文上传**（索引阶段是全量，比查询敏感得多） |
| **首次开销** | 下载 92 MB + 加载 16 s + import torch 65 s | 无 |
| **上线后变更** | 我们决定，可锁定版本 | 供应商可能悄悄升级模型（**你不会被通知**） |
| **质量** | 好（中文小模型里第一梯队） | 通常更好（尤其多语言、长文本） |
| **可复现性** | 完全可复现（权重在我们手里） | 取决于服务端版本 |

### 离线场景下 API 直接出局

不是因为贵，是因为**链路会直接断**：

```
索引阶段要把全文向量化 → 没有网络 = 索引建不了 = 检索为空 = 生成段拿不到资料
```

所以 `tests/conftest.py` 那条"拔网线 `pytest -q` 必须全绿"的硬规矩，
在 RAG 这一层等价于"**必须有一个不依赖网络的 embedder**"。
这也是 `HashingEmbedder` 存在的理由：不是"凑合用"，是**CI 能跑的前提**。

### 未验证项（必须写清，不能编数字）

**API 侧的延迟与吞吐我没有测到**：本机网关（`http://127.0.0.1:8326/v1`）
对 `/embeddings` 返回 `404 not_found`，四个常见模型名全部 404：

```
text-embedding-3-small   status=404  100ms
bge-small-zh             status=404   20ms
embedding-3              status=404   21ms
text-embedding-ada-002   status=404   31ms
```

所以上表里 API 的"单条延迟 / 批量吞吐"两格写的是**未能实测**，不是"大概多少"。
**编一个"约 100ms"填上去，比留白糟得多** —— 那个数字将来会被引用。

要给这两格填数，需要一个能调 embedding 端点的 key。这是**待办**，不是已完成。

## 5. 本地模型的三项代价（写清，不美化）

### ① 占内存：约 400 MB 常驻

torch + 模型权重 + 工作内存。对一个本来 60 MB 的 FastAPI 服务，
这是 **6 倍**的内存增长。

**换来了什么**：离线可用、零调用成本、权重可复现。
**代价什么时候变贵**：上多副本（每个 worker 一份 400 MB）、
上小内存容器（512 MB 的 pod 装不下）。

缓解：`warmup()` 在启动时加载一次，多 worker 场景考虑独立 embedding 服务。

### ② 首次加载慢：16 秒（+ import torch 65 秒）

```
import sentence-transformers   65 s   ← 首次，含 torch 加载
模型加载                        16 s
首次 encode                     77 ms  ← 图优化
预热后单条 encode               10.5 ms ← 差 7 倍
```

**为什么这是问题**：线上第一个真实请求不该承担这 80 秒。
它会让"服务刚启动时特别慢"变成一个查不出原因的玄学问题 ——
监控里看到的是一个 P99 尖峰，而日志里什么都不异常。

**所以给了独立的预热入口**（`BGEEmbedder.warmup()`），在 `on_startup` 里调一次。
**测试不调**（没必要为测试付 17 秒）。

### ③ 需要预热（不只是"加载"）

加载完模型不等于就绪：第一次 `encode` 还要做图优化与内存分配，
比预热后慢 7 倍（77 ms vs 10.5 ms）。**"加载完"和"就绪"是两件事。**

### ④ 镜像变大

torch CPU 版 + 依赖 ≈ 900 MB（`.venv` 实测 1036 MB）。
本项目镜像曾从 242 → 157 MB 瘦身（见 `docs/weekly/w1.md`），
装 torch 之后这一项**需要重做瘦身账**。

> 现在是把它放进主依赖的：CI 会拉 900 MB，但**没有一个测试需要它**
> （bge 相关测试全部 `skipif(not bge_available())`）。
> 这是个有意的取舍：`uv sync` 之后本地能直接跑 `bge_prefix_ab.py`。
> 如果哪天镜像大小变成硬约束，正确的动作是切成
> `[project.optional-dependencies]` 的 `embedding` 组，而不是删模型。
