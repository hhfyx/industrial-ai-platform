## 必答题：`section_path` 进 metadata 有什么用

题目已经把答案的一半写出来了：**检索时按章节过滤，生成时告诉用户"在第 1.2 节"**。
这里把"为什么只有这一条不可替代"说透，而不是复述。

### 三种策略的差异，逐条检验能不能被参数弥补

| 差异 | 能不能用参数弥补 | 结论 |
| --- | --- | --- |
| 块长、块数 | ✅ 完全能。`chunk_chars` 就是干这个的 | 不算"策略差异" |
| 块尾是否落在标点 | ✅ 能。`DelimiterSplitter` 的合并策略已做到 | 不算"策略优势" |
| 是否在语义断点断开 | ⚠️ 部分能。加大 `overlap` 能缓解，但付冗余成本 | 是"策略差异"，但不是**不可替代** |
| **块属于哪一节** | ❌ **不能** | **唯一不可替代** |

第四行的原因很硬：**层级信息只存在于结构里，切完就销毁。**

递归字符看到的是一串字符，它不知道 `## 1.2` 与 `### 公差` 的父子关系 ——
这不是"参数没调好"，是**输入里就没有这个信号**。事后补也不可能：块已经混在
一起，要恢复"这段属于 1.2 节"只能回头看原文，等于全量重跑。

这与 `design-decisions.md` §5（"page 不能事后补"）是同一个论证结构，
只是把"页码"换成了"章节路径"。

### 具体它能做什么（三条，都要有可验证的落点）

**① 检索时按章节过滤。**

`section_path` 是扁平字符串，直接进 Chroma 的 `where`：

```python
store.search(vector, top_k=5, where={"section_path": "第1章 > 1.2 > 公差"})
```

这不是"精确匹配一个路径"（那太窄），而是**前缀过滤**的原料：
`where` 支持精确值，所以更常见的是把粗粒度章节写进单独的扁平字段
（或反过来：用 `section_path` 做展示，用 `heading_title` 做过滤）。
**当前实现只提供字段，没有做前缀过滤的语法糖** —— 这条要写清，
避免读者以为 Chroma 的 `where` 能做 `startswith`（它不能）。

**② 生成时给出比页码更好的定位。**

| 引用标签 | 用户能不能用 |
| --- | --- |
| `合同.pdf 第 7 页` | 能翻到第 7 页，但不知道那一页在讲什么 |
| `合同.pdf 第 1.2 节 > 公差` | **不用翻页就知道这是哪一部分**，而且能直接跳到目录里的 1.2 |

在长合同、技术规格书这类文档里，章节名比页码有用得多 ——
页码是"排版坐标"，章节才是"读者的坐标"。

**③ 二次切分的每一片都能自报家门。**

一条 3000 字的节被切成 5 块后，第 2~5 块**不再以标题开头**。
不给它们补路径，它们进检索时就是"一段不知道在讲哪一章的文字"。
`heading_keep_path=True` 时每片补 `【第1章 > 1.2 > 公差】` 前缀，
并把 `section_path` 写进 metadata（两处，一处给人看、一处给机器过滤）。

### 反过来说：这条价值什么时候用不上

- **PDF 没有标题** → `heading_fallback="page"`，`section_path` 退化成 `第 N 页`，
  价值等于页码（见下）
- **标题只作装饰**（`第 1 节` / `Part A`）→ 路径里没有主题词，等于没有
- **单层标题的短文档** → 路径只有一段，价值不如页码直观

所以它不是"总是更好"，而是"**在有真标题的文档上不可替代**"。

## 实测打穿的五个错（按发现顺序）

这五个都是**跑样本时当场失效**，不是事后靠人工读出来的。
它们的共同点是：**不报错，只让结果变差**。

### 错 1：把"有 `heading_level`"当成"节的开头"

**症状**：`docs/w4-checklist.md` 切出 **44 块 = 文档段数**，一点没合并。

**根因**：loader 的 `heading_level` 挂在该节的**每一段**上，表示"这一段属于哪一级"，
不是"这一段就是标题"。实测该文件 44 段：

```
idx 0  level=1  block=text     '# W4 开工清单'
idx 1  level=2  block=heading  '## 优先级总览'
idx 2  level=None block=table  '| # | 事项 | …'
idx 3  level=2  block=text     '---'
idx 4  level=3  block=text     '### 为什么必须现在就定'
```

按"有 level 就开新节"分组 → 每段都是节开头 → 等于没分组。

**修法**：判据改成"**标题行**"（`block == "heading"` 或首行是 ATX 标题）。
`level` 只用来筛"够不够深"（`> heading_max_level` 的标题只是上一节的分点）。

### 错 2：遇到表格就切断节

**症状**：`## 优先级总览` 被拆成"标题行 / 表格 / 表格后的 `---`"，
而那个 `---` 成了**无主孤儿块**（它属于哪一节没人知道）。

**修法**：表格**不切断节**。它只是"节内一块特殊内容"，节还在继续。
表格的"整张不切"由产出阶段保证，与"它属于哪一节"是两件事。

### 错 3：纯标题节不合并 → 27 字的块只有标题

**症状**：

```
─── [8] chars=27 ───
## P0-2 · `extract` 延迟同样要处理
```

`## P0-2` 下面紧跟 `### 为什么周报里漏了它`，因为 `heading_max_level=3` 把两层
都当节边界，父标题那一节只剩标题行。

**检索后果很具体**：用户问"P0-2 是什么"，命中的是这 27 字块，模型只能答出标题本身；
真正的 518 字内容在下一块，**没进上下文**。

**修法**：`_merge_orphan_headings` 把"去掉标题行后正文为空"的节**并进下一节**。
这正是判据三（标题与内容是否分离）的正面处理，而且**它可自动判定** ——
验证了周一预判里那个附带判断。

### 错 4：heading 策略让表格跟节合并 → `is_table` 变成 `False`

**症状**：表格的 Markdown 结构还在（`|` 分隔），所以**不会报错**，
但 `metadata["block"]` 来自该节**首段**（是标题或正文，不是表格）。

**后果是链条性的**：`is_table=False` → 下游不标"（表格）" → 引用只剩文件名页码；
表格行与正文混在一块 → 模型无法判断哪部分是可引用的条文。

**修法**：产出时把表格**抽成独立块**，但仍带所在节的 `section_path`。
"属于哪一节"与"是否独立成块"是两件事。

### 错 6：代码块被抽到尾部，丢了 `section_path`

**症状**：`docs/w4-checklist.md` 40 块里 39 块带路径，**唯一缺的是代码块**。

**根因**：照抄 `recursive` 的做法"代码块分流、在尾部追加"。对 recursive 无害
（它本来就没有路径），但 heading 的全部价值就在路径上 —— 丢掉它等于把
heading 降级成 recursive，还多付了结构解析的力气。

对代码块来说路径尤其要紧：`` flags = a | b `` 单看完全不知道自己属于
"二、校验逻辑"这一节。

**修法**：代码块**留在所属节里**，由节产出时按角色拆分（`_emit_with_specials`），
每块继承 `section_path`。

**同一个根因还有一个分支**：早期版本只在"超预算"时才拆表格，于是
"标题 + 100 字正文 + 一张**小**表"这种完全装得下的节被整节合并，
表格的 `is_table` 变成 `False`。修法是"含表格/代码的节**一律**走拆分路径"，
与预算无关。

### 错 5：`split_sentences` 打穿覆盖不变式四次（周一遗留，今天仍未完）

覆盖率一度只有 **72%**（4377/6066 字）。四版修法：

| 版本 | 写法 | 丢了什么 |
| --- | --- | --- |
| 一 | `buffer.strip()` 落袋 | 行尾换行全丢 → Markdown 塌成 `# 标题> 正文` |
| 二 | `strip(" \t")` | `"。"` 之后的 `\n` 成空白新句被丢弃 |
| 三 | 空白片段并入上一句 | **连带丢掉换行前的正文** |
| 四 | 空白不落袋、留在 buffer 里往下带 | 对；但表格行被句末标点切碎（177→176） |
| 五（当前） | 表格行内不收句 | 对，覆盖率 99.8%~99.9% |

**教训**：这类错**只在有 Markdown 结构的文档上暴露**。在纯文本样本上它是一个
看不见的问题，因为纯文本没有"结构可丢"。

## 今天的两个新增产物

### `pdf_headings.py`：字号启发式，且必须能"不被相信"

PDF 没有"标题"这个概念，只能猜。实测本样本非常干净：

| 行 | 字号 | 真实角色 |
| --- | ---: | --- |
| `星辰科技内部资料 · 严格保密` | 8 | 页眉 |
| `第 1 章 · 第 1 页主题` | **15** | **标题**（正文 10） |
| `本节是…验收标准。` | 10 | 正文 |

但它在真实文档上会错（封面、公式、整段大字号、扫描件）。所以产物带两个数：

- `confidence`：命中行 / 候选大字号行的比例 —— 衡量"这个判据在这份文档上稳不稳"
- `ratio`：标题字号 / 正文主字号 —— 衡量"字号确实拉开了差距"

**两个都达标才用**；否则 `load_pdf` **一行 `heading_level` 都不填**，
策略层自动降级为按页切并标 `heading_fallback="page"`。这是任务里
"不可靠就降级为递归，别硬做"的落点。

> `probe.is_trustworthy()` 要求 `confidence >= 0.6` 且 `ratio >= 1.3`。
> 只用其中一条会放过两类坏文档：①字号有差距但几乎没有标题（confidence 低）；
> ②有标题但字号差不足（ratio 低，区分度来自噪声）。

### `boundaries.py`：数字与单位不许切开

"0.05mm 不能拆"这条同时约束**三处**代码：

| 位置 | 切坏的样子 |
| --- | --- |
| 硬切（`_hard_cut`） | `…精度为 0.05m` + `m，重复定位…` |
| 重叠截取（`buffer[-overlap:]`） | 后一块以 `05mm` 开头 |
| 节内二次切 | 复用上面两者 |

如果在每处各写一遍"往前挪"，三处必然漂移。所以判定与挪动只在一处。

实测（`chunk_chars=20, overlap=5`，极端预算）：

```
'设备精度为 ±0.05mm，'      ← 硬切，块尾是完整的 ±0.05mm
'±0.05mm，重复定位 0.02mm。' ← 块首不再是 05mm
```

**已知覆盖不到的两类**（写出来而不是假装没有）：
- `1.2-1.5 倍`（小数区间）会被拆成 `1.2` / `-1.5` —— 语义没被破坏（不是 `1.` / `2-1.5`）
- `HT-2026-001` 这类**编号**只有数字部分被保护（那是"标识符被拆"，属于另一类问题）

## 代码块为什么必须从正文分流

代码的"句子"不是中文句号：

| 错法 | 后果 |
| --- | --- |
| 按 `\n\n` 切 | 空行在函数体内也常见，会把一个函数劈开 |
| 按 `，` / `；` 切 | 直接切在 `f(a, b)` 的参数中间 |
| 去掉缩进 | **Python 的缩进是语法**。丢了缩进的块永远报 `IndentationError` |

第三条最隐蔽：切分器会 `strip()` 每一块，而 `strip()` 恰好吃掉 Python
唯一的结构性信息。所以代码块保留每行原始缩进，只去整块首尾空行。

**切分边界按语言**：Python 认顶格 `def`/`class`/`@`；JS/Go 等认 `function`/`func`/
`class`；**未知语言只在空行处切**（不猜语法，猜错的代价是语法碎片）。

**一个实测的优先级**：`宁可块超预算，也不拆函数`。
`def load(...)` 这种 3 行小函数在 `max_chars=40` 时组本身就超预算 ——
第一版走"按行切"，把函数拆成 3 块。正确顺序是**先判断"这组能否装进一块"**，
只有超过 2 倍预算才降级按行切。

## 半句率：量化代理指标

### 定义

```
半句率 = (块首可疑数 + 块尾可疑数) / (2 × 评估块数)
```

分母是 `2 × 块数`：每块有两个边界，两个都可能错。

### 判据（每条都有反例在铺垫）

| 块首 | 判定 | 为什么 |
| --- | --- | --- |
| 句末标点开头 | 可疑 | 标点属于上一句，出现在块首说明上一块被切在标点之前 |
| 逗号/顿号开头 | 可疑 | 强边界不该以弱标点起头 |
| 半截数字（`05mm`） | 可疑 | 数字被拦腰切 |
| 标题/代码围栏/表格行 | **跳过** | 结构边界天然不以标点起头 |

| 块尾 | 判定 | 为什么 |
| --- | --- | --- |
| `。！？；` | 安全 | 句末 |
| `\n` | 安全 | 段落/表格行结束 |
| 数字或单位 | 可疑 | 数字被切断的最强信号 |
| 逗号 | 可疑 | 强边界不该停在弱标点 |
| 汉字无标点 | 可疑（会误报列表项） | 宁可多报一条让人复核 |

**表格与代码整块跳过**：它们的"边界"不是句子边界，计进去会让指标系统性偏高，
而那个偏高的数字不对应任何真实问题。

### 实测数字（`scripts/chunking_samples.py`，2026-11-17）

| 文档 | 策略 | 块数 | 半句率 |
| --- | --- | ---: | ---: |
| `w4-checklist.md` | recursive | 46 | **7.14%** |
| `w4-checklist.md` | heading | 40 | **6.00%** |
| `w4-checklist.md` | semantic | 49 | **6.45%** |
| `sample20.pdf` | 三种都是 | - | **0.00%** |
| **对照：等长硬切** | — | 31 | **33.87%** |

**最后一行是这个指标存在的理由**：等长硬切 33.87% vs 按标点切 7.14% ——
**差一个量级**。它们是同一份文本、同一个平均块长，光看块长分布完全看不出差别。
W4 的 B2 就是这样发现"LangChain 切出半个词"的。

> heading 的 6.00% 与 recursive 的 7.14% 几乎持平 —— 这不说明 heading 没有优势。
> 它的三条可疑块是：`…延迟是这样的：`（引导句，冒号结尾）、
> `各跑 3 次`（清单项）、`宽松度是否过宽`（清单项）——
> 全是**结构上本来就该那样**的块，而不是被切坏的块。
> 半句率量不出"标题与内容是否分离"（判据三），那才是 heading 拉开差距的地方。

> PDF 上三种策略都是 0.00%，是因为 PDF 每行都以句号结尾（合成样本特性）。
> **这个 0 不代表 PDF 切分没问题** —— 它只说明"标点边界都在"。判据二仍然要人读。

### 它测不出什么（必须写清）

**看见标点，看不见语义。** 一块以 `。` 结尾，也可能正好把一个
"若 A，则 B"拆开（`若甲方未按期付款。` —— 有句号但论述不完整）。
判据二（论述单元是否被拦腰切）永远需要人读。

已知误判三类：列表项（通常不带句号）、整块不以 `|` 结尾的表格、以 `}` 结尾的代码块。
所以**按块类型分组统计**（`measure_by_kind`），混平均等于用一个数描述三件不同的事。

## 一个必须记下来的混淆因素

PDF 的 loader 现在会把标题行拆成独立 `Document`（`block="heading"`）。
后果是：**recursive / semantic 不懂结构，标题与正文各成一块（块数翻倍）；
heading 会重新合并成整节。**

所以 `sample20.pdf` 上"recursive 40 块 vs heading 20 块"这个差异
**部分来自 loader，不全是策略差异**。比较块数时必须记得这条 ——
已写进 `summary.json` 的 `knownConfounds`，不藏在注释里。

为什么不改成"不拆"：不拆的话 heading 拿不到节边界
（给整页打 `heading_level` 等于按页切，而且不会被标成 `page` 降级，
那是一条**假的成功路径** —— 实测踩过）。拆是必须的，混淆要写出来。
