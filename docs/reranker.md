# Reranker：原理、延迟与实测（W6 周三）

> 目标：跑通 Cross-Encoder 精排，**量出它的延迟**，因为那个数字决定周六能用多少候选。
> 代码：`app/rag/bm25/rerank.py`｜命令：`make rerank-probe` / `make rerank-eval`

---

## 〇、一页纸：三个延迟数字（本周最关键的一步）

| 指标 | 值 | 评价 |
| --- | ---: | --- |
| 模型加载（一次性） | **12.3 s** | 不进单次查询延迟，但首句体验会等它 |
| 单对耗时 | **172 ms** | —— |
| batch=32 吞吐（按长度排序） | **1.1 对/秒** | 比 batch=1 的 2.3 对/秒**更慢** |
| **Top20 端到端** | **8.9 s** | **超阈值 4.4 倍** |
| **Top50 端到端** | **16.4 s** | **超阈值 8.2 倍** |

**任务书写的是「单 query 超 2 秒，立刻记下来」** ——
实测 Top20 就已经 8.9 秒，Top50 是 16.4 秒。**这不是超标一点，是超一个量级。**

**直接后果**：周六的候选数**不能**按"Top50 精排"设计。
按 2 秒预算倒推，CPU 上只能精排 **约 4~5 条**（2 秒 ÷ 172 ms/对 ≈ 11 对，
但批量有 padding 损耗，实际约 4~5 条才稳）。那个数字比"5 条"更小 —— 见 §四。

## 一、为什么必须两段式（必答问题 A）

| 结构 | 怎么算 | 可预计算 | 检索成本 | 精度 |
| --- | --- | --- | --- | --- |
| **Bi-Encoder**（现在的 bge-small-zh） | query 与 doc **各自**编码成向量，再算余弦 | ✅ doc 向量可离线算 | O(log n) 毫秒级 | 粗 |
| **Cross-Encoder**（本模块） | query 与 doc **拼接**后过同一个模型 | ❌ 每对都要现算 | 每对 172 ms | 精 |

关键在**注意力**：Cross-Encoder 里 query 与 doc 的 token 在同一段注意力里互相看见，
所以它能判断"这段是否真的回答了这个问题"。
Bi-Encoder 把 doc 压成一个向量时就丢掉了与具体 query 的交互 ——
它只能保证"这个 doc 整体上像这个 query"，做不到"这段对不对得上"。

**这就是两段式的算术理由**：

    全库 1363 块 × 172 ms = 约 234 秒/query      ← 不可用
    检索 top20（毫秒级）+ 精排 20 × 172 ms ≈ 8.9 s  ← 仍然太慢，但至少是个能讨论的量

所以先用 Bi-Encoder 把候选压到几十条，再精排。**第二段之所以"还能接受"，
完全依赖第一段把候选压得足够小。**

## 二、必答问题 B：Cross-Encoder 的分数能不能跨 query 比较

**不能。** 本周实测的直接证据：

| query | top1 分 |
| --- | ---: |
| 各条 query 的最高分 | 0.842 |
| 各条 query 的最低分 | 0.002 |
| **跨度** | **0.840** |

**同一个模型、同一批候选，只是换了 query**，分数就整体平移 0.84。
所以：

- ❌ "分数 > 0.5 就算相关" —— 这条阈值在不同 query 上含义完全不同
- ❌ "这条 0.002 分，所以无关" —— 可能只是这个 query 的分数整体偏低
- ✅ 只能用**同一 query 内部的相对排序**
- ✅ 想设阈值必须先按 query 内归一化（`normalize_within_query`）

> **这是本周第五次遇到"分数尺度"问题**：
> Chroma 的 distance、BM25 的无界分数、加权融合的量纲、RRF 免疫量纲、
> 现在是 Cross-Encoder。每次都指向同一句话：
> **跨分布比较绝对分数，是这类系统里最容易犯且最难发现的错。**

## 三、批量：**按长度排序组 batch 是必需优化，不是讲究**

### 3.1 实测发现：批量越大越慢

第一版按检索顺序切 batch，结果反直觉：

| batch | 按检索顺序 | 按长度排序 | 差距 |
| ---: | ---: | ---: | ---: |
| 1 | 548.7 ms/对 | 430.8 ms/对 | 1.27× |
| 8 | **1021.8** | **482.7** | **2.12×** |
| 16 | **1767.2** | **1010.6** | **1.75×** |
| 32 | **1168.6** | **891.0** | **1.31×** |

**按检索顺序时，batch=8 比 batch=1 慢 1.9 倍。** 这是"批量能提速"这条常识的反例。

### 3.2 原因：padding 浪费 230%

| 项 | 值 |
| --- | ---: |
| 50 条候选的 token 数 | 中位 **113**、最长 **542**、合计 6721 |
| batch=32 分组的**实际 token** | 6721 |
| batch=32 padding 后 | **22174** |
| **浪费** | **230%** |

候选里有一条 542 token 的表格块。按顺序切 batch 时，那一组里
**其余 31 条全要被 padding 到 542** —— 而它们大多只有 113 token。

按长度排序后，长块与长块同组、短块与短块同组，
padding 浪费降到个位数。

### 3.3 为什么排序不会改变结果

每个 (query, doc) 对的打分**互相独立** —— 模型不回传跨样本信息。
排序只影响 batch 的组成，不影响任何一对的分数。
`test_sort_by_length_can_be_disabled_for_ab_compare` 保留了这个开关，
让"这个优化值多少"可以被重新测出来。

> **但即使优化后，batch=32 仍然比 batch=1 慢。**
> 原因是 CPU 上 12 线程的并行开销：单对时一个线程跑满，多对时线程争抢。
> **结论：CPU 上"开批量"收益为负。** 这与 W2 测 embedder 时"batch=64 快 4 倍"
> 的结论相反 —— 因为 embedder 是短文本+小模型，reranker 是长文本+大模型。

## 四、这个延迟对周六意味着什么

### 4.1 候选数必须按延迟倒推

任务要求："如果单 query 超 2 秒，立刻记下来，周六的候选数要按这个倒推"。

| 方案 | 端到端 | 是否可行 |
| --- | ---: | :---: |
| Top50 精排 | 16.4 s | ❌ 超 8 倍 |
| Top20 精排 | 8.9 s | ❌ 超 4 倍 |
| Top5 精排 | 约 2.2 s | ⚠ 刚好在阈值上 |
| Top4 精排 | 约 1.8 s | ✅ |

**所以周六若要把精排放进在线链路，候选数只能取 4~5 条。**

### 4.2 但"只精排 5 条"意义有限

精排的价值来自**在较多候选里重新排序**。只给 5 条，它能挪动的空间很小 ——
而 §五的实测正好印证：**8/10 条题里 gold 根本不在候选内，精排无从发挥。**

### 4.3 三条出路（周六要选一条）

| 出路 | 说明 | 代价 |
| --- | --- | --- |
| **A. 离线/异步精排** | 精排不进在线链路，只在评测与批量任务用 | 线上没有精排收益 |
| **B. 换更小的 reranker** | bge-reranker-base / 更小模型 | 精度下降，需重测 |
| **C. GPU** | 交付环境有 GPU 时换 `device="cuda"` | 本机无法验证，不能写结论 |

**本机是纯 CPU（`torch.cuda.is_available()` = False，torch 2.15.0+cpu），
所以 GPU 的数字今天一个都没有 —— 这一点必须写清楚，不能被当成"GPU 上也是这个数"。**

## 五、小样本验证：10 条 query 的精排效果

| 指标 | 值 |
| --- | --- |
| 变好 | **2 条**（f-05、f-08） |
| 变坏 | **0 条** |
| 没变 | 8 条 |
| MRR | 0.0129 → **0.1167**（+0.1037） |
| 精确命中 top5 | 0/10 → **1/10** |

### 5.1 两条变好的

| id | 精排前 | 精排后 | 说明 |
| --- | ---: | ---: | --- |
| f-05 | #13 | **#1** | 「首字延迟这个指标的口径是怎么定的」→ TTFT 定义块 |
| f-08 | #19 | #6 | 「为什么反复把整篇文档塞回上下文最费钱」 |

f-05 从第 13 名提到第 1 名，是今天最干净的一个正面案例 ——
它证明 Cross-Encoder 确实能判断"这段是否回答了这个问题"，而向量不能。

### 5.2 **8 条"没变"全部是精排救不了的**

这是今天最重要的结构性发现：

| 情况 | 条数 |
| --- | ---: |
| gold 在候选 top20 内，精排后变好 | 2（f-05、f-08） |
| **gold 完全不在候选 top20 内** | **8**（f-30 f-18 f-20 f-07 f-25 f-19 f-22 f-10） |

那 8 条**精排根本没机会**：候选里压根没有正确答案，重排序不可能把它变出来。
所以"没变 8 条"不是"精排没效果"，是**精排无从发挥** —— 这两件事完全不同。

> **精排是"重排序"，不是"召回"。** 它只能在你已经找来的候选里选出更好的，
> 救不了"根本没找到"。这与 §四 的"只精排 5 条意义有限"是同一件事的两面：
> 候选窗口太小救不了召回，窗口太大又扛不住延迟。

## 六、截断策略：影响很小（实测）

用 `max_length=256` 强制截断最长块（542 token → 截到 256），三种策略打分：

| 策略 | 截断对数 | logit | sigmoid |
| --- | ---: | ---: | ---: |
| tail（保留开头） | 1 | −9.510 | 0.000074 |
| head（保留结尾） | 1 | −7.991 | 0.000338 |
| middle（保留中段） | 1 | −8.180 | 0.000280 |

**三种都判"不相关"**，差异在 logit 上（−7.99 ~ −9.51）但 sigmoid 后全部趋 0。
这说明：**对这个块，三种截法都不影响结论**。

### 6.1 但"影响很小"不等于"可以不管"

语料里只有 **3/1404 块超过 512 token**（0.21%），中位块只有 77 token。
所以 `max_length=512` 时**几乎不会触发截断** —— 这也是三种策略差异不明显的原因。

**真正会触发截断的场景**：表格块（最长 1307 字 / 717 token）。
若将来块长调大或语料换成 PDF，这个讨论才重新有意义。
产物里 `truncated_pairs` 字段会记录实际截断数，**每次跑都能看到它是不是 0**。

新写一份 `reranker.md` 会自动被排除，**不需要改任何名单**。
