## 今天必须回答：混淆矩阵里哪两个类最容易混？为什么？

**「功能咨询」→「故障报修」。** 两个版本都是这一对，各混 1 次。

### 为什么是这两类

看 `cl-05` 这条 gold 是「功能咨询」的样本：

> 「按照文档装完 uv 之后 git 还是找不到，命令行里敲 git 没反应。」

模型判成了**故障报修**。理由是可以推出来的：

**「敲 git 没反应」在字面上就是一个"功能不可用"的现象**，
而「故障报修」的正向边界写的是「产品功能不可用、报错、崩溃」—— 完全命中。
但这条实际是"我按文档操作失败了、想问问该怎么办"的**咨询**，
只是它借用了"没反应"这种故障式描述。

**这两类的分界线不在"现象"，在"意图"**：

| | 意图 | 典型句式 |
| --- | --- | --- |
| 故障报修 | 报告一个已经确认的异常，期待被修 | 「一直 502」「崩溃了」「点了没反应」 |
| 功能咨询 | 想知道怎么做/支不支持，期待被告诉 | 「怎么传？」「支持吗？」「该怎么弄？」 |

**模型的失败模式是把"意图"当成"现象"来判。** 而用户写咨询时，
往往先描述现象再提问题 —— 现象在前，意图在后，模型读到前半句就做判断了。

### v2 的「反向边界」为什么没解决它

v2 给「故障报修」加的反向边界是「不包括单纯询问用法」，理论上应该拦住。
实测仍然混了 —— 因为这条文本**不像"单纯询问"**：它包含了"照文档做了还是不行"，
那是一个**失败陈述**，不是疑问句。

> 这条混淆**不是模板措辞能修的**。真正要修的是**输入侧的判定线索**：
> 要么在类别定义里补"凡是带疑问/求助语气的，一律先归咨询"，
> 要么在业务上允许一条工单有主次两个标签。**这不是 A/B 能解决的问题。**

### 另一个只在 v2 出现的混淆

fresh 重跑里 v2 还多了一次「投诉建议」→「功能咨询」（`cl-07`：建议把 degraded 改必填）。
v2 的反向边界让「功能咨询」更宽了（加了"怎么测算"），把"提建议"也吸了过来。
**这是 v2 改动带来的副作用，不是随机噪声** —— 详见 §2.3。

### 一个重要口径修正

初版汇总只把**成功条目**纳入统计，于是"一半请求超时"的版本会显示得分 1.0。
修正后**同时给两个口径**：

- `mean_score`（仅成功）—— 能看出"回答质量"
- `mean_score_all`（失败记 0）—— 能看出"真实可用性"

**结论一律用全量口径。** 下面表格里两个都给，但判断以全量为准。

> 这个修正直接救了摘要那一组：只算成功时 A=B=1.0（"无差异"），
> 按全量是 **A=0.90 / B=0.30**（v2 明显更差）。见 §2.4。

**结论：无显著差异（−3.7pp < 阈值 20pp），但方向对 v2 不利，且成本更高。**

### 为什么 v2 没赢（归因到具体改动）

v1 → v2 改了三处，逐条看它们的实际效果：

| 改动 | 预期收益 | 实测结果 |
| --- | --- | --- |
| ① 不确定时"必须有引用" | 引用更完整、可核查 | **部分实现**：确实更多条目给了引用，但 `qa-08` 这类"上下文完全无关"的题仍然 0 引用（正确） |
| ② 加"第一步：先判断信息够不够" | 更稳定地识别信息缺口 | **有收益但被抵消**：`qa-10` 从 0.67 提升到 1.0，`qa-03` 更明确地列出了缺失信息 |
| ③ 答案里禁止"根据[2]"这类填充语 | 正文更干净 | **有效**：v2 正文确实没再把编号写进句子 |

**那为什么总分反而降了？** 看逐条：

| 条目 | v1 | v2 | 变化 |
| --- | ---: | ---: | --- |
| qa-02 | 1.00 | **0.33** | ⬇ 掉了 3 个要点里的 2 个 |
| qa-05 | 1.00 | **0.50** | ⬇ |
| qa-08 | 0.00 | 0.00 | 都没答对（这条本身 gold 有问题，见 §5） |

**真正的元凶是"两步走"结构。** v2 要求先输出 `缺少信息`、再输出 `答案`，
模型在有把握回答的题上也倾向于先"列缺什么"，然后把答案写短 ——
`qa-02`（prompt 精简 30% 只省 11.8%）本来 v1 完整答出 3 个要点，
v2 只答了"成本结构决定优化上限"，**把"输入占 39%、30%×39%≈11.8%"这些关键数字丢了**。

> **归因结论：v2 的"先判断再答"结构在"其实能答"的题上引起了过度保守，
> 答案被压缩，要点覆盖下降。这不是 prompt 写得差，是"分步"这个结构本身有代价。**

### 这条结论稳不稳

−3.7pp 在 10 条样本上是 **0.37 条**，**远低于噪声门槛**。
换一次运行可能变成 +3pp 或 −7pp。**不能据此宣称 v2 更差** ——
只能宣称"v2 没有带来可测的改善，且更贵"。

### 为什么 v2 没赢（归因到具体改动）

v2 改了三处：

| 改动 | 预期收益 | 实测结果 |
| --- | --- | --- |
| ① 加"反向边界"（这一类不包括什么） | 减少边界混淆 | **部分有效**：`cl-02`（问成本测算）从「其他」纠正为「功能咨询」 |
| ② 加固定判定顺序（先排除再定位） | 减少运行间抖动 | 看不出明显效果（两次 fresh 结果一致） |
| ③ 加 `排除类别` 字段 | 混淆可诊断 | **有效**：能看到模型排除了哪些类 |

**但 ① 有副作用**：把「功能咨询」的正向边界从"询问功能怎么用、是否支持某能力"
扩成了"怎么测算"，结果把 `cl-07`（**建议把 degraded 改必填**）也吸过去了 ——
v1 判对（投诉建议），v2 判错（功能咨询）。

> **归因结论：v2 的分都用在"让边界更清晰"上，但扩大「功能咨询」边界时
> 越界吃掉了「投诉建议」。这是一处改善换一处退步，净效果为零，而 token 涨了 49%。**

### 这条结论稳不稳

**很稳。** 两个版本各跑了一次 fresh，混淆矩阵的结构完全一致（都是"功能咨询↔故障报修"主线）。
唯一的不同是 v2 多一条"投诉建议→功能咨询"，且这条能够归因到具体改动（扩大边界）。
所以"v2 在分类上没有收益、只有成本"这个判断是可信的。

### 为什么 v2 赢这么多（**必须诚实归因**）

**不是 v2 模板写得好，是 v1 的字段契约根本对不上。**

v1 的 schema 把槽位写死成 `主体` / `时间`（按工单场景设计：
"联系人 + 发生时间"）。而这批输入来自技术文档，字段是「版本 / 路径 / 要求 / 算法名」。
**模型不是不会抽，是没有槽位可填。**

证据在 v1 的输出里很清楚：

```json
{"主体": "uv", "时间": null, "缺失字段": ["时间"], "置信度": 0.6}
```

gold 要的是 `{"主体":"uv", "版本":"0.13.1", "路径":"%USERPROFILE%\\.local\\bin\\uv.exe"}` ——
**`版本` 和 `路径` 这两个键在 v1 的 schema 里不存在**，所以只能是 0 分。

而且 v1 为此付出了巨大代价：按每条成功归一，v1 的 `completion token` 是 **2327**，v2 只有 **690**。

> 注意这里用的是**每条成功**口径。总量口径（23270 vs 6900）里，v1 那个 23270
> 还包含了一条**失败样本**在修复轮里的巨额消耗 —— 用它做分母会让
> `token_ratio` 显示 1.01（"两版一样贵"），而按成功归一实际是 **0.418**（v2 省 58%）。
> 这是**方向对我有利**的污染，一开始没发现，复盘时才查出来。
原因是被迫在修复轮里来回试 —— 它知道信息在，"时间"填不对，就一直改。

> **归因结论：+63pp 的差距绝大部分来自"v2 支持任意字段清单"这一项契约改动，
> 而不是"提示词写得更好"。** v1 的槽位是业务错误的，v2 修的是这个错误。
>
> 换句话说：**如果 v1 的槽位恰好匹配任务（比如工单场景），这个差距会大幅缩小。**
> 所以这条结论**不能推广成"v2 模板更优"**。

### v2 自身仍有不足

逐条看 v2 的 3 处失分（都不是编造，是"提炼"倾向）：

| 条目 | 问题 |
| --- | --- |
| ex-01 | 路径给 `.local/bin`，gold 是完整 `%USERPROFILE%\\.local\\bin\\uv.exe` —— **抽短了** |
| ex-03 | 问题描述被简化，少了"但 usage 正常"这半句 |
| ex-05 | 值带上了句末标点，与 gold 差一个"。" |
| ex-09 | 手段给"结果缓存命中、小模型分流"（两个都列），gold 只要一个 |

**规律：v2 倾向于"提炼"而不是"照抄"。** 模板里已写"值保持原文原始写法"，
但实测仍有压缩/合并倾向。这是 v2 模板的**真实待改项**，不是模型能力问题。

| 指标 | v1 | v2 | 说明 |
| --- | ---: | ---: | --- |
| 平均得分（仅成功） | 1.000 | 1.000 | 两者成功的条目都是满分 |
| **平均得分（全量）** | **0.900** | **0.300** | Δ = **−0.600** |
| 整条全对率 | 1.00 | 1.00 | （仅对成功的） |
| 成功条数 | **9/10** | **3/10** | |
| prompt token 合计 | 4517 | **1732** | ⚠️ 总量，**被失败率污染** |
| completion token 合计 | 35613 | **16334** | ⚠️ 同上 |
| 成本合计（元） | 0.2939 | **0.1341** | ⚠️ 同上 |
| **每条成功 prompt token** | **502** | **577** | ✅ 正确口径 |
| **每条成功 completion token** | **3957** | **5445** | ✅ 正确口径 |
| **每条成功成本（元）** | **0.03266** | **0.04471** | ✅ **v2 贵 37%** |
| 平均延迟 | 22942 ms | 25366 ms | |
| P95 延迟 | **55098 ms** | 28823 ms | |
| **失败条数** | **1** | **7** | ← 决定性的 |

> ⚠️ **这一行的成本必须按成功样本归一读。**
> 调用的 `token_ratio: 0.38` / `total_cost_cny: 0.294 → 0.134` 字面看是"v2 省 62%"，
> 但失败的 7 条请求**不产出 token** —— "总成本更低"只等于"有 7 次没跑起来"。
> 按每条成功归一后：**v1 = 0.03266 元、v2 = 0.04471 元，v2 实际贵 37%。**
> 详见 [weekly/w3.md §3.1](weekly/w3.md)。

### 为什么 v2 更差：7 条超时

失败的 7 条全部是 `APITimeoutError: Request timed out`。

- v1 只有 1 条超时
- v2 有 7 条超时（70% 失败率）

**v2 的"两步走"结构（先输出 `分段要点` 再合并）让模型产生了更长的思维链**，
单条耗时推到 18–25 秒，撞上了 `timeout=30s` 的上限。

> **归因结论：v2 的"先提炼要点、再合并摘要"这个结构，
> 在本网关（默认 `reasoning=high`）上把延迟推过了超时线。
> 得分从 0.90 掉到 0.30，全部来自超时，不是摘要质量。**

### 这一组的数据要特别小心读

| 读法 | 结果 | 对不对 |
| --- | --- | --- |
| 只看成功的条目 | A=1.0, B=1.0 → "无差异" | ❌ **完全误导**：B 有 70% 请求根本不返回 |
| 看全量口径 | A=0.90, B=0.30 | ✅ 这才反映可用性 |

**这正是我在统计口径上踩过的坑**：初版汇总把失败条目剔除，摘要那组赫然显示"1.0 vs 1.0"。
如果我当时直接写进报告，结论会是"两版无差异、v2 还便宜 54%" —— **完全反了**。

修正后重算（`scripts/rebuild_summary.py`，不重花 API 钱），真相是 v2 差了 60pp。

### 但 v2 也不是一无是处

**按每条成功归一**看 v2 的成本结构（这才是正确口径）：

| | v1（9 条成功） | v2（3 条成功） |
| --- | ---: | ---: |
| 每条成功 prompt token | 502 | **577** |
| 每条成功 completion token | 3957 | **5445** |
| 每条成功成本 | 0.03266 元 | **0.04471 元（贵 37%）** |

**注意：v2 单条其实更贵，不是更便宜。**

原因：v2 的 `prompt token` 总数看着少（1732 vs 4517），但那是因为它只成功了 3 条 ——
**3 条的 prompt 加起来当然比 9 条少。** 单条算下来 v2 的 prompt 反而更多（577 vs 502），
completion 也多 38%。

**那 v2 到底有什么可取之处？** 只剩一个：它的**结构把"提炼"显式化了**
（先出 `分段要点` 再合并），这在延迟不是瓶颈的环境里可能有用 ——
但本网关 `reasoning=high` 让它撞超时线，**这个优点在这里无法兑现**。

> **所以"v2 在成本上更优"这句话是错的 —— 那是我用被污染的口径读出来的。**
> 修正后的事实是：**v2 更慢、更贵、成功率只有 30%。**
> 唯一还没被证伪的是"关掉推理后它是否更好"，而那个变量本周没测。

## 5. 汇总与结论

| 类别 | v1 得分 | v2 得分 | Δ | 结论 | 主要归因 |
| --- | ---: | ---: | ---: | --- | --- |
| qa | 0.572 | 0.535 | −0.037 | 无显著差异（v2 略差） | "两步走"结构导致答案被压缩 |
| classify | 0.800 | 0.800 | 0.000 | 打平，每条成功成本 +22% | 扩大「功能咨询」边界，吃掉「投诉建议」 |
| **extract** | 0.133 | **0.767** | **+0.633** | **v2 大胜** | **契约从"固定槽位"改为"任意字段"** |
| summarize | 0.900 | 0.300 | −0.600 | **v2 惨败** | "两步走"导致 70% 超时；**单条成本还贵 37%** |

> 成本一律用**每条成功**口径。总量口径在两臂失败率不同时**不可比** ——
> 这是本次复盘修正的第三处统计口径问题（见 [weekly/w3.md §3.1](weekly/w3.md)）。

**净结果：3 类没赢（其中 1 类惨败），1 类因契约修复大胜。**

### 三个可以推广的规律

**① "分步结构"在推理模型上不一定划算。**
qa 和 summarize 的 v2 都采用了"先一步、再一步"，结果：
- qa：答案被压缩，要点覆盖下降
- summarize：思维链变长，撞超时

因为本网关默认 `reasoning=high`，**模型自己已经在分步思考了**；
再在提示里加一层"第一步/第二步"，等于让它把同一件事说两遍（
这和周一 [prompt-patterns.md](prompt-patterns.md) 的结论一致：推理模型不该再加 CoT 提示）。

**② 契约不匹配的代价远大于提示词优劣。**
extract 的 +63pp 几乎全部来自"字段槽位能对上"，不是措辞。
**改契约 > 改提示词**，两者不是一个量级的杠杆。

**③ accuracy 是骗人的，混淆矩阵不是。**
分类两类都 0.80，看起来"还行"。混淆矩阵一摆出来：唯一的错误全在"意图 vs 现象"这一个分界上，
而 v2 在别处还多错一条。**只看 accuracy 会得出"两版一样好"的错误结论。**

### 数据集自身的问题（必须说）

| 问题 | 影响 |
| --- | --- |
| `qa-08`（问 degraded 字段用途）gold 要 3 个要点，实际答案只能覆盖 1-2 个 | 两版都 0 分，**是 gold 标得太细**，不是模型错 |
| extract 10 条 gold 里**没有任何 `None` 字段** | 幻觉率指标**没被真正检验过**（都是 0/26、0/22） |
| 每类只有 10 条 | 1 条 = 10pp，**任何 <20pp 的差异都不该当结论** |

## 5.5 成本口径修正（复盘时发现的第三处统计错误）

**这一节是本报告最重要的方法学部分，比任何一行的得分都值得读。**

### 问题

初版 `summary.json` 用**总量**算成本比值：

```json
"token_ratio": 0.38,           // B 的总 prompt token / A 的总 prompt token
"total_cost_cny": 0.294 → 0.134
```

字面读是"v2 省 62% 的钱"。**但失败的请求不产出 token** ——
摘要 v2 有 7 条超时，它们的成本是 0（在 token 侧），不是"省下来的"。

### 按每条成功归一后的真相

| | 总成本 | 成功条数 | **每条成功成本** | 与"总量口径"的结论 |
| --- | ---: | ---: | ---: | --- |
| v1 | 0.293938 | 9 | **0.03266 元** | 基准 |
| v2 | 0.134136 | 3 | **0.04471 元** | **贵 37%**（不是省 62%） |

token 同理：

| | 总量口径 | 每条成功口径 |
| --- | --- | --- |
| prompt token 比值 B/A | 0.383（"省 62%"） | **1.135（多 13%）** |
| completion token 比值 B/A | — | **1.376（多 38%）** |

### 另外三类的复核（有的被我漏了）

| 类别 | 两臂失败率 | 总量口径 token 比 | **按成功归一** | 差异 |
| --- | --- | ---: | ---: | --- |
| qa | 0/10 vs 0/10 | 1.206 | 1.115 | 小（无污染，两臂都全成功） |
| classify | 0/10 vs 0/10 | 1.495 | **1.350** | 中 |
| extract | 1/10 vs 0/10 | **1.006** | **0.418** | **大 —— 方向对我有利** |

> **`extract` 那行才是真正该警惕的**：总量口径显示 1.006（"两版一样贵"），
> 按成功归一显示 0.418（v2 省 58%）。因为 v1 那条**失败样本**在修复轮里
> 烧了巨额 completion token，把 v1 的总分母撑大了。
>
> **我一开始只发现了"对我不利的污染"（摘要），没发现"对我有利的污染"（抽取）。**
> 这说明污染是**双向**的，不能靠"这个数字看着不对"来发现 ——
> 只能靠**把口径固定写死在代码里**。

### 修法（已落到代码）

1. `ab_test.summarize()` 同时输出 `total_*`（标注污染风险）与 `*_per_ok`（主口径）
2. `delta` 里只用 `cost_ratio_per_ok` / `token_ratio_per_ok`；
   原来的 `token_ratio` 改名为 `token_ratio_total_uncontrolled`（明确标"未控失败率"）
3. 两臂失败率不同时，控制台主动打印警告
4. `rebuild_summary.py` 从已有 CSV 重算 —— **改统计口径不重花 API 的钱**

### 两条可推广的规则

> **① 任何"总量"指标，只要分母与成功样本数相关，就必须按成功样本归一。**
> 成本、token、延迟都属此类。
>
> **② 对比两版前先看两臂失败率差。差得多，所有总量指标都不可信。**

## 6. 三类结论的适用边界

### 6.1 哪些是稳健的

| 结论 | 为什么稳健 |
| --- | --- |
| **extract v2 大幅优于 v1** | 差距 63pp，远超噪声；且能指到具体契约改动；v1 的输法（每条成功仍要 2327 completion token，v2 只要 690）是结构性证据 |
| **summarize v2 显著更差** | 失败率 70% vs 10%，是二值事件不是程度差异；错误类型明确（超时）；**且按成功归一后单条也贵 37%** |
| **「功能咨询 ↔ 故障报修」是主要混淆** | 两版独立运行都指向同一处；且能归因到"意图 vs 现象"的语义边界 |
| **v2 的 token 成本普遍更高**（除 summarize） | prompt token +21%、+49%，这是确定性的事实，不受随机性影响 |

### 6.2 哪些可能是噪声

| 结论 | 风险 |
| --- | --- |
| **qa "v2 略差"** | −3.7pp = 0.37 条。两次 fresh 跑出来是 −5.0pp 和 −3.7pp，本身在漂。**只能信"没有可测改善"** |
| **classify 的 Δ=0.00** | 恰好 0 也可能是运气；两次运行混淆矩阵结构一致，所以"结构上无改善"可信，但"完全相等"不可信 |
| **v2 的「排除类别」字段有用** | 这只是可解释性收益，**没被量化**（它不参与判定，不影响得分） |

### 6.3 这套结论不能推广到哪

**① 不能推广到"v2 模板体系更优"。**
extract 大胜是因为"契约能对上"，qa/summarize 都输了。
**正确的读法是"每类模板该不该升 v2，要单独看"**，不是"统一升 v2"。

**② 不能推广到非推理模型。**
本次模型默认 `reasoning=high`，所以"分步结构有害"的结论成立。
换成 `reasoning=off` 或非推理模型，"先给要点再合并"可能是**有效**的
（因为模型自己不会分步）。**这个变量没测。**

**③ 不能推广到别的工作负载。**
10 条样本、单一模型、单一网关。**换网关/换模型，`max_tokens` 与 `timeout` 的合适值都变了** ——
而摘要那组失败恰恰是这两个参数撞线导致的。

**④ 摘要的"超时失败"不是模板质量问题。**
它是**参数配置问题**（`timeout=30s` 太短）。如果调到 60s，v2 的 7 条超时可能全部变成成功。
**所以"v2 摘要模板差"这个结论只在当前 timeout 配置下成立。**

## 7. 回填定版：只有 extract 升级为 v1.1

### 7.1 定版决策

| 类别 | 决策 | 理由 |
| --- | --- | --- |
| **extract** | **v2 → 升级为 v1.1** | +63pp，远超阈值，且赢因是契约修复（可复现） |
| qa | **不升** | −3.7pp，无收益且更贵；升级没道理 |
| classify | **不升** | 打平但 token +49%、成本 +22%；为同等效果多付钱 |
| summarize | **不升** | −60pp（70% 超时）；升了就是把可用性砸掉 |

**为什么只有一类升**：如果"输了也升"，A/B 就变成流程仪式，不是决策依据。

### 7.2 回填后的版本状态

```
app/prompts/extract/
├── v1.jinja2          旧版（保留，历史数据可复现）
├── v1.1.jinja2        新版（原 v2 的内容，升为正式的 v1 修订版）
├── v2.jinja2          中间试验版（保留供对比，不再是推荐版本）
├── schema.py          v1 的输出模型
├── v1_1_schema.py     v1.1 的输出模型
└── v2_schema.py       v2 的输出模型
```

**为什么保留 v1 和 v2**：历史实验数据都是在那些版本口径下测的，
删掉就等于让周一至周六的结论无法复现。这是周四就立的规矩（新版本不改旧版本）。

### 7.3 回填确认（防止"挑出来的"偏差）

升级后**重跑一次** v1 vs v1.1，确认新版本真的赢了 —— 而不是"当初那次运气好"：

| 对比 | A (v1) | B | Δ |
| --- | ---: | ---: | ---: |
| 原实验 v1 vs v2 | 0.1333 | 0.7667 | **+0.6334** |
| **回填确认 v1 vs v1.1** | **0.1333** | **0.7667** | **+0.6334** |

**两次独立运行，得分与差值完全一致，v1 的得分也完全一致（0.1333）。**

这说明：
1. **v1.1 确实是胜出版本**（不是挑出来的那次偏差）
2. 抽取任务在这个模型上**相当稳定**（两次运行没出现漂移）

> 这也是本周唯一做了"升级后复跑"确认的类别。
> qa/classify/summarize 没有升级，所以不需要做。

### 7.4 一个实现细节：`v1.1` 的点号

`v1.1` 这个版本名踩了两个 Python 坑：

| 问题 | 现象 | 修法 |
| --- | --- | --- |
| 排序错 | `v1.1` 被排到 `v1` 前面（字符串序） | 排序键折成元组 `(1, 0)` / `(1, 1)` / `(2, 0)` |
| 模块名非法 | `import_module("app.prompts.extract.v1.1_schema")` 被解析成"从 `v1` 子模块导入 `1_schema`" | 模块名里的点换成下划线：`v1_1_schema.py` |

这两处都改在 `loader.py`（`_version_sort_key` / `_schema_module_name`），
并写进了注释 —— **下次加 `v1.2` 不会再踩一遍。**

## 8. 附带发现：`max_tokens` 被第二次打爆

今天跑摘要 A/B 时，第一轮 **10 条全挂**，报：

```
ValueError: 模型返回 content=None（可能被 max_tokens 截断或推理占满）
```

诊断（同一条 `sm-03`）：

| max_tokens | finish | completion | reasoning 字符 | content |
| --- | --- | --- | --- | --- |
| 4096 | `length` | 4096（打满） | 9405 | **None** |
| 8192 | `stop` | 4485 | 12007 | 正常 |

**这是同一天里第二次踩同一个坑**（周四从 2048 抬到 4096，今天又从 4096 抬到 8192）。

已修：`DEFAULT_MAX_TOKENS` **4096 → 8192**，并把两次实测都写进了源码注释。

> **规律：`max_tokens` 要按"最重的那个任务"定，不是按典型任务。**
> 摘要的思维链最长，分类/抽取的短输出用 8192 不会被用掉（模型到 `stop` 就停），
> 所以统一给足即可 —— `max_tokens` 是上限不是预留，**调大不额外花钱**。

### 但抬到 8192 之后，失败类型从"截断"变成了"超时"

这是第二次失败暴露的新问题：**思维链变长 → 单条耗时 18–25 秒 → 撞 `timeout=30s`**。

所以真正的根因不是 `max_tokens` 不够，而是 **`reasoning=high` 让摘要任务本来就很贵**。
`max_tokens` 和 `timeout` 只是两个先撞到的墙。

## 9. 局限
