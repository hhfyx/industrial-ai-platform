## 一、BM25 是什么（必答问题 A：为什么它抓术语）

    score(D, Q) = Σ IDF(q) · [ tf(q,D)·(k1+1) ] / [ tf(q,D) + k1·(1 - b + b·|D|/avgdl) ]

| 成分 | 解决什么 | 本项目取值 |
| --- | --- | --- |
| **TF 饱和** `k1` | 一个词出现 100 次 ≠ 相关 100 倍 | 1.5 |
| **IDF 加权** | 「所有块都有的词」不该有票 | Lucene 变体 |
| **长度归一** `b` | 长块天然更容易撞词 | 0.75 |

**IDF 就是它补向量的地方。** 向量把整句话压成 512 维稠密向量，所有词被糊在一起 ——
`INVALID_INPUT` 这种低频标识符在向量里几乎没有存在感，主导项是它旁边的「错误码」。
BM25 相反：`INVALID_INPUT` 在全库 1592 块里只出现在 7 块，DF 小 → IDF 大 → 那 7 块直接顶上来。

实测证据（本周跑出来的）：

    Q: INVALID_INPUT 返回什么错误码
    BM25 top1: score=9.22 [api-spec.md] ### 3.1 错误码表
    top3 那块正文里就有 `INVALID_INPUT 422`

同一个 query，向量侧 gold 排第 5 名之后（`f-30` 向量未命中、BM25 也未命中 top5，
但 BM25 的 top3 里已经出现了**含 `INVALID_INPUT 422` 的块**）。

## 二、中文分词：三个必须一起做对的事

| 事 | 做错会怎样 |
| --- | --- |
| 自定义词典 | `同轴光` → `同轴` + `光`，与「同轴」块、「光」块都虚假匹配 |
| 停用词 | 「的/了/是」占 TF 与长度归一，稀释有区分度的词 |
| **两侧同一分词器** | 最隐蔽：两侧都"能跑"，只是分数系统性偏低 |

### 2.1 词典实测效果

    jieba.lcut("同轴光镜头的景深与光通量")  → ['同轴', '光', '镜头', '的', '景深', '与', '光通量']
    tokenize("同轴光镜头的景深与光通量")     → ('同轴光', '镜头', '景深', '光通量')

### 2.2 型号/标识符保护（实测出来的，不是预防性设计）

第一版只做了词典，然后发现：

    INVALID_INPUT   → ('invalid', 'input')      ← 两个都极常见，IDF 低
    bge-small-zh    → ('bge', 'small', 'zh')    ← 拆成三个无意义词
    4.2             → ('4', '.', '2')           ← '.' 还被当标点丢掉

**型号匹配是 BM25 相对向量检索唯一的结构性优势，在这里切碎等于把优势自己拆掉。**
所以加了一层 `_IDENTIFIER` 区间扫描：以字母开头的 ASCII 串允许中间夹 `_ - .`，
小数/版本号整体保留。现在：

    INVALID_INPUT   → ('invalid_input')
    bge-small-zh    → ('bge-small-zh')
    v0.4.1          → ('v0.4.1')

> **占位符替换的做法试过、不可行**：占位符本身含数字，jieba 会把数字单独切出来，
> `INVALID_INPUT` 变成 `('0', '错误码')`。区间扫描没有这个副作用。

### 2.3 一个自己踩的坑：词典文件里混进了说明段落

词典末尾追加了一段 `>` 引用块作说明，结果 `load_userdict` 把**整段话当成一个词**
灌进词典树，而自检又把整段话当成"必须整体切出的词"，报出一堆莫名其妙的失败。

修法：**词典文件只允许注释（`#`）和词**，说明写进注释。
`tests/test_bm25.py::test_dict_file_contains_words_only` 守着。

## 三、索引与持久化

`make build-bm25` → `data/bm25/index.pkl`（已在 `.gitignore` 里，派生数据不入库）。

| 存什么 | 为什么必须存 |
| --- | --- |
| token 流 | 重切要 700 ms；**且词典改了就会切出不同的流** |
| 块 id 列表 | 检索结果要能回查 `Chunk` |
| `k1`/`b`/avgdl | 参数变了分数就变，不能从默认值猜 |
| **分词器指纹** | 词典一改，它就是"该重建了"的信号 |

**不 pickle `BM25Okapi` 对象本身**：它内部缓存 `idf`/`doc_freqs`，那是从 corpus 派生的
中间状态。派生状态存文件等于把缓存当源码 —— 版本升级或参数微调时旧值会悄悄生效。

复用判据是**分词器 + 块集合 + 参数三项都比**，不是"文件存在"。
掠过 vs 重建的实测：

| 情况 | 耗时 |
| --- | --- |
| 指纹相同（复用） | 0 ms |
| `--force` 重建 | **794 ms**（分词 + pickle 落盘 444.8 KB） |

## 四、对照实验：**W5 的标签被推翻了**

### 4.1 两个范围，两个数

| 范围 | 向量 | BM25 | 差异 |
| --- | ---: | ---: | ---: |
| 全量 40 条可答 | 16 | 14 | **10** |
| 子集 10 条（W5「术语未命中」） | 0 | 2 | 2 |

**只跑子集会得出"差异 2 条"，那是采样偏差** —— 子集里 8 条是两路都不中的硬骨头，
而 BM25 真正赢下的 `f-09`/`f-27` 根本不在子集里。验收要的 ≥5 条按全量算，是 10 条。

全量明细：

    两边都中  10  f-11 f-13 f-14 f-15 f-21 f-23 f-24 f-28 m-07 m-10
    仅 BM25 中 4  f-09 f-18 f-20 f-27
    仅向量中   6  f-06 f-12 f-16 f-17 f-29 m-09
    都不中    20

### 4.2 为什么说「术语未命中」标签不成立

按判据逐条查了 W5 判为「② 术语/同义词未命中」的 **15 条**：

| 情况 | 条数 |
| --- | ---: |
| 含稀有标识符（`INVALID_INPUT` 那类，BM25 该强） | **0** |
| 与 gold 块只共享「模型/输入/上限/文档」这类高频普通词 | 12 |
| **连一个公共 token 都没有** | 3 |

**0 条真有字面锚点。** 也就是说这 15 条不是"术语没对上"，
把它们归到"加个更好的分词器"是**两个方向都不对症**。按分布它们该被拆成两类：

| 实际情况 | 该谁修 |
| --- | --- |
| 只共享普通词 → BM25 有分但压不住长块 | 长块降权 / 表格路由（W5 已记的猜想） |
| 零公共 token → 同义/换述 | **向量侧**（更强模型 / 查询改写） |

这解释了为什么 BM25 只赢 4 条而不是预期的十几条：**它该赢的地方，这批题里根本没有。**

| 题型 | 谁强 | 为什么 | 本周证据 |
| --- | --- | --- | --- |
| 型号/编号/错误码 | **BM25** | 稀有 token，IDF 高 | `INVALID_INPUT` 顶到含 `422` 的块 |

### 5.1 「工业文档里 BM25 收益应更大」—— 这个预期**本周无法验证**

任务原文的预期是对的，但**当前语料是技术文档，不是工业文档**：

    景深 0 次    光通量 0 次    背光 0 次    同轴 0 次    公差 4 次

词典里那 4 个工业术语进了词典，但语料里一次都没出现。
所以"BM25 在工业文档上收益更大"这句话，**今天没有任何数据支持**，
只能等真的工业语料进来（或 W7 出题时换成工业文档）再验。

**已验证的部分**：型号/标识符这条路（`INVALID_INPUT`、`bge-small-zh`、`v0.4.1`）
在本项目语料上确实强，而它们与"工业型号编码"是同一类信号。

## 六、停用词与剩下的坑

### 6.1 停用词表（68 个）

中文虚词（的/了/是/在/和…）+ 英文虚词（the/a/of…）。

**故意保留「不」「没」「有」**：它们在本项目里有语义 ——
「不返回 usage」「没有 413」「有缓存时强制离线」。
jieba 自带停用词表会剔掉这些，所以没用它。判据是"在这批文档里 IDF 是否趋 0"，不是"通用中文里是否常见"。

### 6.2 剩下的坑（按危险程度）

| 坑 | 状态 |
| --- | --- |
| **query 与索引用不同分词器** | 已由 `describe()` 指纹 + 测试守住；`make bm25-audit` 每次逐块比对 token 流 |
| 词典改了忘重建 | 指纹变了 → `build-bm25` 会自动重切；`bm25-audit` 会报 |
| 空 token 流产生 `nan` | 已用 `__empty__` 占位 |
| 表头/表格长块 | **未处理**。`b=0.75` 是 Lucene 默认，长块降权留给周六 |
| 分数不可与向量混比 | BM25 分数无界（实测 0~30），`BM25Hit` 独立类型，RRF 未做 |

### 6.3 为什么没做 RRF 融合

三条理由，第一条是纪律：

1. **先对照再融合**。不做对照就不知道"融合后涨 2pp"是 BM25 救了 3 条还是带偏了 1 条 ——
   与 W5 三策略对比同一条纪律。
2. `SearchHit.score` 的契约是余弦相似度，BM25 分数无界。硬塞进同一类型会让"分数"
   在库里有两个含义，那是 W4 踩过的坑（distance vs 相似度）。
3. RRF 只需要名次，`BM25Hit` 已经把 `rank` 算好了 —— 以后要加，不用改检索层。

## 七、代价列（供 W6 周六的收益核算）

| 指标 | 值 | 说明 |
| --- | ---: | --- |
| BM25 重建 | **794 ms** | 1592 块，含分词与落盘 |
| 其中分词 | 约 700 ms | 改词典后这笔钱会变 |
| 落盘体积 | **444.8 KB** | 约为原语料 259 KB 的 1.7 倍 |
| 检索耗时 | < 5 ms | `BM25Okapi.get_scores` 是纯 numpy |

BM25 慢 6.5 倍 —— 但两者**都不是每次请求都跑**，索引是一次性成本。
