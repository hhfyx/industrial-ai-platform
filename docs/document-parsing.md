## 0. 必答题：页码为什么会错位？

**因为你在切分之后才去猜页码。**

这是本格唯一一个"写错了会在 demo 现场被点穿"的问题，所以放在最前面。

### 错位是怎么发生的

错误链路的每一步都看起来合理，合起来必然错：

```
① 全篇抽成一坨文本            ← 丢掉页边界，只剩一串字符
② 按字数切（500 字一块）      ← 此时已经没有任何"哪块属于哪页"的信息
③ 事后把块"对回"页码          ← 只能靠猜
```

第 ③ 步的"猜"只有两种写法，两种都会错：

| 猜法 | 为什么错 |
| --- | --- |
| **按"平均每页多少字"折算** | 页密度根本不均匀。第 1 页是封面（3 个字），第 7 页是密集表格（2000 字）；平均 1200 字/页的假设一进来就崩 |
| **按顺序累加**（第 1 块到第 2 块 = 第 1 页） | 只要有任何一页的字符数不整除块长，误差就累积。50 页之后可以偏出好几页 |

更隐蔽的是：**页眉页脚被剔除过**。每页实际字符数被人为削掉一截（页眉 14 字 + 页码 14 字），
折算基准整体漂移，而你在第 ③ 步用的是"原始字数"还是"清洗后字数"？
用哪个都错 —— 因为真实的页边界信息**在第 ① 步就已经被销毁了**。

### 正确做法：解析阶段就落到每个段落上，切分只继承

```
① pypdf 逐页抽            → 每页一个 Document，page 在结构里就是真的
② 跨页拼接时记 span       → 一段横跨 p1/p2 → pages=(1,2)
③ 切分只 copy 不推断      → Chunk.pages 直接从 Document 继承
```

代码里的三处落点，缺一个就断：

| 位置 | 做的事 | 测试 |
| --- | --- | --- |
| `loaders/pdf.py` | 逐页调用 `page.extract_text()`，`page` 从 1 开始写进 `Document` | `test_pdf_page_numbers_are_sequential_and_correct` |
| `loaders/pdf.py` ⑤ | 跨页拼接后 `span_of[index]` 记上两页 | `test_pdf_crosspage_paragraph_remembers_both_pages` |
| `splitters/recursive.py` | `inherited_pages = doc.pages or (doc.page,)`，**不做任何推断** | `test_chunk_page_is_carried_through_splitting` |

**为什么跨页那段要 `pages=(1,2)` 而不只是 `page=1`**：
用户点进 p1 找不到那句的后半截，点进 p2 又找不到前半截。
"起始页"是半个真话，而半个真话在 demo 现场比完全没页码更容易被点穿。

> **这条认知的延伸**：`page` 之所以在 W4 周一的 `schema.py` 里就被定死，
> 就是为了今天 —— 结构里没有位置放页码时，解析器再准也存不下来。

## 1. 三个 loader 的产出对齐表

三种格式的结构差异极大，但**下游只认一套结构**。这是"统一"的全部含义。

| 维度 | PDF | DOCX | Markdown |
| --- | --- | --- | --- |
| 切块依据 | **页**（pypdf 逐页） | **段落**（一段一条） | **标题**（`#` 分节） |
| `page` | 真实页码 1..N | `None`（Word 没存页） | `None` |
| `pages` | `(7,)` 或跨页 `(6,7)` | `()` | `()` |
| `block="text"` | 正文段 | 非标题段落 | 无标题的正文块 |
| `block="heading"` | —（PDF 无样式信息） | `Heading N` / `标题 N` / `Title` | `#` 开头且**整块只有标题** |
| `block="table"` | pdfplumber 抽 → Markdown | `python-docx` 表 → Markdown | 连续的 `|` 行 → 原样 |
| 表格样式 | `\| a \| b \|` + `\| --- \|` | 同左 | 同左 |
| 额外 metadata | `page_chars` | `heading_level` | `heading_level` |

**表格格式三处必须完全相同**，理由很实际：各 loader 自己发明格式，最终一定有一处漏改，
到那时"为什么 PDF 的表格能答、DOCX 的答不了"要查半天。
`test_all_loaders_mark_tables_the_same_way` 守的就是这条。

### 实测（`tests/fixtures/` 里的样本，可复跑）

| fixture | Documents | 其中表格 | 跨页段落 | warnings |
| --- | ---: | ---: | ---: | --- |
| `sample50.pdf`（50 页，带页眉） | 50 | 0 | 0 | 0 |
| `sample_table.pdf`（1 页 + 网格表） | 2 | 1 | 0 | 0 |
| `sample_crosspage.pdf`（3 页，句子切在页边界） | 3 | 0 | **2** | 0 |
| `sample_short.pdf`（单页 26 字） | 1 | 0 | 0 | 0（**不是**扫描件） |
| `sample_no_text.pdf`（3 页纯图形） | 0 | 0 | 0 | 2（空页 + 需 OCR） |
| `empty.docx` | 0 | 0 | 0 | 1 |

## 2. 表格：为什么单独成块，且必须从文字流里摘掉

### 问题

pypdf 抽表格是**按阅读顺序铺平**的。实测同一张 3×3 表：

```
pypdf:        里程碑 / 时间 / 金额 / 一期交付 / 2026-11-30 / 38400.00 / …
pdfplumber:   里程碑 时间 金额 / 一期交付 2026-11-30 38400.00 / …
```

行列关系彻底丢失。而"这张表的第三列是什么"是合同问答里最常见的问题。

### 做法

1. **pdfplumber 抽表格** → 转 Markdown（带 `| --- |` 分隔行）
2. **从 pypdf 的文字流里摘掉**那段表格文字
3. 表格作为**独立 Document**（`block="table"`），切分器**不切它**

第 2 步是最容易漏的：不摘的话，同一份内容会进库两次 ——
一次是铺平的文字垃圾，一次是结构化表格。检索时两条都命中，
上下文里出现两份"看起来一样但格式不同"的资料，模型可能引用错版本。

摘除用的是**多重集相等**匹配：找到一段连续的行，其内容多重集恰好等于该表格的全部
非空单元格。不用"行内容在单元格集合里就删"——那会误删正文（正文里出现"金额"很正常）。
摘不干净时**保留文字流**（宁可重复也不丢内容）并记 warning：
重复难看，丢内容是数据损坏。

### 实测（1 页表）

| | 耗时 |
| --- | ---: |
| pypdf 抽全文（50 页） | 82.9 ms |
| pdfplumber `find_tables` 全文（50 页） | 164.2 ms |
| 单页 `find_tables`（无表格的页） | 3.3 ms |

**只 open 一次**：`pdfplumber.open()` 会把整份文档的对象树读进来，按页 open 会让
50 页文档 open 50 次。`extract_all_tables` 因此一次读完。

### 表格为什么禁止切分

一张表被切开之后，"第三列是什么"就再也答不出来了 —— 切碎的表格不是"信息少一半"，
而是"变成一堆无法还原的数字"。所以 `RecursiveSplitter` 对 `is_table` 直接整张一块，
哪怕超预算。

超预算的代价是具体的：embedding 请求变贵、可能被模型截断。
但比起"切碎"仍然是更小的代价。**这是有意的取舍，不是疏忽。**

## 3. 扫描件：为什么"没文字"必须和"空页"分开

看起来是一件事，处理方式完全不同：

| 情况 | 该做什么 | 用户该看到什么 |
| --- | --- | --- |
| 空白页 | 跳过，什么都不做 | 不需要知道 |
| **扫描页**（有图像无文本层） | **打 warning** | "第 3、7 页可能需要 OCR" |

判据分两档（`SCAN_PAGE_CHARS = 20`）：

| 判据 | 触发 | warning |
| --- | --- | --- |
| 清洗后 **0 字符** | 空页 / 整页扫描 | "有 N 页没有可提取文本（扫描件或空白页）" |
| **0 < 字符 < 20** | **文本层残缺的部分扫描** | "有 N 页可提取字符少于 20（疑似扫描页，可能需要 OCR）" |

第二档比第一档更危险：那页**有内容**，看起来正常，只是信息大量缺失。
不打 warning，用户永远不知道那页的 90% 查不到。

判据取 20 是因为：正常 A4 正文一页最少也有几百字；能抽出 20 字以下的，
通常只有"页码 + 页眉"被剔除后的残渣，或一个孤立图注。
**必须双向验证**：`test_short_but_normal_pdf_is_not_flagged` 断言
`sample_short.pdf`（26 字，正常文档）**不**触发扫描告警 ——
判据若写成"少于 100 字就算扫描"，短通知、短合同全会被误报。

## 4. 清洗：四种噪声，四种判据，混在一起必然出错

`app/rag/loaders/clean.py` 的每一条规则都对应一种**特定**的噪声模式。
这不是拆分癖，是踩过的坑：

| 噪声 | 判据 | 用错判据的后果 |
| --- | --- | --- |
| 页眉 页脚 | **频率**：首/末行在 ≥60% 的页上重复 | — |
| 页码行 | **形态**：`第 3 页` / `- 3 -` / `Page 3 of 50` | 把它丢进频率计数器 → 每页都不同 → 永远删不掉 |
| 断行 | **上下文**：上行无句末标点 + 下行是续行特征 | — |
| 多余空白 | 纯正则 | — |

**页码行必须用形态匹配**：它每页都不同，频率统计永远看不见它。
**页眉必须用频率匹配**：正文里恰好长得像 `第 3 页` 的引用会被形态正则误删。

### 不许过度清洗：一条可被测试断言的红线

> 清洗后的正文，必须是清洗前正文的**字符子序列**（去掉空白后逐字比对）。

理由不是洁癖：前端引用里给的是原文摘录，**用户会拿去 PDF 里搜**。
清洗只要动了一个字（换词、改标点、调顺序），用户就搜不到 ——
那一刻他不是在怀疑代码，是在怀疑整份报告。

`test_cleaning_never_rewrites_body_text` 守这条。唯一的例外：
- **整行被判为噪声**（页眉/页脚/页码）→ 那是"去掉不该在的东西"
- **表格块** → 我们是重写成 Markdown 的，天然不是原文字序列；
  对表格的要求换成"所有非空单元格都能在原文里找到"

一旦有人往里加"顺手把某个词换掉"的逻辑，这条测试立刻红。

### 断行合并的两个反例（都是实测出来的）

**反例一：标题被当成"没说完"。**

`第 1 章 · 第 1 页主题` 结尾没有标点 → 被判"没说完" → 正文粘上来：

```
第 1 章 · 第 1 页主题本节是第 1 页的正文，讨论第 1 项交付物的验收标准。
```

这看起来**像排版，不像 bug**，最容易留在库里。修法是加一条"上一段本身是标题就不拼"。

**反例二：跨页时把新章节接到上一句屁股后面。**

页末没标点非常常见，但下一页很可能是 `第 6 条 违约责任`。
接上去会造出一句**原文里根本不存在的句子**，而且读起来通顺 —— 比乱码更难发现。

所以 `can_join` 有四条前置条件，缺一不可：

```
1. 上一段没说完（无句末标点）
2. 上一段本身不是标题
3. 下一段不以"标题样"开头（第 N 章/条/附件/1.2/一、/#）
4. 下一段首字符是续行特征（小写/汉字/逗号…）
```

中文拼接**不加空格**（加了会让用户搜不到原文），英文之间补一个
（`Machine` + `Learning` 粘成新词同样是数据损坏）。

├── clean.py        ★ 新增：四类清洗 + 可回溯不变量（从 pdf.py 抽出来）

| 文件 | 改了什么 | 为什么 |

## 6. 明确未做 / 未验证

| 项 | 状态 | 说明 |
| --- | --- | --- |
| OCR | ❌ | 扫描页只**识别并告警**，不做 OCR。要做得接 tesseract/PaddleOCR |
| DOCX 页码 | ❌ 不可能 | Word 文件里没有页信息，硬编就是撒谎 |
| PDF 标题层级 | ❌ | PDF 没有语义样式，只有字号/坐标。推断字号要做，但那是另一格 |
| 多栏排版 | ❌ | pypdf 按内容流顺序抽，双栏 PDF 会串行。要做得用坐标重排 |
| 表格跨页 | ❌ | 一张表跨两页会被抽成两张表，目前不做合并 |
| 表格嵌套合并单元格 | 部分 | pdfplumber 给的是已合并的网格；docx 的合并单元格会产生重复文本 |
| **真实业务文档** | ❌ 未验证 | 所有样本都是脚本生成的合成文档。**页密度、页眉形态、扫描件比例都与真实文档不同**，上真实文档前必须重跑一遍 |
