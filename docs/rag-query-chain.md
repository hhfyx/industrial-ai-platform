## 0. 必答题：`chunk_overlap` 到底解决什么问题

**防止关键信息正好被切在边界上断开。**

具体场景：一条"若甲方未按期付款，则乙方有权暂停服务"的条件句被切在第 200 字处。
前半块只有"若甲方未按期付款"，后半块只有"则乙方有权暂停服务"。
检索命中前半块时，模型看到的是一条**只有条件、没有后果**的残缺规则 ——
它可能说"合同没规定后果"，也可能自己编一个。

重叠 50 字让后半块的开头仍然含"若甲方未按期付款"。

### 代价（三条，都要认）

| 代价 | 表现 | 实测 |
| --- | --- | --- |
| **索引冗余** | 同样的文字被存两次、算两次向量 | 冗余率 **9.4%**（2128 字 → 2328 字） |
| **chunk 数变多** | 同样的文档切出更多块 | 与冗余率同比例 |
| **更容易命中重复内容** | 相邻块共享一段文字，top_k 里可能同时出现 A 和 A 的尾巴 | 分数接近时才会发生 |

第三条最隐蔽：**不报错**，只是让上下文窗口被重复内容占掉。

> **50 该不该留，现在没有数据支持任何一个取值。** 50 只是"半句话的量级"这个直觉。
> W5 要用数据回答 —— 在那之前它就是个未经检验的默认值，**不是"调好的参数"**。

## 1. 中文切分：为什么不用 LangChain 的 `RecursiveCharacterTextSplitter`

任务点名了它，所以我把两者在**同一份中文语料**上跑对比。

### 实测：LangChain 切出「半个词」

2128 字中文合同，`chunk_size=500, chunk_overlap=50`，
`separators=["\n\n","\n","。","！","？","，",""]`：

| | 块数 | 每块结尾字符 | 全落在句末标点？ | 冗余率 |
| --- | ---: | --- | :---: | ---: |
| LangChain | 5 | `程` `款` `准` `划` `。` | ❌ **4/5 是半个词** | 7.9% |
| 本项目 | 5 | `。` `。` `。` `。` `。` | ✅ **5/5** | 9.4% |

LangChain 切出了 `…支付合同价**程**`、`…验收标**准**`、`…付款计**划**`。

**不是配置问题**。它的策略是"先按分隔符切成小片，再按字符长度往回填满
`chunk_size`"—— 填满那一步会**切割原子片**，不看截断点落在哪。
`keep_separator` 只影响分隔符归属，不影响"是否切割"：

```
keep_separator=True   -> ['第一条。第二条', '。第三条。第四条']    ← 在词中间断
keep_separator='end'  -> ['第一条。第二条。', '第三条。第四条。']  ← 仍是 8 字硬切
```

要改这个行为得覆写私有方法，而 `_split_text_with_regex` 在 1.1.3 里已经是私有的
（实测 `AttributeError`）—— **依赖一个会变的私有实现，比维护 60 行自己的合并逻辑更贵**。

本项目只合并**完整原子片**，装不下就开新块。代价是块略短（实测平均 470/500），
换来"每块读起来是完整句子"。

### 中文分隔符必须自己配

LangChain 的默认 `separators` 是 `["\n\n", "\n", " ", ""]` —— **全英文**。
用它切中文，等于只在空格处断，而中文段落几乎没有空格：

> 实测：304 字的中文段落用默认分隔符切，**一块都不切**，整篇挤成一块。
> 直到 2128 字时才因为超过 `chunk_size` 被迫硬切。

本项目的优先级表（顺序错了不报错，只会让边界变差）：

```
段落 \n\n  →  换行 \n  →  句末 。！？；  →  逗号 ，  →  硬切
```

`。` 必须排在 `，` 前面 —— 反了就会优先在逗号处断，块尾变成半句话。

## 2. metadata 继承：`page` 一旦丢了就补不回来

切分的核心职责不只是"切"，还有**把出处原样传下去**。四件事：

| 字段 | 来源 | 为什么必须是它 |
| --- | --- | --- |
| `source` | `Document.source` 原样 | 引用要显示文件名 |
| `page` | `Document.page` 原样 | **起始页**，引用显示 `p7` |
| `pages` | `Document.pages` 原样 | **覆盖范围**，跨页段落的 `(6,7)` 要传下去 |
| `doc_id` | 由 `source` 派生（10 位短哈希） | 按文档删除/过滤；**不来自 Document** —— loader 没填也一定有值 |

**同一页切出的多个 chunk 共享同一个 `page`** —— 它们确实来自同一页。
"这一块覆盖了哪几页"要看 `pages`，不是 `page`。

**跨页段落**：`Document(pages=(6,7))` 切出的每一块 `pages` 都是 `(6,7)`。
只记 `page=6` 是"半个真话"：用户点进 p6 找不到后半截，点进 p7 又找不到前半截 ——
这正是 demo 现场最容易被点穿的地方。

测试逐字段核对（`test_every_chunk_inherits_its_group_fields`），不是"抽查有值就算过"。

## 3. 完整链路

```
问题 → 检索 top_k=5 → 拼上下文（带 [1][2] 编号）→ 调模型
     → 解析答案里的 [n] → 映射回 source+page → 输出答案 + 引用列表
```

### CLI

```powershell
python -m app.cli.ask "违约金怎么算" --docs 合同.pdf --embedder bge-small-zh --debug
```

| 输出层次 | 用途 |
| --- | --- |
| 默认 | 答案 + 引用列表 |
| `--debug` | 加检索到的每一块（分数 / 来源 / 页码 / 正文前 60 字） |
| `--json` | 结构化输出（含 `scores` / `refused` / `invalid_refs` / `retrieved`） |

`--debug` 刻意做厚：**"为什么答错了"这个问题的 90% 答案在检索结果里**，
不在模型输出里。

### 实测（`scripts/rag_e2e_demo.py`，用假 client）

| 场景 | 结果 |
| --- | --- |
| 正常问答 | 检索排序 `[1]p2 [2]p1 [3]p3`，答案引用 `[1]` → 映射回 **合同.pdf 第 2 页** ✓ |
| 引用约束 | prompt 里含「只允许引用给定编号」且枚举了 `[1][2][3]` ✓ |
| 模型编编号 | 答案 `[2]` + `[9]` → 有效 `[2]`，**无效 `[9]` 被记录** ✓ |
| 空库 | 拒答，`refused=True`，**未调模型** ✓ |
| 低分 | 0.0386 < 0.99 → 拒答，**未调模型** ✓ |

**为什么用假 client**：本机网关对 chat 端点返回
`502 {'message': '未配置凭据，请先登录'}`。而真实答案的内容**不是这条链路的验收标准** ——
验收标准是四件结构性的事（编号进了上下文、约束进了 prompt、编号能映射回出处、拒答不调模型），
这四件用假 client 就能验，而且**可复现**。拿真模型验收链路，等于把
"链路对不对"和"模型答得好不好"混在一起。

## 4. 引用约束：三层，缺一层就漏

| 层 | 做法 | 防的是什么 |
| --- | --- | --- |
| **prompt** | 明确"每个事实句后用 [n] 标注"+"**只允许引用给定编号**"+"枚举当前可用编号" | 只说"请标注引用"不够 —— 模型会自己发明编号 |
| **解析** | 正则抽 `[n]`，支持 `[1][2]` / `[1,2]` / `[1-3]` | 模型把编号写进正文，而结构化字段可能空着 |
| **校验** | `n` 必须是给定编号的子集；越界的进 `invalid_refs` | 越界编号说明模型在编，**不能静默丢弃** |

### 越界编号为什么必须可见

三种处理方式的后果：

| 方式 | 后果 |
| --- | --- |
| 静默丢弃 | 答案里留一个 `[9]` 悬空，前端显示断链或"来源不明" |
| 抛异常 | 一次越界就整次问答失败，代价过高（答案主体可能有用） |
| **保留正文 + 标记无效 + 记录警告** | 用户看到答案，也知道哪条依据无效 |

选第三种，`Answer.invalid_refs` 记录，CLI 额外打一行 stderr 警告。

**"看起来正常但有编造成分"是最危险的输出**，必须让它可见。

### 为什么以正文里的编号为准，而不是结构化字段

W3 的 `qa/v2.jinja2` 有结构化的 `引用编号: list[int]` 字段。但 RAG 场景里
模型经常把编号写进正文而字段空着 —— 两者不一致时以哪个为准？

**以正文为准**。理由是"用户看到的是正文"：如果正文说 `[1]` 而引用列表说 `[2]`，
那引用列表就是在骗人。

## 5. 拒答：阈值必须挂在 embedder 上

### 双重闸门，都在模型之前

| 闸门 | 判据 | 位置理由 |
| --- | --- | --- |
| 空结果 | `chunks` 为空 | 让模型对着空上下文回答，它唯一能做的就是编 |
| 分数过低 | 最高分 < 阈值 | 库里只有"字面碰巧相似"的垃圾时，模型会拿它当依据硬答 |

**拒答是代码的决定，不是模型的**：`REFUSAL_TEXT` 是固定字符串。
让模型自己说"我不知道"不可靠 —— 它倾向于尽力回答。

话术要引导正确的下一步：

> 知识库中未找到相关内容。
> 我没有在你的知识库里找到能回答这个问题的内容，因此不作回答。
> 如果这个问题确实应该有答案，请确认相关文档已经导入。

"资料中没有提到"听起来像"模型看过但没找到"，而实际是**我们的检索没找到** ——
用户该做的是"检查文档有没有导入"，不是"再问一遍试试"。

### 一个真实的坑：全局阈值把正确命中的答案拒了

我先写了全局 `DEFAULT_MIN_SCORE = 0.35`。结果 `test_rag_skeleton.py` 里两条
用 `HashingEmbedder` 的端到端测试挂了：正确命中的答案（分数 **0.247**）
被误判成"未找到"并拒答。

**不是测试写错了，是阈值不该是全局常量。** 量化（`scripts/embedding_score_probe.py`，
4 条相关 + 4 条无关）：

| embedder | 相关（min~max） | 无关（min~max） | 可分？ |
| --- | --- | --- | :---: |
| **bge-small-zh** | 0.578~0.676 | 0.253~0.367 | ✅ 空隙 0.367→0.578 |
| hashing(64) | 0.148~0.478 | **-0.098~0.149** | ❌ **重叠** |
| hashing(256) | 0.088~0.484 | **0.000~0.148** | ❌ **重叠** |

hashing 的"相关最低 0.148" ≤ "无关最高 0.149" —— **完全重叠**。
任何单一阈值都会同时误杀真答案和放过无关内容。

所以阈值搬到了 `Embedder.recommended_min_score`：

| embedder | 值 | 理由 |
| --- | ---: | --- |
| `bge-small-zh` | **0.40** | 空隙中点 0.472，往下取 —— **宁可少拒不误拒** |
| `hashing` | **0.0** | 分布无可分界线，**诚实关掉闸门** |

**为什么往下取而不是取中点**：误拒真答案（用户看到"知识库没有"而其实有）
比放过一条弱相关（模型还有机会说"材料不足"）更伤。这个不对称是有意的。

### 阈值不负责提高准确率

周四的 10 条验收里：

- 命中者的**最低分**是 **0.466**
- 未命中的两条最高分是 **0.5087** 和 **0.6514**

**未命中的分比命中者的最低分还高。** 分数**不能区分命中与未命中**。

所以阈值只有一个作用：**挡住"库里完全无关"的情况**（随机方向的期望是 0）。
把它当"质量旋钮"去调，越调越糟 —— 调到 0.5 会开始误拒好答案，而坏答案照样进来。
