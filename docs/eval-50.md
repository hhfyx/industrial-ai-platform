## 〇、一句话

50 条（30 事实 + 10 多跳 + 10 拒答）已就位，
`python -X utf8 scripts/tasks.py eval-retrieval` 一条命令出指标。

**基线（chunk=500 / overlap=50 / top_k=5 / 阈值 0.40）**：

> ⚠️ **这个 32.5% 不是「现在的水平」** —— 它是**锚点修复后、旧语料上的第一个干净基线**。
> 当前基线是 **40.0%**（1365 块）。
>
> **三个 Recall@5（32.5% / 37.5% / 40.0%）的谱系对照表见
> [retrieval-tuning-final.md](retrieval-tuning-final.md) §〇·二** ——
> 引用任何 Recall@5 之前先看那张表，否则会把参数演进的不同阶段误读成矛盾。
>
> 一句话区分：**Recall@5 与拒答阈值无关**（阈值只改「答不答」，
> 不改「找没找到」），所以「32.5% 是阈值 0.40 导致的」这个说法是错的。

| 指标 | 值 |
| --- | ---: |
| Recall@5 | **32.5%**（13/40） |
| MRR | 0.2096 |
| 事实型 Recall@5 | 36.7%（11/30） |
| 多跳 Recall@5 | **20.0%**（2/10） |
| 正确拒答 | **0/10** |
| 误放（该拒却答） | **10/10** |
| 误拒（被阈值挡掉的真答案） | **0** |
| 召回未命中（top10 内都没找到） | **23/40** |

> **三个数不要混**：`误拒 0` 是说没有真答案被**阈值**挡掉；
> `召回未命中 23` 是说那 23 条压根没被**检索到**。
> 前者是拒答策略的问题，后者是召回的问题 —— 修法完全不同。

**最要紧的两条**：

1. **召回只有 32.5%，且 8→10 无提升**（都是 17/40）—— 说明未命中的不是"排得靠后"，
   是在 top10 里都不出现。这比周四的 65% 低得多，原因见 §4.1（题目难度不同）。
2. **拒答在当前阈值下完全失效**：10 条同领域问题全部拿到高于 0.40 的分数。见 §4.2。

## 一、两条纪律（比任何技巧重要）

### 1.1 这 50 条是「调参集」，不是「评测集」

| 能 | 不能 |
| --- | --- |
| 比较不同 `top_k` / `overlap` / 阈值 | 报告"我们的检索准确率是 X%" |
| 比较换 embedder 的相对影响 | 跨语料泛化（只有 13 份自造文档） |
| 判断加过滤后命中率变没变 | 生成质量（本集子不调 LLM） |

**W7 的 200 条是另一批题，不得从这 50 条扩充。**
否则 W7 的数字是"调参时反复见过这些题"的表现，而这个虚高**没有症状** ——
不会报错，只会让最终报告比真实水平高一截。

本项目已踩过两次：W3 的 A7、W4 的 E5。详见 `eval/README.md` §〇。

### 1.2 锚点必须锚在**原文位置**，不能锚 `chunk.id`

实测（同一份语料，只改 `chunk_chars`）：

| chunk_chars | 块数 | 同一段文本的 chunk id |
| ---: | ---: | --- |
| 300 | 676 | 变了 |
| 500 | 532 | 变了 |
| 800 | 465 | 变了 |

`Chunk.id = sha256(source + page + 正文)[:16]`，**正文一变 id 就变**。
而改 `chunk_chars` 就是在改正文边界。

所以数据里 `gold_chunk_ids` 一律是 `[]`，真值是：

```json
{"source": "sse.md", "page": null, "head12": "TTFT（Time To", "quote": "TTFT（Time To First Token）= …"}
```

运行时按 `source` + `quote` 反查当前索引里的块。**不做这个映射，
周六一换切分策略就得重标 50 条。**

## 二、标注过程中真正踩的坑

标注不是"写 50 行 JSON"，而是**三件事反复来回**。

### 2.1 坑一：原始文件里成立 ≠ 索引里成立

子代理用**原始 md 文件**校验锚点：`text.count(quote) == 1`，50 条全过。
但我的脚手架一跑，**8 条解析失败**。

原因：检索用的不是原始文件，而是 `loader` **清洗后**的文本
（`loaders/clean.py`：空白压缩、全角空格→半角、连续换行压成两个）。
清洗改了字符，锚点就对不上了。

**教训**：锚点的校验对象必须是**`Chunk.text`**，不是 `Path.read_text()`。
这两者看起来是同一份文本，实际差着一次清洗。

> 这也解释了为什么"逐条回查原文确认没标错"这条要求在程序里做才可靠 ——
> 人工比对时看的是渲染后的 markdown，看到的和 `Chunk.text` 不一样。

### 2.2 坑二：直引号 vs 中文弯引号

8 条里 6 条是同一个原因：标注把 `"` 写成了 `“”`。
两者**视觉上几乎相同**，但字节不同。

```
原文：微调解决的是"**模型不会某种行为**"（格式、语气…）
标注：微调解决的是“**模型不会某种行为**”（格式、语气…
                    ↑ 直引号              ↑ 中文左引号
```

修法不能手改 —— 50 条里 8 处，人眼看 jsonl 看不出来。
写了 `scripts/repair_quotes.py`：对每条 quote 在源文件里**忽略标点差异**定位，
然后**取原文的切片**替换回去。

关键设计：**归一化只用于定位，不用于存储**。
先试精确匹配（快），失败才归一化后定位、再用同一坐标去原文切片。
如果把归一化后的字符串存进去，下次比对又会失败 —— 归一化是有损的。

### 2.3 坑三：锚点正好落在块尾，被 overlap 复制到下一块

剩下 3 条更隐蔽：`quote` 在源文件里**只出现 1 次**，但索引里命中 **2 块**。

实测 f-19 的两处命中：

```
chunk#91  quote at 419..459  ← 恰好结束在块尾（块长 459）
chunk#92  quote at   8..48   ← overlap 把上一块尾部 50 字复制到这里
```

`overlap=50` 会把上一块尾部复制到下一块开头（`delimiters._merge`）。
所以**任何贴着块尾结束的 quote 都必然命中 2 块** ——
而且缩短也没用（右边界始终贴着块尾）。

修法是反过来：**向外扩展**，让右边界推进到块内。
`scripts/expand_anchors.py` 固定左边界、向右延伸，或固定右边界、向左延伸
（优先向左，语义更完整），直到三种切分下都唯一。

修完的实例：

```
旧（{'300':1,'500':2,'800':1}） '两个 512 很容易被混成"512 维 512 字"'
新（{'300':1,'500':1,'800':1}） '两个 512 很容易被混成"512 维 512 字"。\n\n按'
```

**最终 50 个锚点在 300/500/800 三种切分下全部唯一命中 1 块。**

### 2.4 三个修锚点的脚本为什么不合并

它们解决的是**三种不同的病**，合并成一个会让"什么时候该用哪个"变模糊：

| 脚本 | 病 | 手段 |
| --- | --- | --- |
| `repair_quotes.py` | 标点字符不符 | 归一化定位 → 取原文切片 |
| `shorten_anchors.py` | 短语在文档里重复 | 从中心收缩 |
| `expand_anchors.py` | 正好贴在块尾 | 向外扩展 |
| `fix_anchors.py` | —— | 只诊断：报告每条在三种切分下的命中数 |

`fix_anchors.py` 是**唯一必须常跑**的那个：换文档、加题目时都用它先体检。

### 2.5 坑四：修复脚本换掉了锚点，而"合格"检查看不出来（**这个最危险**）

修完 8 个锚点后，基线从 47.5% 掉到 32.5%。一开始我以为是缓存或随机性，
但同一份索引、同一份参数，**分数变了 13%** —— 只可能是锚点本身变了。

查 f-19：题面是"多进程部署时，本地模型该怎么避免每个进程各加载一份？"，
锚点指向 `` `warmup()` 在启动时加载一次，多 worker 场景考虑独立 embedding 服务 `` ——
这与题面**自洽**，但更早那版锚点讲的是 512 维度。**它被换成了另一句。**

**谁换的**：`shorten_anchors.py` 与 `expand_anchors.py` 都会**主动改写** quote
（收缩或扩展）。它们改完仍"合格"—— 因为合格的定义只是
"存在且唯一"，而**新片段也是存在且唯一的**。

`repair_quotes.py` 反而安全：它只取**等长**的原文切片，长度不符就返回 None
（实测验证过）。这是它该有的约束。

**教训（三条，一条比一条硬）**：

1. **自动修复后必须看日志里的"旧值 → 新值"**，不能只看"不合格数 = 0"。
   合格只说明锚点可用，不说明它还是原来那一句。
2. **改写型脚本（收缩/扩展）必须逐条人工确认**。
   它们不是"修复"，是"换一个锚点"，而新锚点会指向不同的 chunk。
3. **数据改动后基线数字必须重跑并核对量级**。
   这次是"47.5% → 32.5%"这么明显的差异才被抓到；
   如果只差 1~2pp，很可能就被当成噪声放过了。

**所以那个 47.5% 不能采信** —— 它是"锚点被换掉一部分"的中间态跑出来的。
**本文所有数字都来自最终版数据**（50 个锚点全部验证唯一，
且逐条核对过题面与 `gold_answer` 自洽）。

> 这正是"每条标完立刻回查原文确认没标错"那条要求的价值：
> 它防的不是笔误，是**改完之后自己都忘了改了什么**。

## 三、脚手架：`eval/run_retrieval_eval.py`

### 3.1 一条命令

```bash
python -X utf8 scripts/tasks.py eval-retrieval
# 或（装了 make 的话）
make eval-retrieval
```

产出 `eval/results/retrieval-<时间戳>.{json,md}`。

**为什么有 `tasks.py` 而不只是 Makefile**：实测本机没有 `make`
（Windows 默认不带），而验收要求"一条命令出指标"。
让验收依赖一个没装的工具，等于交付一个跑不起来的东西。

所以命令只在 `scripts/tasks.py` 定义一次，`Makefile` 只做转发 ——
**两套定义必然漂移**（`make test` 与 `tasks.py test` 的参数会慢慢不一样）。

### 3.2 锚点反查：三种失败必须分开报

| 情况 | 含义 | 错误信息里有什么 |
| --- | --- | --- |
| 0 块匹配 | 锚点写错 / 该句被切碎 | 提示"写错"与"被切碎"两种成因 |
| >1 块匹配 | 不唯一（重复或块尾重叠） | 提示换更短/更居中的片段 |
| source 不存在 | 写成 `docs/sse.md` 而块只有 `sse.md` | 列出可用 source |

**静默跳过是最坏的处理**：一条解析不到 gold，会被算成"未命中"，
召回率凭空下降，而人会去调参数 —— 查错方向。

> 实测这条设计救了一次：第一次跑就是 6 条失败并整体退出，
> 而不是给我一个"召回率 35%"的假数字。

### 3.3 多跳的评分口径

`hit@k` = **两个锚点对应的块都在 top_k 里**。只命中一个算未命中。

排名取"较晚出现的那一处"（要看到两处，起决定作用的是后面的）。
`anchor_ranks` 单独记每个锚点的位置，所以能看出"差在哪一处"。

### 3.4 一个必须修的口径 bug

第一版把 `false_refusal` 写成"所有未命中的可答题"，跑出来是：

```
误拒 19 条  正确拒答 0/10
```

读起来像"拒答机制挡掉了 19 条真答案"，而**实际挡掉 0 条** ——
那 19 条的 top1 分数大都在 0.6 以上，只是没检索准。

现在分成三个数：

| 指标 | 含义 |
| --- | --- |
| `false_refusal` | top1 **低于阈值** —— 真被阈值挡掉的 |
| `false_accept` | 该拒却拿到高分 —— 拒答失效 |
| `recall_miss` | 没进 top_k —— **召回问题，不是拒答问题** |

修正后基线是：误拒 **0**、误放 **10**、召回未命中 **21**。
`tests/test_run_retrieval_eval.py` 有一条专门锁这个区分。

## 四、第一次基线跑出了什么（以及它说明的问题）

### 4.1 召回

| k | Recall@k |
| ---: | ---: |
| 1 | 12.5%（5/40） |
| 3 | 22.5%（9/40） |
| **5** | **32.5%**（13/40） |
| 8 | 42.5%（17/40） |
| 10 | 42.5%（17/40） |

按题型：

| 题型 | 条数 | Recall@5 | MRR |
| --- | ---: | ---: | ---: |
| 事实型 | 30 | 36.7% | 0.2581 |
| 多跳 | 10 | **20.0%** | 0.0643 |

**两个形状值得记**：

1. **5→8 有实质提升**（32.5% → 42.5%，+4 条），**8→10 完全无提升**。
   所以剩下的 23 条不是"排得靠后"，而是在 top10 里都不出现 ——
   `recall_miss` 是 23 条，与 `40 - 17` 对得上。
   **这说明加大 k 在 8 以上已经没用**，问题在召回本身。
2. **多跳的 MRR 只有 0.0643** —— 即使命中，也大多排在第 10 位之后。
   多跳需要两块同时进入 top5，这个组合难度是指数级的。

> ⚠️ **这个 32.5% 与周四的 65% 不可比**。
> 周四那 20 条是"挑好答的问"，今天这 50 条按规范覆盖 13 份文档、
> 包含多跳与拒答，没有挑题的余地。**把两个数字并列会严重误导。**

> 这个基线比周四的 65%（20 条）低，主因不是模型变差，而是**题目变难**：
> 周四的 20 条是"选好答的问"，今天这 50 条按规范覆盖 13 份文档、
> 包含多跳与拒答，没有挑题的余地。**两组数字不可比** —— 这也是
> "调参集不能当准确率"的具体体现。

### 4.2 拒答：10 条同领域问题，10 条全部误放

| id | 问题 | top1 分数 |
| --- | --- | ---: |
| r-01 | 换成 Qdrant 或 pgvector 时，向量索引的量化配置该怎么选？ | 0.6288 |
| r-08 | 给抽取任务做 LoRA / QLoRA 微调，显存和效果大概是什么水平？ | 0.5966 |
| r-02 | BGE-M3 和 text-embedding-3 相比… | 0.5670 |
| … | … | … |
| r-10 | 在 MTEB 或 BEIR 上刷分… | 0.5077 |

**拒答题的分数区间 [0.5077, 0.6288] 完全落在可答题区间 [0.4642, 0.8488] 内部。**

阈值扫描（用这 50 条）：

| 阈值 | 挡住几条拒答题 | 同时误拒几条可答题 |
| ---: | ---: | ---: |
| 0.40（当前） | **0/10** | 0/40 |
| 0.50 | 0/10 | 2/40 |
| 0.55 | 5/10 | 6/40 |
| 0.60 | 9/10 | **12/40** |
| 0.65 | 10/10 | **29/40** |

**没有一个阈值可用。** 要挡住 9 条拒答题，得拿 12 条真答案去换。

### 4.3 为什么这次比周四更可信

周四的 5 条拒答题是**跨领域**的（红烧肉、汇率）。那时我说"同领域问题会更难"，
但**没有证据**。今天换成了 10 条真·同领域问题：

> Qdrant / pgvector / BGE-M3 / nDCG / cross-encoder / IVF_PQ / DiskANN /
> vLLM / LangGraph / LoRA / ColPali / MTEB / BEIR

全部验证过在 12.3 万字语料里出现 **0 次**，但它们与语料讲的是**同一个领域**
（RAG/LLM 工程）。于是 bge 会给出高分：语料通篇在讲 embedding、检索、评测，
"另一个向量库"在语义上确实很近。

**这证实了周四的猜测，也把话说死了**：
分数不能用来判"能不能回答"，只能用来判"字面/语义上相不相关"。

### 4.4 那该怎么办（不在检索层）

1. **不要为了 10 条拒答题去牺牲 12 条真答案。** 维持 0.40。
2. **把拒答交给生成层**：`generation.ANSWER_PROMPT` 第 3 条要求模型
   "材料里找不到就直说"。模型看到 5 条讲 embedding 的块而被问 LoRA 显存，
   它是能说"材料没提到"的。
3. **真正的解法是补语料** —— 用户问 LoRA 是因为库里没有 LoRA 文档。
4. **这 10 条应该标成 `expect_uncertain`**（W4 的 `qa.jsonl` 有这个字段），
   在 W7 的 200 条里区分"该拒"与"该谨慎答"。

**报告里绝不能写"拒答准确率 0%，需要调阈值"** —— 那句话会导向
一个明确错误的方向（调阈值），而真正的动作是补数据。

## 六、诚实边界

| 边界 | 具体是什么 | 影响 |
| --- | --- | --- |
| **50 条太少** | 1 条 = 2pp | 只做相对比较。**Recall@5 32.5% 不是"我们的水平"** |
| **题是我自己出的** | 单人标注，且出题时已知语料内容 | 偏易（知道哪句好定位）。W7 需要双人标注 + 一致率 |
| **13 份自造文档** | 都是技术说明文，不是真实业务语料 | 参数结论不可外推到合同/工单 |
| **只用 recursive 策略** | 合并语料丢 `heading_level`（见 retrieval-tuning §2） | 章节过滤类能力没进这套评测 |
| **拒答只有 10 条** | 且全部误放 | "误放 10/10"的置信区间很宽，但方向明确 |
