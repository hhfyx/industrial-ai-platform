# 检索评测集的标注规范

> 本文定义 `eval/questions-50.jsonl` 怎么标。
> 规范先于数据存在 —— 否则 50 条标完了没人说得清标准是什么，
> 换个人标一遍结果就不一样，而**那种差异会被当成"模型变好了/变差了"**。
>
> W7 的报成绩集（questions-120）的字段格式与命中口径见 §九；
> 指标定义与防刷设计见 [metrics.md](metrics.md)（2026-11-30 冻结）。

---

## 〇、这套题的性质（比任何标注细节都重要）

**这是「调参集」，只能用来选参数。**

- 它用来回答"`top_k` 取 5 还是 8""`overlap` 取 50 还是 100""阈值 0.40 还是 0.50"
- 它**不能**用来报告"我们的检索准确率是多少"
- W7 的 200 条评测集是**另一批题**，且**不得从这 50 条扩充而来**

### 为什么这条纪律比标注技巧重要

一旦 W7 的评测集是从这 50 条长出来的，W7 报出来的数字就是
**"这些题我们在调参时已经反复见过"** 的表现 —— 而这个虚高没有任何症状：
它不是 bug，不会报错，只会让最终报告里的准确率比真实水平高出一截。

这件事本项目已经踩过两次，记在案上：

| 位置 | 当时的问题 |
| --- | --- |
| W3 的 A7 | 评测集与提示词迭代用的是同一批题 |
| W4 的 E5 | 同上，换了个场景重犯 |

所以本文件的第一条规矩是：**50 条的题面不得进入 W7 的 200 条**，
哪怕换个问法也不行 —— 同一个事实被问过一遍，人对它的"难易感"就已经变了。

> 具体防法写在 W7 的计划里：W7 出题时从**不同的文档**出题，
> 且第一批 20 条与这 50 条做过 `question` 的模糊去重。

## 一、为什么 `gold_chunk_ids` 是空的

任务给的格式里有 `gold_chunk_ids[]`，但**这个文件里它一律是空数组**。

### 原因：chunk id 会随切分参数变化

实测（同一份 13 文档语料，只改 `chunk_chars`）：

| chunk_chars | 块数 | 同一段文本的 chunk id |
| ---: | ---: | --- |
| 300 | 676 | 变了 |
| 500 | 532 | 变了 |
| 800 | 465 | 变了 |

`Chunk.id` 是 `sha256(source + page + 正文)` 的前 16 位（见 `schema.py`）——
**正文一变，id 就变**。而改 `chunk_chars` 就是在改正文边界。

所以硬编码 id 的后果是：**周六一换切分策略，50 条全部失效，重标一遍。**

### 做法：用原文位置锚定，运行时反查

```json
"anchors": [
  {"source": "sse.md", "page": null, "head12": "TTFT（Time To", "quote": "TTFT（Time To First Token）= 从发起请求到收…"}
]
```

`anchors` 是**唯一真值**，`gold_chunk_ids` 是运行时的派生物：

1. 按 `source` 找到当前索引里该文档的所有块
2. 在这些块里找**包含 `quote`** 的那一块
3. 把它的 `chunk.id` 填进 `gold_chunk_ids`

为什么带 `head12`：`quote` 可能很长（50 字），而 `head12` 是块首附近的最短定位。
**两者都存**是为了在 `quote` 匹配失败时能立刻判断"是边界变了还是内容变了" ——
只有 `quote` 时，这两种失败长得一模一样。

`page` 现在一律 `null`（markdown 没有页），但字段保留：**换成 PDF 语料时它必须被填上**，
否则"第 7 页那块"会退化成"某份文档里的一块"。

## 二、哪些算 gold（事实型）

### 判定「答案唯一」

一条问题算事实型，必须满足：

| 条件 | 反例 |
| --- | --- |
| 答案在语料里**只有一处**给出 | "chunk 大小默认多少" —— 文档里 300/500/800 都出现过 |
| 答案能在**单个 chunk** 内完整读到 | 答案需要合并两句话才能得出 → 这是多跳 |
| 问的是**事实**，不是判断 | ❌ "这个设计好不好"（没有唯一答案）|

### quote 的要求

**逐字原文，20~60 字，在该 source 里出现且仅出现 1 次。**

为什么要求"唯一"：如果同一段文字在文档里出现两次（比如目录与正文各一份），
那么"命中哪一块"就不确定了，命中判定会变得不可复现。

为什么 20~60 字：太短（<15 字）容易撞上别的段落；太长（>80 字）容易在
`chunk_chars=300` 时被切开，导致这条锚点在某些参数下失配。

### 问题不能包含 quote 的前 10 个字

否则测的是**字面匹配**而不是检索能力。bge 有语义能力，但如果问题照抄原文，
`HashingEmbedder` 那种纯字面实现也能满分 —— 那这张表就分不出"换 embedder"
的影响，而那正是它要测的东西之一。

## 三、多跳怎么标

**定义：需要跨 2 个不同 chunk 才能回答的问题。**

两个 `anchors` 分别指向一处，且两处**必须落在不同的 chunk 里**
（同一 chunk 内能读完的，按事实型标）。

### 三种可接受的多跳形态

| 形态 | 例子 | 为什么是两跳 |
| --- | --- | --- |
| **定义 + 实测数字** | "A 机制在 X 文档定义，在 Y 文档给了实测值，那个值是多少" | 一处有定义、一处有数据 |
| **两个互相比对的量** | "A 比 B 便宜多少" | A 的单价与 B 的单价各在一处 |
| **链条推理** | "如果按 A 的做法，B 会变快还是变慢，依据是什么" | 结论在一处、依据在另一处 |

### 一个反例（不该标成多跳）

> "先看 A 的定义，再看 A 的优缺点" —— 这两段常常**紧挨着在同一个 chunk 里**。

标成多跳前必须实测：用 300/500/800 三种切分各跑一遍，
确认两处 quote **确实落在不同的 chunk**。落在一起就说明它其实是事实型。

### 多跳的评分口径（写在这里，因为脚手架要实现它）

**`hit@k` = 两个 anchor 对应的块都在 top_k 里。** 只命中一个算**未命中**。

理由：多跳题的价值就是"模型要同时看到两处"，只给一处它答不出完整答案 ——
把它算成命中会让数字虚高，而那正是这个评测集最该防的事。

## 四、拒答怎么标

### 什么算合格的拒答题

**同领域、但语料确实没覆盖。**

| 合格 | 不合格 | 为什么 |
| --- | --- | --- |
| "pgvector 的索引类型怎么选" | "红烧肉怎么做" | 跨领域太容易，验证不了"同领域边界" |
| "bge-m3 和 bge-small 有什么区别" | "今天天气" | 同上 |
| "RAGAS 这个评测框架怎么用" | "公司的期权怎么算" | 同上 —— 后者是真没覆盖，但不是同领域 |

**为什么必须"同领域"**：跨领域问题任何检索器都会低分，测不出阈值的好坏。
真正的难点是"语料里有大量相似术语，但恰恰缺这一条" ——
比如语料通篇讲 bge-small-zh，问 bge-m3 才会拿到一堆高分干扰项。
这直接对应 `docs/retrieval-params.md` §3 那个"分数分不开"的问题。

### 必须做全文搜索确认

标完每一条，把问题里的**主题关键词**在全部 13 份文档 + README 的拼接全文里搜一遍，
**确认出现 0 次**。搜到了就说明语料其实覆盖了，这条是错的。

这条检查不能靠"我觉得没写过"：`docs/` 有 12.3 万字，
"我记得没提过 pgvector" 与 "确实没提" 之间差着一次 grep。

## 五、每条的字段说明

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | str | `f-01`..`f-30` / `m-01`..`m-10` / `r-01`..`r-10` |
| `type` | str | `fact` / `multi_hop` / `refusal` |
| `question` | str | 用户视角的口语发问，不含 quote 前 10 字 |
| `anchors` | list | **唯一真值**。fact 1 个 / multi_hop 2 个 / refusal 空 |
| `gold_chunk_ids` | list | **一律空数组**，运行时按 anchors 反查后填充 |
| `gold_answer` | str | 一句话标准答案（≤40 字）。给人工复核用，脚手架不判它 |
| `notes` | str | 为什么这么标 |

`anchors[].source` 是**文件名不含目录**（`sse.md`，不是 `docs/sse.md`）——
因为 `Chunk.source` 来自 `loader` 的 `file_path.name`。
写成 `docs/sse.md` 会让锚点解析失败，而失败的报错是"找不到这个 source"，
看起来像文档缺失（上一轮在过滤评测里踩过，见 `filter_eval.py` 的说明）。

## 六、标注完成后的自检（脚手架会做，标完也该手跑一遍）

1. **quote 逐字唯一**：`source` 全文里 `quote` 出现次数 == 1
2. **问题不泄题**：见下面的判据说明
3. **锚点跨切分稳定**：在 300/500/800 三种 `chunk_chars` 下，
   每条 quote 都恰好落在一个 chunk；多跳的两条落在**不同** chunk
4. **拒答确实没有**：关键词在全文出现 0 次
5. **id 唯一、数量对**：30 + 10 + 10

任何一条不过，**改数据而不是改检查**。这与 `chroma_acceptance.py` 里
`assert_gold_exists()` 是同一条纪律：**测试数据本身出错是最贵的错**，
它不会报错，只会让所有结论失真。

### ⚠️ 三条实测踩过的坑（这一节最值钱）

#### 坑一：校验必须对着 `Chunk.text`，不是原始 md 文件

第一次标注时，校验用的是 `Path.read_text()`：50 条全部通过。
但脚手架一跑，**8 条解析失败**。

原因：检索用的是 `loader` **清洗后**的文本（`loaders/clean.py`：
空白压缩、全角空格→半角、连续换行压成两个）。清洗改了字符，锚点就对不上。

**所以自检的命令是**：

```bash
python -X utf8 scripts/fix_anchors.py     # 对着真实索引体检，三种切分各跑一遍
```

而不是"我 grep 过原文了"。

#### 坑二：直引号 `"` 与中文弯引号 `“”`

8 条里 6 条是同一个原因。两者视觉几乎相同，字节不同。

```bash
python -X utf8 scripts/repair_quotes.py --dry-run   # 先看
python -X utf8 scripts/repair_quotes.py             # 再修
```

它按"忽略标点差异"定位、**取原文切片**替换 —— 所以修完必定是逐字原文，
而不是"我以为的原文"。

#### 坑三：锚点正好贴在块尾，被 overlap 复制到下一块

剩下 3 条：（在源文件里只出现 1 次，但索引里命中 **2 块**）。
`overlap=50` 会把上一块尾部复制到下一块开头，所以**贴着块尾结束的 quote
必然命中 2 块** —— 缩短也没用。

```bash
python -X utf8 scripts/expand_anchors.py            # 向外扩展，让它离开边界
```

### 泄题判据：不是"前 10 字是否出现"

第一版写成 `quote[:10] in question`，抓出来的唯一一条是：

```
f-22  问题「同一份中文合同上，LangChain 的切分留下了什么痕迹？」
      quote「LangChain 切出了 …支付合同价程…」
```

重叠的是**产品名**。问这件事必须提到它，要求"不提产品名也能问"
等于要求问题不像人话。

现在的判据是**最长公共子串 ≥5 字符且有 ≥4 个汉字**：
`LangChain` 是纯 ASCII，不算；`支付合同价程`（6 个汉字）才算。

> 阈值 5 是实测调出来的：口语化改写的中文问题与原文的重叠通常只有 4~6 字。
> 设 8 会让这条检查在真实数据上**从不触发**，等于关掉它。

## 七、这套集子能回答什么、不能回答什么

| 能 | 不能 |
| --- | --- |
| 不同 `top_k` 之间哪个召回更高 | 绝对准确率（50 条太少，1 条 = 2pp） |
| 加过滤前后命中率变没变 | 跨语料的泛化能力（只有 13 份自造文档） |
| 某个阈值下拒答准确率 | 阈值在真实业务语料上的最优值 |
| 换 embedder / 换切分策略的相对影响 | 生成质量（本集子只看检索，不调 LLM） |

**绝对不要**拿这套的数字去写"我们的检索准确率是 X%"。
它的样本量决定了它只能做**相对比较**。

## 八、怎么跑

```bash
# 一条命令出指标（跨平台，不依赖 make）
python -X utf8 scripts/tasks.py eval-retrieval

# 装了 make 的话也一样
make eval-retrieval
```

产出 `eval/results/retrieval-<时间戳>.{json,md}`。
加 `--out eval/results/xxx.json` 可固定名字（基线就叫 `retrieval-baseline`）。

常用参数：

```bash
python -X utf8 scripts/run_retrieval_eval.py --chunk-chars 300 --top-k 8
python -X utf8 scripts/run_retrieval_eval.py --threshold 0.55
python -X utf8 scripts/run_retrieval_eval.py --embedder hashing   # 只验证流程
```

> `k` 不用传：脚手架一次跑出 `Recall@{1,3,5,8,10}`，四档都在同一份结果里。
> 这是刻意的 —— **同一份索引、同一批查询向量**才能做前缀比较
> （k=10 的前 5 条必然等于 k=5 的结果）。

**基线结果与它的解读见 [docs/eval-50.md](../docs/eval-50.md)。**

## 九、W7 命中口径（2026-11-30 冻结）

> **此规则在 11/30 冻结。** 冻结的含义：出题开始后口径不许再动——
> 口径变了，前后两批数字不可比，等于前一批白跑。
> 要改只能整集作废重来，且必须在 metrics.md 顶部记录为什么。

适用范围：`eval/questions-120.jsonl`（W7 报成绩集）与后续所有评测。
调参集的口径已在上文各节定义，与此处一致但样本量不支持绝对数。

| 题型 | 命中口径 | 单独统计 |
| --- | --- | --- |
| 事实题（fact） | **任一锚点**进 top_k 即算命中 | by_type 里单列 |
| 多跳（multi_hop） | **两个锚点都**进 top_k 才算，只中一个 = 未命中 | by_type 里单列 |
| 拒答（refusal） | 无"命中"概念，由阈值判，三分类分开报（见 metrics.md §六） | 三分类并列 |
| 压缩场景 | Recall **算在压缩前的 chunk 上**（压缩不改变 chunk 身份） | ④ 组沿用 W6 口径 |

三个口径的理由：

1. **fact"任一锚点"**：fact 只标 1 个锚点，"任一"与"全部"等价；
   写"任一"是为防将来有人给 fact 加第二锚点时口径悄悄变严。
2. **多跳"两个都命中"**：多跳题的价值就是"模型要同时看到两处"，
   只给一处答不出完整答案——算成命中会让数字虚高
   （此口径自 W5 起已在脚手架 `evaluate_query()` 实现，冻结于此）。
3. **压缩前算 Recall**：若在压缩后的文本上算，压缩删句会伪装成
   检索退化——把压缩的风险算到检索头上，两个指标都被污染。

指标定义（公式 + 为什么 + 怎么刷 + 防刷）见 [metrics.md](metrics.md)。
